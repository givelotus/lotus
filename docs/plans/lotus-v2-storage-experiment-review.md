# Independent storage experiment review — 2026-10-15

The cache and Bloom experiments merit further work as explicit optional candidates; detached bodies merit a separate storage architecture prototype. None of these results supports adopting a default. Source inspection found no introduced consensus, proof-authentication, undo or sync-path defect in the reviewed changes. The principal remaining work is validation on the current integrated source, complete Bloom-enabled corruption/reorg coverage, and workloads that establish whether the cache has useful reuse under root churn.

This review was written in a new isolated monorepo worktree based on `e28844da`; only this document was added. Candidate checkouts were read-only. No build, benchmark, node or database operation was run in this review. Initial cache/Bloom inspection occurred during the body-locator measurement window; body-locator inspection started after the coordinator reported all twelve trials complete. Existing retained JSON/stdout and binary files were read to check counts, comparisons and SHA-256 provenance; passing test logs below are prior candidate evidence, not tests independently rerun by this reviewer.

## Findings and required follow-up

1. **Medium validation gap: full disk-state tests do not enable Bloom.** In the Bloom candidate, `test_disk_state.cpp::Options` (lines 51–55) leaves `bloom_bits_per_key` at zero. `existing_disk_state_test` therefore supplies baseline regression evidence only. `experiment.cpp` checks roots, four sampled proofs/coins, replacement/disconnect, reopen, raw-row equality and WAL faults with Bloom, but does not run the existing corruption, sibling-kind, undo-corruption, alternate-reorg, resource and callback suites under Bloom. Before integration, parameterize the full suite over 0/10 bits and retain both results. Add actual SST filter/meta-block corruption and missing-filter coverage, including reopen and lookup, rather than inferring filter correctness solely from WAL injection.

2. **Medium applicability gap: the cache measures unchanged-root reuse, not mutation performance.** Every successful insert/erase changes the cache context; uniform phases have zero hits and capture/eviction overhead. `measurement.cpp::Reads` checks fixture presence/value and aggregates sibling counts/values. Its runner compares root, phase, observation aggregate and Gets between variants; it does not compare every measured proof bitmap, sibling hash and encoded coin byte. Exact proof equality is covered separately by `manifest_test.cpp` and the disk-state oracle suite. Keep that distinction in claims. A future workload should record exact sampled results alongside realistic node query reuse, root churn, absent lookups, large coins and transactions. No mutation or node throughput benefit is established.

3. **Medium integration gap: no current-source or combined validation exists.** Apply any future candidate to a new exact integrated source revision, rerun the required suites there, and test cache/Bloom combinations independently. Indexed candidates, journal recovery, finalization and complete node reorg coordination are outside these generic-store measurements. Keep defaults at zero meanwhile.

4. **Low evidence limit: allocation and durability claims must remain precise.** Cache accounting is not RSS or a strict allocator-byte ceiling. Store and transaction have separate budgets; map/list/vector overhead and temporary proof construction are additional. Bloom's fault harness simulates WAL append/sync errors, not process termination or power loss. Broader resource and crash-recovery claims need their own tests. Existing documentation generally states these limits correctly.

## Authenticated cache correctness assessment

`disk_state.cpp::Prove` (candidate lines 965–1020) keys entries by query coin key and binds them to the complete root `Summary`, including digest and kind/cardinality classification. A hit rereads every original proof-path node and terminal coin-table row through the original callback and compares exact optional bytes. Changed or missing rows evict the entry and execute `BuildProof`, including node parsing, coin/tree agreement and proof verification. There is no newly supplied digest treated as proof of authentication.

`AuthReadCoin` still independently reads the queried coin row and checks membership and exact encoded coin equality. This matters for absent queries: a cached absence cannot hide an orphan coin row. Usability checks precede cache access, including empty-root proofs whose read manifest is empty. Store and transaction caches are separate; transaction reads include its overlay. Root changes invalidate context on the next proof operation, so retained stale entries cannot serve a changed root. Returning to the same root through a disconnect remains safe because manifest rows are reread. Abort destroys the transaction implementation and cache; reopen creates a fresh process-local view. Successful commit retains the finished transaction object until released, but its usability guard prevents further proof service.

The cache changes no on-disk encoding, commit batch, undo encoding or write synchronization. Existing poisoned-store checks still reject after an ambiguous WAL failure. The new warm-cache regressions explicitly check that a warmed empty proof cannot bypass poisoning. The LRU's 128-entry cap and accounted budget bound retained entries; oversized captures bypass retention. Allocation failure handling does not publish an unverified proof. This assessment assumes the backend's existing single-writer/view-lifetime contract; it does not establish concurrent thread safety.

Retained CTest evidence has two passing entries: `cache_manifest_test` and `disk_state_test`. The latter executes its full function suite once with budget zero and once at 1 MiB. Manifest tests independently cover exact proof fields/coin bytes, changed and missing warm node/coin rows, unchanged output on corruption, warm absence/orphan detection, context/cardinality change, tiny budgets and eviction. This is meaningful cache-specific evidence, with no C++ assertion count inferred from the two CTest entries.

The retained measurement has **12 successful invocations**, **84 JSON records** (12 seed records plus 72 phases), and **72,000 queries**. This review recomputed equal paired roots and per-phase observation/Get tuples for all six disabled/enabled pairs. Maximum retained accounting is **565,772 bytes**. Uniform phases have no hits; warm repeated phases have 1,000 hits. The first repeated phase at 1k has 941 hits/59 misses because preceding uniform work already warmed five identities; this is consistent with source order rather than evidence of a cold-cache result.

The published warm CPU reductions support investigating repeated parsing/hashing cost at an unchanged root. The reported uniform-proof CPU increases and unchanged logical Gets also matter. Heavy QEMU/Dart contention, small cardinalities and three trials limit latency inference. Reopen occurs in the same process with uncontrolled OS caches. The results do not establish physical I/O savings, memory savings, seed/mutation speed or node TPS.

## Bloom, batching and durability assessment

The implementation adds an owned LevelDB filter policy, validates 0–30 bits/key before opening a home, and leaves zero as default. Member destruction order destroys the DB before its filter/cache. Filter choice is absent from schema/profile bytes. `dboptions.paranoid_checks` remains true, and normal reads retain checksum verification. Bundled `table.cc::ReadMeta/ReadFilter` verifies filter metadata/block checksums under paranoid checks and falls back to unfiltered reads if loading the optional filter fails. This source path is sound, while the missing candidate-specific corruption coverage above remains material.

No batching or sync policy is changed in the backend. Batches of 100/1,000 are fixture commit boundaries, so their different undo histories are expected. The experiment compares every raw key/value row across Bloom settings at equal batch size and excludes only undo rows when comparing live state across batching. It independently constructs the final oracle root, checks four proof/coin samples per measured invocation, disconnects replacement, compares metadata on reopen and compares raw snapshots after reopening. Opposite-option reopen currently checks the root; stronger bidirectional post-reopen proof reads should accompany the full Bloom suite.

The separate fault cases cover both Bloom settings, append/sync failures, database-error classification, poisoning, complete old-or-new root/metadata recovery and disconnect of a recovered new checkpoint. Initial harness lock-lifetime failure and successful retry logs are retained. These are honest operational error tests, not power-loss simulation.

The **12 measured records** all have return code zero, one shared live-row digest, and one raw-row digest per batch size across Bloom settings/trials. This review independently checked those counts/digests and the recorded binary hash. Logical Gets are exactly **262,924** at batch 100 and **165,081** at batch 1,000 for both Bloom settings. Recomputed median Env read-call counts are **154,328 → 81,614** and **76,725 → 36,670**. Median append bytes increase by **586,468** and **273,423**, respectively, matching the published filter-write regression. The raw reports support these statements.

Those read counts are Env API calls, including background engine activity and mmap spans; they are not SSD reads. Close joins engine background work before cumulative append counters are sampled. Larger batches change memory use and durable/undo boundaries, so their savings cannot authorize a change to live block publication. Three contended trials with uncontrolled OS caches support an optional Bloom investigation and a batching tradeoff study, with no default or whole-node performance conclusion.

## Recommendation

Continue Bloom as the simpler optional operational feature after full enabled-mode corruption/reorg validation on the exact integrated pin. Continue authenticated proof reuse only alongside measured real reuse/root-churn rates and explicit total memory accounting. Preserve all original candidates and their evidence; do not merge one by treating its benchmark as consensus or deployment approval. Further work should have separate correctness gates and a later coordinated measurement window.

Review confirmed trials and summary blobs are unchanged and the annotation agrees with the matched fixture: V(2) is height 3, ID `59572fa921a7157edc12d88bb3845bb351d5985656d658b3c5319378fbddde6f`, root `33dee9ed5f17cd7e785d9b977a75b61e26ee48cea3f77da3b4fb71b22cacfd5c`; V(3) is height 4, ID `7fb8139809ad5379efe2c6115b85b858d057cb1c95ae03b683847b2963c1db58`, root `1f4f143925cffbe1953a9757ea70b152cc1b4db8d804909281f507188fa5281d`, with four fixture coins. This is source reconstruction, not contemporaneous timing output.

2. **High adoption blocker, explicitly acknowledged by the candidate:** no atomic state/body publication, durable locator database, crash recovery, reader leases, prune coordination or migration is implemented. Export duplicates bytes already retained in undo. File/parent `fsync` does not establish the LevelDB backend's macOS F_FULLFSYNC durability contract. Success/failure at each publication boundary, orphan/truncated extents, ambiguous synchronization, journal resume and concurrent pruning remain untested and unimplemented integration dependencies. This is an architecture prototype, not a replacement for retained bodies.

3. **Medium interpretation limit:** the read paths provide different audit guarantees. Baseline `ReadRetainedBlockBody` checks current retained undo/context binding on each read; detached reads rely on a previously authenticated connected identity and reauthenticate only returned body/frame commitments. The reduced work is intentional. Do not present the read comparison as equivalent validation cost or equal corruption-audit coverage. A raw request authenticates selected bytes and membership, without proving the whole file remains a valid block or that its offset is the original sequential frame position. These limits do not permit transaction substitution because both requested identities and membership are checked.

4. **Medium scaling/resource gap:** the accepted timing fixture is only 351 bytes and two transactions; its selected spend is 108 bytes. Full per-transaction proofs use O(n log n) retained metadata. Derivation decodes/reencodes the whole body and builds all proofs; supplied byte caps bound response allocation, not total decoded-object/proof memory, CPU, retention or concurrent readers. Larger framing controls are not accepted block fixtures and supply no large-block throughput evidence. Future API/storage design needs explicit quotas for those dimensions.

### Authentication and lifecycle assessment

Export calls the original retained-body validation boundary before deriving locators, creates an exclusive non-followed file, and syncs file and parent. It does not change state or publish availability. Failures can leave an orphan and preserve caller output. This is appropriate for a detached export with its documented cleanup contract.

`ReadRaw` opens a regular file with `O_NOFOLLOW`, checks file size against the anchored header, block ID/ChainID, target/PoW and genesis identity, then verifies requested TxId/TxHash and a count-bound TransactionRoot inclusion proof. The proof implementation follows the existing uneven largest-power split and leaf/internal/count domains. It caps proof depth at 32, checks index/count and validates canonical prefix width and exact length, offset/size arithmetic, response cap, parsed frame and recomputed identities. No caller offset or sibling is trusted. Authentication remains sound if unrelated bytes are corrupt or if a valid frame also appears at another location: the response is still exactly the requested committed transaction. Active membership and the anchor's prior contextual validity must come from the chain owner.

`ReadBody` rereads and fully decodes the file, checks all transaction framing and the complete TxRoot, and binds the decoded header to the requested ID again after the initial positioned header check. That second ID check handles concurrent header replacement between reads. Neither read path repeats historical VM/state transitions. Historical reads after disconnect are intentionally allowed; missing/pruned files report unavailable. This is availability behavior, not a prune/reorg coordinator.

Source correctness controls compare exact body/raw coinbase/spend bytes, exercise offset/length/index/count/identity/proof mutations and header/prefix/frame corruption, capacity, truncation, trailing bytes, missing file, overwrite refusal, reopen and historical disconnect. Additional counts 1/3/5/17/1,000 check every transaction and three-byte frame prefixes. `DecodeBlockWire` rejects an empty transaction list before locator proof derivation, so the recursive proof builder's nonempty precondition is met. The larger generated controls establish framing/cryptographic behavior only; they are not claimed as accepted contextual blocks. No crash, failed-write/fsync, prune-reader race or real restart recovery gate is supplied.

### Retained costs and recommendation

Independent inspection confirms **12 successful records**, three per mode, each with 1,000 repeated reads. Body reply totals are 351,000 bytes; raw replies total 108,000 bytes. Median foreground C++ allocation traffic matches the result table: baseline body 273,002 calls/74,483,016 requested bytes; detached body 87,000/9,223,000; baseline raw 369,002/84,598,016; positioned raw 41,000/4,227,000. These are cumulative foreground operator-new requests, not live memory or total engine allocation.

The full detached path reports 2,000 positioned calls/485,000 bytes and raw reports 3,000/243,000 bytes. Those counts match 134-byte header plus full 351-byte body, or header plus one-byte prefix plus 108-byte frame, respectively. Baseline positioned counters are uninstrumented zeros. Process CPU includes background work; lifetime RSS includes setup; OS caching and substantial host contention prevent physical-I/O or general latency claims. The benchmark raw check compares reply length each iteration, while separate correctness controls establish exact byte parity. Recorded elapsed improvements support the hypothesis that removing repeated undo auditing and full-body redecoding can reduce read work for this fixture.

Proceed only with a separate immutable-body schema/API design and explicit atomic publication/recovery/pruning invariants. A same-LevelDB-batch checked body record is a reasonable design to evaluate before append-only files; it must still specify authenticated summaries, profile/version binding, availability and active status, journal pins, retention quotas, disconnect semantics and migration/rollback. File-based publication additionally needs durable-before-index ordering and orphan recovery. Keep this detached experiment outside defaults until those dependencies and accepted larger-fixture checks exist.
