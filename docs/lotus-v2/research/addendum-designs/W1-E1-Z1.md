## W1. Async wallet notification queue (eCash tier)

### W1.1 What changes, and what must not change

Move delivery of `Chain::Notifications` callbacks for **wallets only** from
the shared scheduler thread to a per-registration FIFO worker. The worker
blocks the producer when it is full.

Why per-subscriber semantics stay identical:
- the worker is one thread;
- it is FIFO;
- it receives events in scheduler order.

So the `CValidationInterface` contract (serial callbacks, in generation order)
still holds for each wallet. The changes are confined to these:

1. **Cross-subscriber timing.** A wallet may lag Chronik, PeerManager, etc. No
   ordering across subscribers is documented (`validationinterface.h` class
   comment), so this is allowed.
2. **Fences.** Fences that wait only on the main queue no longer cover the
   wallet. Fixed in W1.3.
3. **Lifetime.** Unregister must drain and join the worker.
4. **Overflow and exceptions.** These get explicit policies, below.

**Avalanche is not moved.** `avalanche::Processor` registers through the same
`handleNotifications`. Its `updatedBlockTip`/`transactionAddedToMempool`
timing feeds polling. Making it asynchronous is a behaviour change outside W1,
so delivery is opt-in per registration. `bench/wallet_balance.cpp` keeps
synchronous delivery.

### W1.2 Decisions

- **Scope.** Opt-in through a new `interfaces::Chain::NotificationDelivery`
  argument. The default stays `SCHEDULER_THREAD`. Only `CWallet::AttachChain`
  passes `DEDICATED_WORKER`.
- **One worker per wallet registration.** Not one shared worker:
  - each wallet's FIFO stays independent;
  - unload drains only that wallet;
  - a thread per loaded wallet is acceptable.
  Thread name: `walletnotify` (12 characters, within the Linux 15-character limit).
- **Backpressure: block the producer.** Do not use Chronik's fail-closed mode.
  - The producer is the scheduler thread, or the `FlushBackgroundCallbacks` caller at shutdown.
  - Why: `AttachChain` holds `cs_wallet` for the whole load rescan, which can take minutes on a busy node, while events keep arriving. A fail-closed queue would shut the node down during a normal wallet load.
  - Blocking adds nothing new. In the worst case it reproduces today's behaviour, where the scheduler waits on `cs_wallet`. That wait already throttles validation through `LimitValidationInterfaceQueue` (`validation.cpp:4731`, `CallbacksPending() > 10`).
  - Limits (bounded memory, not lossy): `MAX_TASKS = 65536`, `MAX_BYTES = 64 MiB` per wallet, `TASK_OVERHEAD = 256` bytes.
  - A single task larger than the byte limit is admitted only when the queue is empty, so a 32 MB block never deadlocks the queue.
- **Exceptions.** Today an exception thrown by a wallet callback on the scheduler thread terminates the process. New behaviour:
  1. On the first worker exception, `m_failed` is set.
  2. The node logs `FATAL: wallet notification worker failed; shutting down. The wallet rescans from its last flushed best block on restart.` and calls `StartShutdown()`. This is the same mechanism Chronik uses (`<shutdown.h>`).
  3. **All later queued tasks for that wallet are discarded, not run.** In particular a later `chainStateFlushed` must not advance the persisted locator past a block the wallet failed to apply.
  4. `Sync()` still completes. Discarded tasks count as completed.
- **Unload.** `NotificationsHandlerImpl::disconnect()` unregisters, then calls `StopWorker()`.
  - `StopWorker()` runs every accepted task, then joins. Accepted events are real wallet updates.
  - Events that reach `Enqueue` after `Stop` are dropped. The wallet is unloading, and its persisted locator makes the next load rescan.
  - **The caller must not hold `cs_wallet`.** Every in-tree caller already satisfies this: `RemoveWallet` from RPC, `UnloadWallets` at shutdown, the `CWallet::Create` failure path at `wallet.cpp:3003-3005`, which is outside `AttachChain`'s lock, and `TestUnloadWallet`. The rule is documented on `Handler`.
- **Fence completeness.** Add `ValidationSignals::SyncSecondaryQueues()`. `BroadcastTransaction(wait_callback=true)` calls it after its main-queue promise resolves. This covers `submitpackage`, Qt `walletview.cpp:315` and future callers. As a side effect `submitpackage` also waits for Chronik indexing (eCash `060`), which is the documented intent of `wait_callback`.

**Commit W1-a: `util: let BoundedTaskQueue block producers instead of failing on overflow`**

File: `src/util/bounded_task_queue.h` (owned by eCash `060`; the change is additive).

- Add `enum class Overflow { FAIL, BLOCK };`.
- New constructor:
  `BoundedTaskQueue(size_t byte_limit, size_t count_limit, std::function<void()> fail, Overflow overflow = Overflow::FAIL, std::string thread_name = {})`.
  - Chronik's call is unchanged, which keeps it at `FAIL`.
  - The worker calls `util::ThreadRename(thread_name)` when the name is non-empty. Include `<util/threadnames.h>`.

     This form cannot underflow, even when an oversized task was admitted.

  4. Otherwise push exactly as today, including the allocation-failure path, which calls `m_fail` and sets `m_failed`/`m_stopping`.

- **`Stop()`** additionally calls `m_drained.notify_all()` after setting `m_stopping`, so blocked producers wake and return `false`.

### W1.4 Ordering, shutdown, unload, rescans: argument

- **Ordering.** One producer (the scheduler), FIFO, one consumer. The ordering doc in `validationinterface.h` (`TransactionRemovedFromMempool` before `BlockConnected`, and so on) is preserved per wallet.
- **`BlockUntilSyncedToCurrentChain`.** It does `waitForNotificationsIfTipChanged` → `SyncWithValidationInterfaceQueue()`:
  1. The main queue drains, so every earlier event has been handed to the wallet queue.
  2. `SyncSecondaryQueues()` then waits for `m_completed >= m_submitted`.
  Because the main fence passed, no producer is blocked mid-`Enqueue` for an earlier event, so the target count is complete. The unchanged-tip early return behaves exactly as today. Its mempool staleness is today's semantics, and `sendrawtransaction`/`submitpackage` are covered by the explicit fences.
- **Shutdown** (verified order):
  1. `client->flush()`.
  2. `scheduler->stop()`.
  3. `ForceFlushStateToDisk`, which generates `ChainStateFlushed`.
  4. `FlushBackgroundCallbacks()`. This flushes the main queue on the shutoff thread, which may block on a full wallet queue while the worker keeps draining, then waits for the wallet queues. The wallet's best-block locator is therefore written before unload.
  5. The second flush's `ChainStateFlushed` is never dispatched: the scheduler has stopped. That is the same as today.
  6. `client->stop()` → `UnloadWallets` → `RemoveWallet` → `disconnect()` drains (normally empty) and joins.
  7. `UnregisterAllValidationInterfaces()` finds no live workers.
- **Wallet unload during operation.** `unloadwallet` now waits for that wallet's queued events (bounded by the limits) before `NotifyUnload`/`WaitForDeleteWallet`. Previously the scheduler could still run wallet callbacks after unregister through the in-flight `shared_ptr`. Draining is strictly safer.
- **Rescans.**
  - `AttachChain`: register, then rescan under `cs_wallet`. Queued events wait on `cs_wallet` in the worker instead of the scheduler, so the documented duplicate-processing semantics are unchanged.
  - `m_attaching_chain`-gated `chainStateFlushed`: FIFO puts it after the `blockConnected` events that waited for the lock, exactly as today.
  - `rescanblockchain`/import rescans run on RPC threads, concurrently with the worker, as they ran concurrently with the scheduler before.
  - `requestMempoolTransactions` calls the wallet directly, bypassing the proxy, as before.
- **Deadlocks.**
  - New waits: producer → worker (when full), and fence callers → worker. The worker needs `cs_wallet`, and through `chain()` calls also `cs_main`/`mempool.cs`.
  - Every fence caller already waited on the main queue, which today runs the same wallet code. So any caller that holds one of those locks already deadlocks today. `SyncWithValidationInterfaceQueue` asserts `!cs_main`; `BlockUntilSyncedToCurrentChain` asserts `!cs_wallet`.
  - The worker never waits on the scheduler. No wallet callback calls a fence.
  - The producer blocks only in proxy callbacks, which run with no lock held.
  - `Enqueue(BLOCK)` asserts it is not on the worker. The new `disconnect()` drain documents and asserts `!cs_wallet` through the call-site comment. Add `AssertLockNotHeld(wallet->cs_wallet)` in `RemoveWallet`.
- **Memory.** Validation can now run up to 64 MiB / 65536 events per wallet ahead of a stalled wallet before backpressure reaches `LimitValidationInterfaceQueue`. That bound is deliberate.
- **Qt.** `CWallet` signals (`NotifyTransactionChanged`, ...) now fire on `walletnotify` rather than the scheduler thread. Qt connects them with queued connections, so this is thread-safe. Not exercised: Qt is not built in the coordinator gates.

### W1.8 Risks

- **`unloadwallet` latency** is now bounded by the queue depth, not instant.
- **Repeated rescans.** A wallet stalled by a long rescan lets up to 64 MiB of events accumulate. Bounded, but visible in memory.
- **Hidden lock dependency in the drain.** Some out-of-tree caller may reset the handler under `cs_wallet` (Qt was checked: unload is on the GUI thread without the lock; not run). The assert catches it in debug builds.
- **Exception policy.** Moves from terminate to shutdown-plus-discard. This is safer, but different.

### E1.2 bitcoin-cli HTTP client (Beast), exact behaviour

  `static HTTPReply HTTPPost(const std::string &host, uint16_t port, const std::string &target, const std::string &auth_header, std::string body, int timeout_secs)`.
- `HTTPReply` keeps `status`, `error` (default -1) and `body`.
- Keep `http_errorstring(int)` with identical numbers and strings, using a local enum that mirrors libevent's values:

  | Value | Name | String |

  | 1 | `EOF` | "EOF reached" |
  | 2 | `INVALID_HEADER` | "error while reading header, or invalid header" |
  | 3 | `BUFFER_ERROR` | "error encountered while reading or writing" |
  | 4 | `REQUEST_CANCEL` | "request was canceled" |
  | 5 | `DATA_TOO_LONG` | "response body is larger than allowed" |

**Transport:**

- One `boost::asio::io_context`, `tcp::resolver`, `beast::tcp_stream`, async operations, `io.run()`.
- Resolve `host`/`port` with `async_resolve`, flags none. Then `beast::async_connect` over the results.
- Resolve or connect failure → `status = 0` and the error mapping below.

**Request** (`http::request<http::string_body>`):

- Method POST, `target` = `"/"` or `"/wallet/" + urlEncode(rpcwallet)`, version 11.
- Fields, in this order: `Host: <host>` (host only, no port, as today), `Connection: close`, `Content-Type: application/json`, `Authorization: Basic <b64>`.
- Body = the request with its trailing `"\n"`. `prepare_payload()` sets `Content-Length`.
- No `User-Agent` and no `Accept-Encoding`, so the server never compresses.
- Header order and the exact header set are checked against the E1.1 recording. If libevent's order differs, match it.

**Response:**

- `http::response_parser<http::string_body>` with `body_limit(boost::none)` (unlimited; libevent's client default) and `header_limit(1 << 20)`.
- Read in a loop of `http::async_read_some` until `is_done()`. Beast's handling covers chunked encoding and EOF-delimited bodies.
- **Timeout = inactivity, matching `evhttp_connection_set_timeout`:**
  - if `timeout_secs > 0`, call `stream.expires_after(seconds(timeout_secs))` before resolve+connect, before the write, and before **each** `async_read_some`;
  - if `<= 0`, call `stream.expires_never()`. This replaces the 5-year emulation, which was a libevent limitation.

**Error mapping** (`status = 0`, `error = …`):

| Condition | Code |

| `beast::error::timeout` | 0 |
| `http::error::end_of_stream` / `asio::error::eof` / `connection_refused` / `connection_reset` / resolve failure / any connect failure | 1 |
| `http::error::*` header or body parse errors | 2 |
| Other socket read/write errors | 3 |
| Body limit | 5 (unreachable when unlimited) |

### E1.3 torcontrol on Asio, exact behaviour

Move the declarations of `TorControlReply`, `TorControlConnection`,
`SplitTorReplyLine`, `ParseTorReplyMapping` and new
`std::optional<CService> ParseTorControlAddress(const std::string&)` into
`src/torcontrol.h`, so unit tests can drive them. `TorController` stays in the
.cpp. The public functions keep their signatures: `StartTorControl(CService)`,
`InterruptTorControl()`, `StopTorControl()`, `DefaultOnionServiceTarget()`,

**`TorControlConnection(boost::asio::io_context &io)`**

Members:
- `std::optional<tcp::socket> m_socket`;
- `std::string m_rbuf`;
- `std::deque<std::string> m_wqueue`;
- `bool m_writing`;
- `uint64_t m_gen` (generation; increments on every `Disconnect()`);
- `connected`, `disconnected`, `message`, `reply_handlers`, `async_handler`, as today.

`Connect(center, connected, disconnected)`:
1. If a socket exists, `Disconnect()`.
2. Parse with `ParseTorControlAddress`, numeric only, same accepted forms as `evutil_parse_sockaddr_port`. On failure, log `tor: Error parsing socket address %s` and return false (no reconnect, as today).
3. Create the socket. On a synchronous open failure, log `tor: Error connecting to address %s` and return false.
4. Store the callbacks, call `async_connect`, and return true.
5. On completion, if the generation still matches:
   - success → log `tor: Successfully connected!` and call `connected(*this)`, then start reading;
   - error → log `tor: Error connecting to Tor control socket`, `Disconnect()`, `disconnected(*this)`.
6. Writes queued before connect start once the connection succeeds.

Read loop: `async_read_some` into a 64 KiB buffer and append to `m_rbuf`. Then, while `m_rbuf` holds a `'\n'`:
1. Take the line and strip one trailing `'\r'` (matches `EVBUFFER_EOL_CRLF`: optional CR before LF).
2. Apply the **unchanged** body of today's `readcb` loop: lines of fewer than 4 characters are skipped; the status code and lines are accumulated; `' '` dispatches. Codes `>= 600` go to `async_handler`, otherwise to `reply_handlers.front()` followed by `pop_front`, or to the "Received unexpected sync reply" log.
3. Check the generation after each dispatch. A handler may have called `Disconnect()`; if so, stop.

After the loop: if `m_rbuf.size() > MAX_LINE_LENGTH`, log `tor: Disconnecting because MAX_LINE_LENGTH exceeded` and call `Disconnect()` **without** `disconnected` (preserved). On EOF, log `tor: End of stream`; on any other error, log `tor: Error connecting to Tor control socket`. Either way, call `Disconnect()` then `disconnected(*this)`.

`Command(cmd, handler)`:
1. Return false if there is no socket.
2. Append `cmd + "\r\n"` to `m_wqueue` and push the handler.
3. If idle and connected, start `async_write`.
4. Return true.

A write error is handled like a read error: `Disconnect()` + `disconnected`.

`Disconnect()`: `++m_gen`, close the socket with error-code overloads, reset the socket, and clear `m_rbuf` and `m_wqueue`. `reply_handlers` and `message` are not cleared. This mirrors today, where only the bufferevent is freed. Completion handlers check `m_gen` and ignore `operation_aborted`.

**`TorController(io_context &io, center, target)`**

- `asio::steady_timer m_reconnect_timer{io}` replaces `reconnect_ev`. The constructor's out-of-memory log goes away.
- `disconnected_cb`:
  1. Remove the local service.
  2. If `reconnect`, log as today.
  3. `m_reconnect_timer.expires_after(std::chrono::milliseconds(int64_t(reconnect_timeout * 1000.0)))`, then `async_wait` → if not aborted, `Reconnect()`.
  4. `reconnect_timeout *= RECONNECT_TIMEOUT_EXP`.
- `connected_cb` resets `reconnect_timeout = RECONNECT_TIMEOUT_START`.
- `RECONNECT_TIMEOUT_START = 1.0`, `RECONNECT_TIMEOUT_EXP = 1.5`. No cap (preserved).
- The authentication and onion logic is unchanged text-for-text:
  - `protocolinfo_cb`: password beats NULL, NULL beats SAFECOOKIE, then the HASHEDPASSWORD-missing message. Quote escaping in `-torpassword`.
  - `authchallenge_cb`: 32-byte nonce check, ServerHash verification.
  - `ComputeResponse` HMACs.
  - `auth_cb`: the `-onion` default proxy `127.0.0.1:9050`; the `SetReachable` rule.
  - `ADD_ONION %s Port=%i,%s` with `NEW:ED25519-V3`.
  - `add_onion_cb`: the 250/510/other branches; `ServiceID`/`PrivateKey`; `WriteBinaryFile(onion_v3_private_key)`; `AddLocal(LOCAL_MANUAL)`.
  - Destructor `RemoveLocal`.

**Thread:**

```cpp
static std::unique_ptr<boost::asio::io_context> g_tor_io;
static std::thread torControlThread;
static void TorControlThread(CService target) {
    auto guard = boost::asio::make_work_guard(*g_tor_io);
    TorController ctrl(*g_tor_io, gArgs.GetArg("-torcontrol", DEFAULT_TOR_CONTROL), target);
    g_tor_io->run();
}   // ctrl destroyed on the tor thread: RemoveLocal as today
void StartTorControl(CService t) {
    assert(!g_tor_io);
    g_tor_io = std::make_unique<boost::asio::io_context>(1);
    torControlThread = std::thread(&util::TraceThread, "torcontrol", [t] { TorControlThread(t); });
}
void InterruptTorControl() { if (g_tor_io) { LogPrintf("tor: Thread interrupt\n"); g_tor_io->stop(); } }
void StopTorControl() { if (g_tor_io) { torControlThread.join(); g_tor_io.reset(); } }
```

- `io_context::stop()` is thread-safe. It is sticky if called before `run()`, which matches `event_base_once` + `loopbreak`.
- Pending handlers are destroyed without being invoked. They capture only raw `this`, so this is safe.
- `evthread_use_*` disappears.

**Logging:** every log string and category (`BCLog::TOR`) is unchanged.
