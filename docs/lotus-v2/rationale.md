# Design rationale and claim boundaries

Status: explanatory, not normative. [Consensus](consensus.md) owns rules; [decisions](decisions.md) owns alternatives.

## Authorization and assets

Alternative paths express OR; the required branches within one path express AND. Branch MASTs select methods within a role. Asset accounting is a separate obligation: conserving token units does not prove the owner approved, and owner approval does not authorize additional supply. Program-derived token identity supports continuing mint authority and is the chosen model (D05): a token ID is the root of its mint scripts. The earlier outpoint-derived design is superseded; which of its historical code is reusable remains to be settled.

A branch tree needs membership, while a transaction tree needs order and a state map needs key position and nonmembership. Calling all three “Merklix” obscured their different contracts. The proposed branch proof uses sorted children; it must not be silently reused to authenticate transaction order.

Leaf/interior tags follow the principle illustrated in [RFC 6962 §2.1](https://www.rfc-editor.org/rfc/rfc6962#section-2.1). Their inputs are distinct by construction, while security of their outputs still relies on cryptographic assumptions. BLAKE3's internal compression flags do not tag the application's scripts and tree nodes automatically. Duplicate-leaf ambiguity and leaf/interior ambiguity are separate concerns; the old draft conflated them. Adding a second leaf normally changes a root even when the first leaf's encoding is unchanged.

## What belongs to the daemon

Memory layout, RAM trie representation, RocksDB/LevelDB selection, write-behind, mempool indexes, block-template algorithms, RPCs and transport may evolve if they preserve accepted blocks and required state. The authenticated-state root algorithm is consensus even when its physical storage is replaceable. Snapshot discovery/streaming can evolve; snapshot trust cannot be inferred from transport success.

A matching state root detects a mismatch; it does not reconstruct lost state. Crash recovery needs a durable atomic boundary linking block index, coins, undo and monetary state, plus a replay policy. Likewise, fixed-width fields do not automatically align a packed wire record. Two-minute spacing does not eliminate stale blocks.

Two classic Bitcoin protocol hazards—quadratic $O(N^2)$ signature hashing and parent-transaction / oversized-output OOMs—are eliminated by consensus construction rather than left to ad-hoc daemon workarounds:
- **$O(1)$ per-invocation sighash preimages and Merkleized `TxID`/`TxHash` (`00`, `01`, `02`):** In [P01](decisions/encoding-and-signatures.md), `TxID` and `TxHash` hash a fixed 112-byte preimage (`ChainID || TxHeaderCore || InputsRoot/FullInputsRoot || OutputsRoot`) over P02's bottom-up indexed binary Merkle trees (`IndexedTreeRoot`), mode `00` hashes `TxID` and `CoinsRoot`, and partial modes `01` and `02` hash `OwnInputHash(i)` and `OutputsRoot` / `OutputLeaf(i)`, all computed in strictly linear $O(\text{tx bytes} + \text{resolved coin bytes})$ time. Every `CHECKSIG` (`0xac`) or `SIGHASH` (`0xec`) call in any mode hashes a fixed-size preimage of 138, 150, or 178 bytes ($\le 3$ BLAKE3 64-byte blocks) in $O(1)$ time, even when an input executes multiple branches or checks multiple partial-mode signatures.
- **Bounded `Coin` memory and zero parent-transaction loading (`MAX_OUTPUT_BRANCHES = 16`, `MAX_OUTPUT_PATHS = 16`):** Input resolution fetches only the compact `Coin` record (`Outpoint || Bytes(Output) || creation_height || creation_parent_mtp || coinbase`), never the parent transaction. Because scripts live in witnesses and contract state/data commitments live in `branches` (either as a data leaf in the executing branch tree, as a dedicated unexecuted data branch, or on a pruneable `IS_BURN` `0x02`/`0x03` output that never enters `UtxoRoot`), an `Output` carries only 32-byte `branch_root`s and path indices. Consensus caps every output at `MAX_OUTPUT_BRANCHES = 16` and `MAX_OUTPUT_PATHS = 16` ([P01](decisions/encoding-and-signatures.md), [P05](decisions/resources-and-parameters.md)), bounding every serialized `Output` to $\le 812\text{ bytes}$ (45B native / 77B token for single-branch spendable outputs; 43B for a 1-word native burn output) and every `Coin` to $\le 867\text{ bytes}$. Resolving 256 or 1,000 inputs from the largest transactions in history requires $< 225\text{ KB}$ or $< 870\text{ KB}$ of `Coin` memory, and each path is a subset of `0..15` that fits in a single `uint16_t` bitmask (`uint16_t paths[16]`, 32 bytes per coin in RAM), making `UTXOREQUIRESBRANCH`, `OUTPUTREQUIRESBRANCH`, `OUTPUTEXCLUSIVEBRANCH`, and `OUTPUTCONTINUESBRANCH` pure $O(1)$ bitmask operations.

The scope of post-genesis improvements must be reviewed. New wallet languages and optimized validation can preserve semantics. Different hashes, changed resource ceilings, transaction versions or monetary parameters change consensus unless their behavior was already completely defined at genesis. New operations fit without a hard fork only through P03's named extension points, whose assignment can narrow validity but never widen it. No advisory voting layer can authorize anything beyond that; such a change is a hard fork, which the design aims to make unnecessary.

## Rejected opcodes and consensus features (and how to build those contracts instead)

Several recurring requests—block-header introspection opcodes, in-script global UTXO proofs, read-only reference inputs, witness-inclusive `OP_TXHASH`, and protocol-level subsidy faucets—are deliberately excluded from Lotus v2. Recording why they are rejected and how to express their target applications idiomatically prevents future specs or contract authors from reintroducing consensus hazards when standard covenant patterns already solve the underlying problems.

### 1. `OP_BLOCKHEIGHT`, `OP_BLOCKTIME`, `OP_BLOCKHASH`, and block-dependent transactions

- **Why rejected:** Allowing scripts to read the candidate block's height, timestamp, or hash—or adding transaction expiry bounds (`max_block_height` / `max_mtp`)—violates monotone contextual validity ([C22a](consensus.md)): a transaction that is valid in the mempool at height $h$ can become invalid at height $h+1$ even though none of its inputs were spent. That breaks mempool and block-template invariance, opens unpaid mempool eviction and griefing vectors (an attacker broadcasts high-fee transactions engineered to expire or flip a script branch on the next block, forcing nodes to validate and then drop them for free), makes script execution sensitive to benign single-block reorgs, and invites miners to manipulate block timestamps to alter contract execution paths.
- **How to build those contracts instead in Lotus v2:**
  - **Standing on-chain limit orders (with full and partial fills):** Lock the offered asset in a covenant output. A full fill spends the order coin and verifies that a designated output pays the maker's branch exclusively (`OUTPUTEXCLUSIVEBRANCH` `0xcb`), asset (`OUTPUTTOKENID` `0xcc`), and required amount (`OUTPUTVALUE` `0xca`). A partial fill verifies that the maker receives at least `fill_qty * limit_price` (using checked 128-bit arithmetic so rounding favors the maker) and that the remaining `order_qty - fill_qty` is returned to a continuation output carrying the exact same covenant via `OUTPUTCONTINUESBRANCH` (`0xcf`). A separate cancel path or leaf lets the maker reclaim the coin at any time.
  - **Dutch auctions and linear vesting (time-dependent price or unlock curves):** A transaction's `lock` field—inspected in script via `TXLOCKTIME` (`0xc5`) and `TXLOCKKIND` (`0xe0`)—commits a deterministic lower bound (`height >= lock_value` for kind `01`, or `MTP(parent) >= lock_value` for kind `02`) that satisfies `C22a` unconditionally: once valid at height/MTP $t$, that transaction remains valid at all later heights/MTPs.
    - In a **Dutch auction** whose price decays over time, the script verifies `TXLOCKKIND == expected_kind`, reads `t = TXLOCKTIME`, computes `price(t) = max(floor_price, start_price - decay_rate * max(0, t - start_time))`, and checks that the maker payout output receives `>= price(t)`. Because a higher `t` yields a lower price for the buyer while consensus rejects any transaction whose `t` exceeds the current block height or parent MTP, a rational taker always sets `lock` to the exact current height or parent MTP. The contract achieves a live descending price schedule with zero block-header opcodes and full monotone validity.
    - In **linear vesting**, the beneficiary sets `lock` to the current height or parent MTP (or sets input `SEQUENCE` inspected via `INPUTSEQUENCE` `0xc8` for relative elapsed time since coin creation), the script computes `vested(t)` from `TXLOCKTIME` (or `INPUTSEQUENCE`), allows withdrawing the newly vested delta, and requires the unvested balance to continue in the vesting covenant via `OUTPUTCONTINUESBRANCH` (`0xcf`) with the updated claimed counter in its data leaf.
  - **Expiring offers and timeouts:** Instead of making a signed transaction invalid after height $H$ in consensus, encode expiry as a competing spend path on the offered coin. Before $H$, the counterparty can execute the fill leaf; at or after $H$, a refund/sweep leaf gated by `CHECKLOCKTIMEVERIFY` (`0xb1`) or `CHECKSEQUENCEVERIFY` (`0xb2`) allows the maker (or a designated keeper) to spend and reclaim the coin. Spending the coin permanently revokes the offer under standard UTXO consumption (`C13`) without ever violating `C22a`.

### 2. `OP_UTXOPROOFVERIFY` (in-script global UTXO state proofs)

- **Why rejected:** Verifying membership or absence against the global header `UtxoRoot` inside VM execution introduces severe concurrency and time-of-check/time-of-use (TOCTOU) hazards. Any unrelated transaction in the network that creates or spends a coin changes `UtxoRoot`, so a transaction carrying a proof against a specific `UtxoRoot` would either fail as soon as the chain advances one block or require VM access to historical header roots—reintroducing block-dependent script validity (`C22a` failure) and allowing a third party to invalidate an unconfirmed transaction without spending any of its inputs.
- **How to build those contracts instead in Lotus v2:**
  - **Off-chain verification, RPCs, snapshots, and stateless relay (`ProvenTx`):** The compact single-leaf-collapsed `UtxoRoot` and its canonical membership/absence proofs in [P02](decisions/commitments-and-state.md) are designed strictly for RPC queries, snapshot verification, and optional transport-layer `ProvenTx` input-proof relay packages—never as a script opcode.
  - **Shared on-chain state (oracles, AMM pools, registries):** Represent shared contract state as a coin that is consumed and recreated in the same transaction (`C13`), using `OUTPUTCONTINUESBRANCH` (`0xcf`) or `OUTPUTEXCLUSIVEBRANCH` (`0xcb`) to enforce the state transition on the successor output. Multiple users interacting with the same pool or oracle are sequenced by spending the continuing coin in chained transactions or keeper-aggregated batches.
  - **Large key-value maps, sets, and parent-transaction proofs inside a contract:** Rather than querying the global UTXO tree from script, a contract maintains its own authenticated collection root in `branches` (either inside its branch tree via P02's data-leaf convention or in a dedicated unexecuted data branch read via `UTXOBRANCH` `0xd5`) and verifies membership, non-membership, or leaf updates directly in script using `MERKLEROOT_SORTED` (`0xee`, `hash_alg in 0..3`, for unordered/sorted-pair trees) or `MERKLEROOT_INDEXED` (`0xef`, `hash_alg in 0..3`, for key-bit-indexed sparse or dense binary trees, including `hash_alg = 0` for P02's `IndexedTreeRoot` and `hash_alg = 3` for `HASH256` trees), then commits the updated collection root to its continuation output with `OUTPUTCONTINUESBRANCH` (`0xcf`) or `OUTPUTBRANCH` (`0xd6`).

### 3. Read-only reference inputs (`D06`)

- **Why rejected:** Read-only inputs allow Transaction B to depend on Coin X remaining unspent without consuming Coin X. If Transaction A later spends Coin X, Transaction B becomes invalid even though their consumed input sets are disjoint, complicating mempool conflict resolution, fee-bumping/eviction accounting, and parallel validation ([C13](consensus.md), [D06](decisions.md)).
- **How to build those contracts instead in Lotus v2:**
  - **Signed oracle or configuration data:** Have the authority sign the statement (`epoch || payload`) off-chain and verify it directly in the consumer's script with `CHECKDATASIG` (`0xba`) or `CHECKDATASIGVERIFY` (`0xbb` is unassigned; `0xba` followed by `VERIFY` `0x69`). Zero on-chain oracle UTXO contention occurs regardless of how many transactions read the price or configuration in the same block.
  - **On-chain shared state:** Spend and recreate the state coin in the same transaction (`C13`) using `OUTPUTCONTINUESBRANCH` (`0xcf`), which makes the dependency explicit in the UTXO graph and lets standard mempool chaining order concurrent readers/writers.

### 4. In-script `OP_TXHASH` (witness-inclusive transaction hash)

- **Why rejected:** `TxHash` (`H_txhash(ChainID || TxHeaderCore || FullInputsRoot || OutputsRoot)`) commits to the complete transaction including every input's witness argument vector `Vec(Bytes(arg))`. Exposing `TxHash` as an opcode inside script would create a circular dependency whenever a script inspects `TxHash` and compares or signs against an argument supplied in `Vec(Bytes(arg))`.
- **How to build those contracts instead in Lotus v2:**
  - Use `TXID` (`0xc0`) or `OUTPOINTTXID` (`0xc7`), which commit to `ChainID || TxHeaderCore || InputsRoot || OutputsRoot`—where `InputsRoot` binds every input's outpoint/sequence/flags, selected path and `CoreWitness` (`Bytes(script) || Vec(h32 sibling)`), and `OutputsRoot` binds every output. Because `InputsRoot` already binds the exact executed scripts and Merkle proofs while excluding `Vec(Bytes(arg))`, contracts can bind cross-input claims, unique nonces, or covenant continuation IDs to `TXID` (`0xc0`) without circularity, and can prove any individual input `InputCore(m)` or output `Output[k]` of a parent transaction (`OUTPOINTTXID` `0xc7`) in $O(\log N)$ space using `MERKLEROOT_INDEXED` (`0xef`, `hash_alg = 0`) and `<"Lotus/v2/txid\x00"> SWAP CAT BLAKE3` (`0xbf`). When a method needs to authenticate a witness argument, it either verifies a signature over it (`CHECKSIG` `0xac` / `CHECKDATASIG` `0xba`) or requires its effect to appear in committed output fields inspected via output opcodes (`0xca`–`0xcf`, `0xd6`, `0xd8`, `0xd9`, `0xde`, `0xe3`, `0xe6`, `0xe8`).

### 5. Protocol-level onboarding faucet and 50-50 subsidy splits (`D11`)

- **Why rejected:** Enshrining an onboarding faucet or a 50-50 block-subsidy diversion in consensus (`D11`, rejected) requires consensus-tracked treasury/faucet state in `StateRoot`, special coinbase output routing, or bespoke anti-sybil distribution rules at the base layer. Lotus v1 explicitly removed the Infrastructure Funding Plan (`28-ifp-removal.patch`), and base-layer subsidy policy in Lotus v2 stays clean: miners may claim up to `100%` of the block subsidy $R$ plus `floor((F - T) / 2)` of remaining fees after the mandatory token-output fee burn $T$, with the other half of remaining fees burned (`C16`, `C17`).
- **How to build those contracts instead in Lotus v2:**
  - **Voluntary user-space faucet covenants:** Any donor, application, or miner can lock native XPI or tokens into an unprivileged covenant output whose spend script enforces a per-claim drip limit (`OUTPUTVALUE` `0xca`), rate-limits claims across blocks or MTP intervals via `CHECKSEQUENCEVERIFY` (`0xb2`), requires an anti-bot credential or voucher via `CHECKDATASIG` (`0xba`) (or a hash-preimage puzzle via `BLAKE3` `0xbf`), and returns the remaining balance to the exact same covenant via `OUTPUTCONTINUESBRANCH` (`0xcf`) or `OUTPUTEXCLUSIVEBRANCH` (`0xcb`). This achieves programmable onboarding and recurring grants completely in user space with zero consensus special cases.
