Decisions that can proceed now

“CANDIDATE” means an implementable proposed rule, not approved mainnet consensus or independent verification. The six packets provide precise proposed encodings, integer algorithms and tradeoffs. Implementation entry contracts identify work that can start without guessing production constants. No decision is FROZEN.

P01–P06 can now drive a complete parameterized reference implementation and local vectors, including the 134-byte pure BLAKE3 recursive header (P04), the canonical 56-byte MonetaryState record (P02), the additive bootstrap recurrence + absolute tail issuance $S_n = B_n + T_n$ (P06), and the unified cu parabolic transaction cost and block fee-burn floor (P05). Shift parameters ($k_{\text{boot}}, S_{\text{tx\_knee}}, w, E_{\min}, S_{\text{linear}}, S_{\text{quad}}$), primitive cu weights, and initial monetary constants ($R_0, T_0, T_{\min}, T_{\max}, W_{-1}, E_0$) remain to be confirmed by simulation and hardware benchmarking before genesis freeze. The monetary analysis must choose an objective before optimizing it: expected discounted miner profit, reward per hash, or total network issuance are different quantities. Evaluate fixed-share and mobile miners, changing share, discovery randomness, allowed timestamp histories, transaction fees, clipping, and rounding. A reward formula involving difficulty is not by itself a proof of timestamp honesty. Record any impossibility result or tradeoff rather than claiming a “sweet spot” without a feasible-history model.

Closure record

For each closed decision record: accepted rule and rejected alternatives; maintainer acceptance; spec revision and requirement IDs; exact parameter/vector digests; independent reviewer; remaining limitations; affected patches and examples. Reopening before genesis invalidates dependent vectors and measurements. After genesis, a changed validity rule is not an ordinary implementation update.

D10 formula adoption (2026-10-15): maintainer authorizes the absolute genesis-anchored tail F(work)=clip(isqrt(T_g²*work//W_g)), retaining one-block lag. Immutable anchors and formula version 1 are bound to profile identity; 56-byte state caches are checked. Constant calibration and economic/runtime acceptance remain open.

Typed addresses — maintainer direction, 2026-10-19

Address specification: type 0 carries an explicit MAST root; type 1 is the candidate BLAKE3(x-only secp256k1 public key) program defined there, with a full 32-byte payload and exact 37-byte native VM template. IDs 2–30 remain reserved and 31 is an extension escape whose encoding is still open. Message signing records the maintainer's compact recoverable ECDSA choice, chain-bound Lotus digest, canonical keyhash binding, eCash compatibility and validation gates. Native transaction signatures remain BIP340. Both address and application-proof choices remain provisional through testnet. Type-1/message implementation is a separate candidate; native wallet receive/spend is a distinct dependency, not implied by codec acceptance. Keep this decision and daemon documentation synchronized.

Partially signed transactions — maintainer direction, 2026-10-20

The Lotus PSBT profile retains BIP174's container and key/value map conventions wherever possible. Native v7 transaction structure does not fit Bitcoin PSBTv2 output semantics, so the candidate uses the distinct profile version 0x4c560001 rather than claiming Bitcoin PSBTv2 compatibility. The initial profile covers ordinary native spends; specialized invocation construction is outside that initial scope. Its executable profile checks and conformance vectors bind the proposed encoding. The profile remains provisional through testnet. Specification checks do not imply completed daemon implementation or interoperability; implementation must preserve the specified transaction identity and witness separation and provide matching signing/finalization tests.

Forward catch-up and optional history — maintainer direction, 2026-10-20

“Possibly never reaching genesis is reasonable, but never being able to catch up is not.” N06a requires authenticated bootstrap followed by forward validation to reach and follow the moving live tip under explicitly supported workload, hardware, storage, network and data-availability assumptions, with measured positive catch-up headroom. Genesis backfill is optional, bounded and lower priority; it may remain incomplete indefinitely without starving forward validation. Restart/downtime recovery must preserve separate durable active and historical progress. Historical archive retrieval is not reverse-peel state verification, and neither permits concurrent rollback of the active forward state.

The optional archive direction is filesystem-first, separate from active validation state; no S3 commitment is selected. Trust, finality, consensus and monetary rules are unchanged. Closure requires moving-tip catch-up measurements, bounded historical backlog/outage tests, same-node forward/historical isolation and restart/downtime evidence described in N06a. This direction remains provisional through testnet; it does not assert these operational properties are already implemented or tested.

SHA256D mining envelope — discussion requested, 2026-10-20

The maintainer requested an optional 80-byte Bitcoin-shaped mining-envelope alternative, with BLAKE3-committed canonical extension fields and SHA256D over exactly the 80-byte envelope. This is an unselected alternative to D12/P04, not an additional accepted block format; the current 134-byte recursive BLAKE3 header/work/BlockID scheme is unchanged. The proposed 80-bit search space combines 32 nonce, 32 former-time-position and 16 rolling-version bits; it is not a claim about S9 hardware counters. Actual time remains committed in the extension. BlockID, rolling allocation, controller/Stratum adaptation and any transition require separate selection. Height-driven upgrade preference is recorded for discussion without adopting new activation rules or assigning miner signaling control. The document records ASIC reuse/security/economic tradeoffs and independent-vector, real-device, controller, pool and full-validation gates. No compatibility, performance, exchange-listing or production-readiness result is claimed.

Mining-envelope clarification (2026-10-20): the discussed direct-commitment architecture has the node supply completed work headers and the fixed extension commitment. A controller/host adapter partitions permitted header fields and returns solutions; miners need not generate coinbase/Merklix/extension data. Stratum session/target/share mechanisms may be reused with adapted job construction. A Bitcoin coinbase/Merkle wrapper is optional, not a prerequisite for the direct design. Expanded search space reduces node-template turnover only when the actual controller can use it; chip nonce exhaustion still requires appropriate chip assignments. A shared pool manager with native browser and Stratum adapters is a proposal, not existing ASIC support. P04 and the open selection/measurement gates remain unchanged.

Historical root verification — provisional maintainer direction, 2026-10-20

N06a historical verification policy records the proposed default: authenticated backwards root-transition checks, with full historical transaction/script/signature execution on a separate opt-in track. Neither full historical replay nor reaching genesis is required for catch-up. Every newly connected forward block still requires the existing full consensus validation. This is a pre-testnet/provisional synchronization policy, not a consensus relaxation or an implemented proof protocol.

Archive commitment checks, block-derived root-transition checks and full historical execution carry distinct assurance and durable provenance. Arbitrary root-changing updates do not prove transaction authorization or monetary validity; full StateRoot components, spent/creation proofs, block binding and expiry-sweep completeness need a precise reviewed proof contract. Authenticated snapshot/header/PoW and any required finalization anchors remain explicit. Peer-count majorities are not trust proofs; Avalanche reliance is conditional on its defined quorum/bootstrap evidence, not a generic historical-validity claim. Root checking must never mark scripts executed. Proof encoding, completeness, status reporting, invalid-history handling and independent tests remain open; no new trust or activation mechanism is adopted here.

Prunable burn data and script receipts — open questions, 2026-10-20

The maintainer requested the burn-data appendix to explore commitment-preserving pruning and large paid publication data. Existing native Merkleized output identities can retain an opaque leaf hash, but that hash alone does not authenticate disclosed burn classification or accounting fields. A separately committed small burn descriptor plus payload commitment is a hypothesis requiring its own canonical format, streaming validation, charged resource model and retention/retrieval evidence. It is not a selected rule or a request to rewrite block files.

Descriptor-only pruning, script-readable historical receipts and consumable receipts/nullifiers are separate choices. Burned value remains unspendable; references must not resurrect it or bypass conservation. Read-only inputs are still forbidden. Any receipt capability requires explicit chain anchoring, reorg/replay/duplicate-claim handling and cost/availability analysis, with existing branch/HAS_STATE contract commitments considered first. The appendix flags the older P01 state-field description versus implementation discrepancy without modifying either rule. Backwards transition verification still needs its authenticated coin/provenance and full-state evidence. No payload availability guarantee, new wire format, consensus activation, fee parameter or burn distribution is selected.
