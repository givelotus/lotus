🎯 Why: Document the engineering tradeoffs that keep Lotus V2 parallelizable and Hard-Fork-Free.

In Practice: Why Lotus avoids fragile design shortcuts from older blockchains and how developers build auctions, timers, and shared state safely.

Under the Hood: Formal justification for excluding OP_BLOCKHEIGHT, OP_UTXOPROOFVERIFY, and read-only inputs to preserve C22a monotone mempool validity.

Design rationale and claim boundaries

Status: explanatory, not normative. Consensus owns rules; decisions owns alternatives.

Authorization and assets

Alternative paths express OR; the required branches within one path express AND. Branch MASTs select methods within a role. Asset accounting is a separate obligation: conserving token units does not prove the owner approved, and owner approval does not authorize additional supply. Program-derived token identity supports continuing mint authority and is the chosen model (D05): a token ID is the root of its mint scripts. The earlier outpoint-derived design is superseded; which of its historical code is reusable remains to be settled.

A branch MAST needs unordered script membership (BranchNode(a, b) = H_branch(01 || min(a, b) || max(a, b))), whereas both the block's non-coinbase transaction tree (Subtree A in tx_root) and the global UTXO state map (UtxoRoot in state_root) require consistent key-prefix range partitioning (256-bit single-leaf-collapsed Merklix trees keyed by TxID and txid || vout respectively) so that mempool acceptance, transaction subtree hashing, and UTXO validation can be sharded horizontally across CPU cores and processes without cross-shard array-index synchronization (Sharding Bitcoin Cash, 2018; see P02). Combining the coinbase leaf with Subtree A at the top of tx_root (H_txroot(03 || CoinbaseLeaf || SubtreeA)) and pipelining coinbase UTXO insertion into a subsequent block allow the block coordinator to finalize both tx_root and state_root in $O(1)$ after aggregating shard subtree roots and fee sums, while preserving txid-prefix co-location between dbi_coins (Vout lookup) and dbi_smt_nodes (path-based Merklix branch storage).

Leaf/interior tags follow the principle illustrated in RFC 6962 §2.1. Their inputs are distinct by construction, while security of their outputs still relies on cryptographic assumptions. BLAKE3's internal compression flags do not tag the application's scripts and tree nodes automatically. Duplicate-leaf ambiguity and leaf/interior ambiguity are separate concerns; the old draft conflated them. Adding a second leaf normally changes a root even when the first leaf's encoding is unchanged.

What belongs to the daemon

Memory layout, RAM trie representation, RocksDB/LevelDB selection, write-behind, mempool indexes, block-template algorithms, RPCs and transport may evolve if they preserve accepted blocks and required state. The authenticated-state root algorithm is consensus even when its physical storage is replaceable. Snapshot discovery/streaming can evolve; snapshot trust cannot be inferred from transport success.

A matching state root detects a mismatch; it does not reconstruct lost state. Crash recovery needs a durable atomic boundary linking block index, coins, undo and monetary state, plus a replay policy. Likewise, fixed-width fields do not automatically align a packed wire record. Two-minute spacing does not eliminate stale blocks.

Two classic Bitcoin protocol hazards—quadratic $O(N^2)$ signature hashing and parent-transaction / oversized-output OOMs—are eliminated by consensus construction rather than left to ad-hoc daemon workarounds:

  • $O(1)$ per-invocation sighash preimages and Merkleized TxID/TxHash (00, 01, 02): In P01, TxID and TxHash hash a fixed 112-byte preimage (ChainID || TxHeaderCore || InputsRoot/FullInputsRoot || OutputsRoot) over P02's bottom-up indexed binary Merkle trees (IndexedTreeRoot), mode 00 hashes TxID and CoinsRoot, and partial modes 01 and 02 hash OwnInputHash(i) and OutputsRoot / OutputLeaf(i), all computed in strictly linear $O(\text{tx bytes} + \text{resolved coin bytes})$ time. Every CHECKSIG or SIGHASH call in any mode hashes a fixed-size preimage of 138, 150, or 178 bytes ($\le 4$ BLAKE3 64-byte blocks including the domain prefix) in $O(1)$ time, even when an input executes multiple branches or checks multiple partial-mode signatures.
  • Bounded Coin memory and zero parent-transaction loading (MAX_OUTPUT_BRANCHES = 16, MAX_OUTPUT_PATHS = 16): Input resolution fetches only the compact Coin record (Outpoint || Bytes(Output) || creation_height || creation_parent_mtp || coinbase), never the parent transaction. Because scripts live in witnesses and contract state/data commitments live in branches (either as a data leaf in the executing branch tree, as a dedicated unexecuted data branch, or on a pruneable IS_BURN (0x02/0x03) output that never enters UtxoRoot), an Output carries only 32-byte branch_roots and path indices. Consensus caps every output at MAX_OUTPUT_BRANCHES = 16 and MAX_OUTPUT_PATHS = 16 (P01, P05), bounding every serialized Output to $\le 812\text{ bytes}$ (45B native / 77B token for single-branch spendable outputs; 43B for a 1-word native burn output) and every Coin to $\le 868\text{ bytes}$. Resolving 256 or 1,000 inputs from the largest transactions in history requires $< 225\text{ KB}$ or $< 870\text{ KB}$ of Coin memory, and each path is a subset of 0..15 that fits in a single uint16_t bitmask (uint16_t paths[16], 32 bytes per coin in RAM), making UTXOREQUIRESBRANCH, OUTPUTREQUIRESBRANCH, OUTPUTEXCLUSIVEBRANCH, and OUTPUTCONTINUESBRANCH pure $O(1)$ bitmask operations.

The scope of post-genesis improvements must be reviewed. New wallet languages and optimized validation can preserve semantics. Different hashes, changed resource ceilings, transaction versions or monetary parameters change consensus unless their behavior was already completely defined at genesis. New operations fit without a hard fork only through P03's named extension points, whose assignment can narrow validity but never widen it. No advisory voting layer can authorize anything beyond that; such a change is a hard fork, which the design aims to make unnecessary.

Monetary research

Research sources are the papers Adaptive PoW Monetary Policy Without Oracles: A Constructive Mechanism for Pseudo-Stability via Work-Coupled Tail Emission and Burn (main.tex SHA-256 60f845adc6b3645722e97cad3b7f8e315cc557d4ab4b27f851eba0770ef4dacd) and CashWeb: A Cryptocurrency-Integrated Protocol for Federated Anti-Spam Messaging and Publish-Subscribe Systems (main.tex SHA-256 29b71351f2a6558d721b90cc44fafb59bca4c19a7d3db5b928112d4cb08a79e4). The hashes identify the exact paper revisions read; they are more precise than a repository commit when a paper has local edits.

The paper's height-decaying bootstrap plus genesis-anchored absolute work-responsive tail is realized in P06 as a single smooth additive block subsidy $S_n = B_n + T_n$ active from Block 1, backed by the canonical MonetaryState record (56 bytes bootstrap_reserve:u64 || tail_subsidy:u64 || prev_work:u256 || ema_block_cost:u64 at Genesis $h = 0$, and 88 bytes with 32-byte history_root appended at $h \ge 1$ in P02):

  • Denomination and candidate genesis scale (1 XPI = 10^6 atoms): Consensus amounts are integer atoms with 6 decimal places ($\text{1 XPI} = 10^6\text{ atoms}$). Standard wallet UIs display 2 decimal places (1.00 XPI, like dollars and cents) and hide the lower 4 sub-cent decimal places (0.00_0000) by default so ordinary transaction fees ($\sim 200\text{--}2{,}000\text{ atoms} = 0.0002\text{--}0.0020\text{ XPI}$) sit inside the hidden sub-cent precision while providing $10{,}000$ integer ticks per 0.01 XPI for P05's parabolic fee-burn accounting. With candidate initial bootstrap $B_0 = 250{,}000\text{ XPI/block}$ ($2.5 \times 10^{11}\text{ atoms}$), total bootstrap reserve $R_0 = 2^{20} \cdot B_0 = 262{,}144{,}000{,}000\text{ XPI}$ ($\approx 2.62144 \times 10^{17}\text{ atoms}$), and initial tail $T_0 = 250{,}000\text{ XPI/block}$ ($2.5 \times 10^{11}\text{ atoms}$), Block 1 has gross entitlement $S_0 = 500{,}000\text{ XPI}$ before its resource deduction. A finite bootstrap reserve gives no aggregate supply cap while the adaptive tail continues; u64 limits individual amounts/state fields, not cumulative issuance.
  • Telescoping bootstrap reserve ($R_n$): $B_n = \max(1, R_n \gg 20)$ when $R_n > 0$ (and $0$ when $R_n = 0$), $R_{n+1} = R_n - B_n$, giving an exponential mean lifetime of $2^{20} = 1{,}048{,}576$ two-minute blocks ($\approx 4.00\text{ years}$, matching Bitcoin's $210{,}000$ ten-minute blocks $\approx 4.00\text{ years}$ halving interval within $0.3\%$) and exact atom conservation $\sum_{n=0}^{\infty} B_n = R_0$ with zero division and zero floating-point arithmetic.
  • Absolute work-responsive tail ($T_n$): $T_{n+1} = \min(T_{\max}, \max(T_{\min}, \text{isqrt}(\lfloor T_g^2 W_n / W_g \rfloor)))$, which is homogeneous of degree 1 in currency units and degree 0 in work units.
  • Steady-state supply convergence under tail emission and coin loss/burn: As shown by Peter Todd (Surprisingly, Tail Emission Is Not Inflationary, 2022; see also Carlsten et al., On the Instability of Bitcoin Without the Block Reward, 2016, on why pure fee-only PoW block generation is unstable), even a constant tail emission $k$ with proportional independent coin loss $\lambda N(t)$ obeys $\frac{dN(t)}{dt} = k - \lambda N(t)$ and converges to a finite steady-state active supply $N(\infty) = \frac{k}{\lambda}$ rather than unbounded inflation: $$N(t) = \frac{k}{\lambda} + \left(N_0 - \frac{k}{\lambda}\right)e^{-\lambda t} \xrightarrow{t \to \infty} \frac{k}{\lambda}$$ Lotus v2 strengthens both sides of this equilibrium: $T_n$ scales the tail emission with authenticated PoW work rather than fixing an arbitrary constant $k$, while protocol fee burns, parabolic resource-burn floors, C14a token-output burns, and explicit IS_BURN outputs provide direct on-chain supply sinks on top of natural custodial/key loss $\lambda N(t)$.

A miner's immediate reward and its influence on future difficulty need not accrue to the same party. Evaluate complete feasible timestamp histories under the exact DAA, not arbitrary independent choices of future difficulty. Local stability under a simplified hashrate model does not prove truthful timestamps or resistance to mobile miners. D10 separates the deterministic integer recurrences in P06 from economic simulation of the final constants.

For application demand, write $A_n$ for the actual external-currency budget spent on native burns and $P_n>0$ for external currency per XPI. The resulting burn is approximately $A_n/P_n$ XPI, with atom rounding and transaction costs. A price decline raises coin-denominated burns only if budgets and participation persist; if attention demand collapses, $A_n$ can fall faster than $P_n$. The papers' burn-to-speak loop is therefore a conditional economic hypothesis, not an automatic price floor. At the candidate $250{,}000$ XPI tail and 120-second target, a steady 365-day year would issue $65.7$ billion tail XPI. At a reference price of $1/XPI, replacing that tail with voluntary burns alone after bootstrap would require about $65.7$ billion/year of actual external spending. That figure assumes the tail stays fixed and ignores other burns/underclaims; it is neither a launch forecast, peg, nor supply guarantee.

The monetary paper's aggregate expectation writes a gross fee term before subtracting its fee burn. For V2 accounting, C16 is normative: $\Delta M_n=S_n-B-U-\text{Burn\_explicit}$. The fee share paid to miners and optional tips transfer existing coins; they do not create issuance or count as burns. $B$ includes mandatory C14a token-output burn and the burned share of remaining native fees; a native IS_BURN output counts once in $\text{Burn\_explicit}$, separately from fees. CashWeb's proof-of-payment construction links an unspendable output to an off-chain message; V2 applications can verify a native IS_BURN receipt for this purpose without adding a new consensus policy or counting its burn twice.

The monetary paper's Lyapunov theorem establishes local convergence only in its linearized model with persistent fiat-budget burns, immediate hashrate response, an assumed price response and inactive clipping; it does not establish these premises in a deployed V2 market or fix a price level. Genesis calibration needs joint simulations of adoption and burn-budget persistence, price elasticity, mining lag, energy and hardware shocks, clipping and integer rounding, correlated demand/price/work shocks, and the miner security payout remaining after fee burns and required underclaims. Include cold-start and demand-collapse paths, then report the resulting supply and security ranges as scenario outcomes.

Rejected opcodes and consensus features (and how to build those contracts instead)

Several recurring requests—block-header introspection opcodes, in-script global UTXO proofs, read-only reference inputs, witness-inclusive OP_TXHASH, protocol-level subsidy faucets, memory-hard PoW algorithms, and hard byte-cap walls—are deliberately excluded from Lotus v2. Recording why they are rejected and how to express their target goals idiomatically prevents future specs or contract authors from reintroducing consensus hazards when cleaner mechanisms already solve the underlying problems.

1. OP_BLOCKHEIGHT, OP_BLOCKTIME, OP_BLOCKHASH, and block-dependent transactions

  • Why rejected: Allowing scripts to read the candidate block's height, timestamp, or hash—or adding transaction expiry bounds (max_block_height / max_mtp)—violates monotone contextual validity (C22a): a transaction that is valid in the mempool at height $h$ can become invalid at height $h+1$ even though none of its inputs were spent. That breaks mempool and block-template invariance, opens unpaid mempool eviction and griefing vectors (an attacker broadcasts high-fee transactions engineered to expire or flip a script branch on the next block, forcing nodes to validate and then drop them for free), makes script execution sensitive to benign single-block reorgs, and invites miners to manipulate block timestamps to alter contract execution paths.
  • How to build those contracts instead in Lotus v2:
  • Standing on-chain limit orders (with full and partial fills): Lock the offered asset in a covenant output. A full fill spends the order coin and verifies that a designated output pays the maker's branch exclusively (OUTPUTEXCLUSIVEBRANCH), asset (OUTPUTTOKENID), and required amount (OUTPUTVALUE). A partial fill verifies that the maker receives at least fill_qty * limit_price (using checked 128-bit arithmetic so rounding favors the maker) and that the remaining order_qty - fill_qty is returned to a continuation output carrying the exact same covenant via OUTPUTCONTINUESBRANCH. A separate cancel path or leaf lets the maker reclaim the coin at any time.
  • Dutch auctions and linear vesting (time-dependent price or unlock curves): A transaction's lock field—inspected in script via TXLOCKTIME and TXLOCKKIND—commits a deterministic lower bound (height >= lock_value for kind 01, or MTP(parent) >= lock_value for kind 02) that satisfies C22a unconditionally: once valid at height/MTP $t$, that transaction remains valid at all later heights/MTPs.
  • In a Dutch auction whose price decays over time, the script verifies TXLOCKKIND == expected_kind, reads t = TXLOCKTIME, computes price(t) = max(floor_price, start_price - decay_rate * max(0, t - start_time)), and checks that the maker payout output receives >= price(t). Because a higher t yields a lower price for the buyer while consensus rejects any transaction whose t exceeds the current block height or parent MTP, a rational taker always sets lock to the exact current height or parent MTP. The contract achieves a live descending price schedule with zero block-header opcodes and full monotone validity.
  • In linear vesting, the beneficiary sets lock to the current height or parent MTP (or sets input SEQUENCE inspected via INPUTSEQUENCENUMBER for relative elapsed time since coin creation), the script computes vested(t) from TXLOCKTIME (or INPUTSEQUENCENUMBER), allows withdrawing the newly vested delta, and requires the unvested balance to continue in the vesting covenant via OUTPUTCONTINUESBRANCH with the updated claimed counter in its data leaf.
  • Expiring offers and timeouts: Instead of making a signed transaction invalid after height $H$ in consensus, encode expiry as a competing spend path on the offered coin. Before $H$, the counterparty can execute the fill leaf; at or after $H$, a refund/sweep leaf gated by CHECKLOCKTIMEVERIFY or CHECKSEQUENCEVERIFY allows the maker (or a designated keeper) to spend and reclaim the coin. Spending the coin permanently revokes the offer under standard UTXO consumption (C13) without ever violating C22a.

2. OP_UTXOPROOFVERIFY (in-script global UTXO state proofs)

  • Why rejected: Verifying membership or absence against the global header UtxoRoot inside VM execution introduces severe concurrency and time-of-check/time-of-use (TOCTOU) hazards. Any unrelated transaction in the network that creates or spends a coin changes UtxoRoot, so a transaction carrying a proof against a specific UtxoRoot would either fail as soon as the chain advances one block or require VM access to historical header roots—reintroducing block-dependent script validity (C22a failure) and allowing a third party to invalidate an unconfirmed transaction without spending any of its inputs.
  • How to build those contracts instead in Lotus v2:
  • Off-chain verification, RPCs, snapshots, and stateless relay (ProvenTx): The compact single-leaf-collapsed UtxoRoot and its canonical membership/absence proofs in P02 are designed strictly for RPC queries, snapshot verification, and optional transport-layer ProvenTx input-proof relay packages—never as a script opcode.
  • Shared on-chain state (oracles, AMM pools, registries): Represent shared contract state as a coin that is consumed and recreated in the same transaction (C13), using OUTPUTCONTINUESBRANCH or OUTPUTEXCLUSIVEBRANCH to enforce the state transition on the successor output. Multiple users interacting with the same pool or oracle are sequenced by spending the continuing coin in chained transactions, keeper-aggregated batches, or via Snowstorm's Sticky Conflict-Tiebreak Winner promotion (snowstorm.md §6.3, which guarantees that a contended shared-state UTXO commits at least one winning transition per 100–250 ms pre-consensus epoch without starvation).
  • Large key-value maps, sets, and parent-transaction proofs inside a contract: Rather than querying the global UTXO tree from script, a contract maintains its own authenticated collection root in branches (either inside its branch tree via P02's data-leaf convention or in a dedicated unexecuted data branch read via UTXOBRANCH) and verifies membership, non-membership, or leaf updates directly in script using MERKLEROOT_SORTED (0xc0, hash_alg in 0..3, for unordered/sorted-pair trees) or MERKLEROOT_INDEXED (0xc1, hash_alg in 0..3, for key-bit-indexed sparse or dense binary trees, including hash_alg = 0 for P02's IndexedTreeRoot and hash_alg = 3 for HASH256 trees), then commits the updated collection root to its continuation output with OUTPUTCONTINUESBRANCH or OUTPUTBRANCH.

3. Read-only reference inputs (D06)

  • Why rejected: Read-only inputs allow Transaction B to depend on Coin X remaining unspent without consuming Coin X. If Transaction A later spends Coin X, Transaction B becomes invalid even though their consumed input sets are disjoint, complicating mempool conflict resolution, fee-bumping/eviction accounting, and parallel validation (C13, D06).
  • How to build those contracts instead in Lotus v2:
  • Signed oracle or configuration data: Have the authority sign the statement (epoch || payload) off-chain and verify it directly in the consumer's script with CHECKDATASIG followed by VERIFY. Zero on-chain oracle UTXO contention occurs regardless of how many transactions read the price or configuration in the same block.
  • On-chain shared state: Spend and recreate the state coin in the same transaction (C13) using OUTPUTCONTINUESBRANCH, which makes the dependency explicit in the UTXO graph and lets standard mempool chaining order concurrent readers/writers.

4. In-script OP_TXHASH (witness-inclusive transaction hash)

  • Why rejected: TxHash (H_txhash(ChainID || TxHeaderCore || FullInputsRoot || OutputsRoot)) commits to the complete transaction including every input's witness argument vector Vec(Bytes(arg)). Exposing TxHash as an opcode inside script would create a circular dependency whenever a script inspects TxHash and compares or signs against an argument supplied in Vec(Bytes(arg)).
  • How to build those contracts instead in Lotus v2:
  • Use TXID or OUTPOINTTXID, which commit to ChainID || TxHeaderCore || InputsRoot || OutputsRoot—where InputsRoot binds every input's outpoint/sequence/flags, selected path and CoreWitness (Bytes(script) || Vec(h32 sibling)), and OutputsRoot binds every output. Because InputsRoot already binds the exact executed scripts and Merkle proofs while excluding Vec(Bytes(arg)), contracts can bind cross-input claims, unique nonces, or covenant continuation IDs to TXID without circularity, and can prove any individual input InputCore(m) or output Output[k] of a parent transaction (OUTPOINTTXID) in $O(\log N)$ space using MERKLEROOT_INDEXED (0xc1, hash_alg = 0) and <"Lotus/v2/txid\x00"> SWAP CAT BLAKE3 (0xba). When a method needs to authenticate a witness argument, it either verifies a signature over it (CHECKSIG / CHECKDATASIG) or requires its effect to appear in committed output fields inspected via the output-introspection opcodes.

5. Avalanche-controlled payouts (D11)

Payout coordination (D11) uses Bitcoin ABC's existing Avalanche winner-selection and staking-reward parking machinery. P06 records the exact source behavior and V2 integration boundary. Payouts divide the resource-adjusted coinbase entitlement; they do not increase issuance. Treasury contracts, genesis vesting allocations, controller coins, and mutable treasury state are excluded. Local Avalanche polling state is coordination policy, not a deterministic historical consensus input.

6. Memory-hard and GPU-targeted PoW algorithms (ProgPoW, KawPoW, Ethash, RandomX) (D12)

  • Why rejected: Memory-hard and dynamic-program Proof-of-Work algorithms destroy PoW verification symmetry—the foundational property that work is expensive to find but instantaneous to verify. Requiring multi-megabyte/gigabyte DAGs or scratchpads, thousands of random memory gathers, or dynamic shader compilation to verify a single header slows full-node header synchronization by $10^3\times\text{--}10^5\times$, creates asymmetric header-spam DoS vectors, and prevents cheap SPV, browser, and mobile light-client header verification. Worse, historical evidence across every major "GPU-only" or memory-hard PoW shows that once block rewards grow large enough, secret FPGAs and custom ASICs are built anyway, forcing chains into a perpetual emergency-hardfork treadmill while punishing ordinary validators every day.
  • How Lotus v2 solves this instead (P04):
  • Pure tagged BLAKE3 (H_headerbody, H_headerwork, H_blockid): Lotus v2 uses tagged BLAKE3 for both its 134-byte recursive header commitments and its Proof-of-Work (BlockID), making BLAKE3 the single consensus hash primitive across the entire protocol (headers, PoW, TxID, TxHash, UtxoRoot, StateRoot, and branch MASTs). Because BLAKE3 is pure 32-bit add-rotate-xor (ARX) with no lookup tables, commodity GPUs mine it natively across SIMD lanes at massive throughput, while a CPU verifies a block header in ~50 ns (a single 64-byte final compression block per nonce iteration once BodyHash is fixed).

7. Arbitrary hard byte-cap walls MAX_TX_BYTES and MAX_BLOCK_BYTES (D08)

  • Why rejected: Hard step-function byte ceilings (MAX_TX_BYTES and MAX_BLOCK_BYTES) create artificial cliff edges: legitimate multi-input wallet consolidations fail abruptly at an arbitrary byte count, while blocks below MAX_BLOCK_BYTES can be stuffed at zero marginal protocol cost by a miner mining their own transactions (when miners keep 100% of fees) and blocks at the wall suffer sudden vertical fee spikes.
  • How Lotus v2 solves this instead (P05, C16, C24, C25):
  • Unified Cost Units (cu) and Parabolic Transaction Cost $C_{\text{tx}}$: All wire bytes (1 wire byte = 1 cu), hashes, signatures, state updates, and static VM opcode charges sum into a transaction's linear base cost $L(\text{tx})$, which maps to a parabolic effective cost $C_{\text{tx}} = L(\text{tx}) + ((L(\text{tx}) \cdot L(\text{tx})) \gg S_{\text{tx\_knee}})$ (candidate $S_{\text{tx\_knee}} = 17$, i.e. $131{,}072\text{ cu}$). Normal payments and ~100-input Frank consolidations sit in the flat region of the parabola ($L \ll 2^{17}$), whereas mega-transactions pay a super-additive quadratic surcharge ($(L_1 + L_2)^2 > L_1^2 + L_2^2$), naturally incentivizing wallets to split oversized batches and letting the mempool rank/filter uniformly by $\text{fee} / C_{\text{tx}}$ while keeping structural framing bounds (u16 counts, MAX_OUTPUT_BRANCHES = 16, MAX_ELEMENT_BYTES = 8192, MAX_SCRIPT_BYTES) so parsers never allocate unbounded buffers.
  • Rolling ema_block_cost ($E_n$) and Parabolic Block Burn Floor via C16: Summing $C_{\text{block}} = C_{\text{envelope}} + \sum C_{\text{tx}}$ across all transactions, including coinbase and block-envelope work and maintaining the integer EMA $E_{n+1} = E_n - (E_n \gg 10) + (C_{\text{block}} \gg 10)$ in MonetaryState, consensus requires the block's mandatory 50% burned native fees ($\text{BurnedFees}_n = G_n - \lfloor G_n / 2 \rfloor$) to satisfy $\text{BurnedFees}_n + U \ge ((C_{\text{block}} \cdot \max(E_n, E_{\min})) \gg S_{\text{linear}}) + ((C_{\text{block}} \cdot C_{\text{block}}) \gg S_{\text{quad}})$. Because half of all native fees are permanently burned (C16), not even a miner mining their own transactions can stuff a block for free.

The byte minimum is 1,000 native atoms per 1,000 bytes. Coinbase and block framing pay from reward underclaim; P05 defines the exact payout deduction. Opcode upgrades retain the genesis monetary accounting view for the committed EMA and may impose higher enforcement costs only as additional validity restrictions.

The candidate tail is the absolute genesis-anchored form, selected after an arithmetic review; it supersedes the paper's recurrence. P06 defines F(work)=clip(isqrt(T_g²*work//W_g)) with the same reward lag. Returning to a work level restores its anchored entitlement after rounding or saturation; this does not establish economic stability or fix launch constants. The monetary envelope retains checked redundancy for compatibility with existing commitment encoding.
