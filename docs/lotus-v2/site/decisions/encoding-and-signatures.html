🎯 Why: Eliminate malleability, quadratic sighash bugs, and bloated parent-transaction proofs forever.

In Practice: Every transaction has a fixed, predictable fingerprint so payments can be chained safely before confirmation, and hardware wallets can sign any transaction in constant time without downloading gigabytes of history.

Under the Hood: 16-byte fixed prefix (version=7, packed 64-bit lock word, u16 counts), Merkleized TxID vs. TxHash separation, and O(1) 4-block BLAKE3 BIP340 sighash modes over InputsRoot, OutputsRoot, and CoinsRoot.

Encoding, transaction identity and signatures

Decision packet P01, October 9, 2026. Recommended candidate, not frozen or implemented. Refines D01/D03/D04 and the serialization portions of D12–D14. This packet owns the detailed candidate grammar; the consensus overview links here. Production parameter values and independent vectors remain prerequisites for acceptance.

Choice and tradeoffs

Use a single canonical byte grammar with fixed-width outer counts, shortest CompactSize for nested collections, one input layout whose flags select spend, mint or coinbase, an explicit lock clock, and separate core/witness identities. By default sign every input/output policy and every selected leaf in one full-transaction mode; two explicit partial modes let a signer commit to only their own input plus all outputs or one paired output. Exclude mutable confirmation metadata from signatures so a benign reorg need not require resigning; contextual validity still checks that metadata.

Use a 32-byte ChainID chosen independently before genesis construction. It is an immutable network parameter, not the genesis hash and not a hash of a manifest containing itself. A published release manifest later binds ChainID, final parameters and the mined genesis. Different production/test networks must select different IDs. This breaks the would-be genesis/signature/UTXO-root circular dependency.

This keeps a 16-byte transaction prefix but changes its fields from the earlier design. Do not implement both encodings under the same version. CompactSize remains useful for bounded nested lengths; fixed-width wire fields alone do not provide zero-copy access to aligned host structs.

Primitive encoding

u8/u16/u32/u64/u128 are unsigned fixed-width little-endian integers. i128 is exactly 16-byte two's-complement little-endian. h32 is 32 raw digest bytes, displayed in the same order. Concatenation has no padding. CS, Bytes and Vec are as in C04; each grammar use below fixes the element type. Shortest lengths are mandatory. Reject trailing bytes within the enclosing transaction frame.

For every size/count, first check the declared count against its semantic cap, the remaining frame bytes against a conservative minimum, and all additions/multiplications against overflow. An announced large count does not authorize allocation. Amounts are u64; aggregate per-asset amounts and positive mint deltas are u128, with checked operations. Input and output counts are each at most 65,535 and indexing is zero-based. Lower production limits are D08 parameters.

Complete transaction grammar

Tx = version:u32(7) || lock:u64
     || input_count:u16 || output_count:u16
     || Input[input_count] || Output[output_count]

lock       = one little-endian u64 packing two fields
lock_kind  = lock & 0xff              (bits 0..7)
lock_value = lock >> 8                (bits 8..63, 56 bits)

Input = prev_txid:h32 || prev_index:u32 || sequence:u32 || flags:u8
        || authorization(flags)
authorization(01 spend)    = CS(path_index) || Vec(BranchWitness)
authorization(02 coinbase) = CoinbaseData
authorization(03 mint)     = BranchWitness
CoinbaseData = Vec(Bytes(data))  // count 0 or 1; present data length 1..8192
BranchWitness = CoreWitness || Vec(Bytes(arg))
CoreWitness   = Bytes(script) || Vec(h32 sibling)

Output = flags:u8 || value:u64 || token_id?
         || Vec(h32 branch_root) || Vec(Vec(CS(branch_index)))

An output has no separate state field. Output.flags defines two bits—bit 0 (0x01) HAS_TOKEN (token_id:h32 present and nonzero) and bit 1 (0x02) IS_BURN (provably unspendable burn / commitment output, analogous to OP_RETURN)—while bits 2..7 (0xfc) are unassigned and MUST be zero (valid flags values are 0x00, 0x01, 0x02, 0x03). A contract or protocol stores data or Merkle roots in branches in three ways (P02): on an IS_BURN (0x02/0x03) output with paths = [], as a dedicated unexecuted data branch on a spendable coin (branches = [CodeRoot, StateMerkleRoot], paths = [[0]]), or inside the executing branch tree itself (BranchNode(DataLeaf, M)).

The fixed transaction prefix is 16 bytes (4+8+2+2); nothing follows the outputs. On the wire the first lock byte is lock_kind and the next seven bytes are lock_value, little-endian. Lock_kind values 3..255 are unassigned and reject; they are not an extension mechanism. There is no transaction-kind field: a coinbase is recognized by its input. Version is 7, chosen so that no parser for Bitcoin-family or Lotus v1 transactions (versions 1 and 2) mistakes a v2 transaction for one of its own; any other version rejects. Input and output counts are at most 65,535 by construction; a larger payment set is expressed as chained transactions. Lower production limits remain D08 parameters. Output grammar/flags are C05. Unknown version/flags reject. No token-operation byte, scriptSig, annex, hidden per-input signature-mode byte, separate mint section, or optional trailing section exists.

An ordinary transaction is one with no coinbase input. Ordinary transactions require at least one consuming input. Zero outputs are permitted: a native imbalance becomes fees and a token imbalance becomes a token burn under accounting rules. Every spendable output ((flags & 0x02) == 0), even a zero-valued one, must have a valid nonempty authorization policy (path_count in 1..16); every burn/commitment output ((flags & 0x02) != 0) must have path_count == 0 (paths = []) and branch_count in 1..16, is included in the transaction's output sum (O_a) so 100% of its value is permanently burned, and is never inserted into the UTXO map (UtxoRoot). Zero amounts do not bypass resource charges. Inputs may not repeat a (prev_txid, prev_index) pair, whatever their flags. Input flags are 01 spend, 02 coinbase and 03 mint; 00 and every other value reject. The same numbering, 1 spend, 2 coinbase, 3 mint, is used wherever the kind of an input or invocation is tagged: in Input flags, in the signing selectors and by P03's INVOCATIONKIND. Earlier drafts had a read-only reference input kind, which has been removed (C13).

A coinbase is a transaction whose only input has flags 02. That input carries prev_txid = the parent BlockID (zero at genesis), prev_index = the derived block height as u32, sequence = ffffffff, and CoinbaseData. It resolves no coin. CoinbaseData has a canonical shortest-CompactSize count of zero (absence) or one; when present, its one Bytes(data) element MUST be nonempty and at most MAX_ELEMENT_BYTES = 8192 bytes. Count greater than one, an empty present element, and an oversized element reject. Its bytes are opaque vanity/extranonce data: they are never executed, scanned for OP_SUCCESS_N, interpreted as BranchWitness or used as a proof or authorization. Its encoded count, length and payload are charged as wire bytes, and hashing them is charged under P05. A coinbase therefore has exactly one input and no spends or mints; it requires at least one output, lock zero, and only native outputs ((flags & 0x01) == 0). The first transaction of a block MUST be a coinbase and no later transaction may contain a flags-02 input. The derived height MUST fit u32; overflow rejects, rather than wrapping. The parent BlockID and derived height MUST match the block context, including zero parent ID at genesis. Parent ID and height distinguish coinbase identities along one chain without requiring distinct data across competing siblings: sibling blocks with the same parent and height MAY use identical coinbase transactions. There is no global duplicate-coinbase ban; C07's within-block duplicate-TxID and occupied-outpoint checks still apply. Pools may vary CoinbaseData per worker, which changes both transaction identities and the block transaction root, or vary outputs/templates. Genesis has zero native issuance and initializes monetary state without advancing a recurrence (P02); exact genesis bytes remain a manifest choice. Non-genesis coinbase claims include P05's mandatory resource deduction. The coinbase contains no current-block ID or current-state root. Coinbase core thus depends only on already available parent/height/template data, avoiding a post-state-root cycle. No BIP30-style exception to occupied-outpoint rejection is imported.

A mint is an input with flags 03. It resolves no coin and is not a consuming input. Its authorization is one BranchWitness. Compute mint_root from Leaf(script) and the supplied siblings exactly as C11 computes a branch root; the prev_txid field holds the token ID, which MUST be nonzero and equal mint_root itself (C15's proposed program-derived identity). The root is already a domain-tagged BLAKE3 commitment, so it is not hashed again. prev_index MUST be zero and sequence MUST be ffffffff. A token's mint policy is thus a script tree like any branch: several mint methods may be committed and only the one used is revealed; a single-script policy is the zero-sibling case. The token ID, revealed script and membership proof sit in the core while the method arguments are witness-only data, as with a spend input's branch witness. A token ID and a branch root are the same kind of value. The consequence is that every script tree names a token whose ID is its root. Leaves are not typed, so a contract keeps its mint scripts and its spend scripts in separate trees (P02): the token ID is the root of the mint scripts alone, and they name the root of any rules tree that outputs must carry. The spend/mint tag in the signature selector keeps a signature for one use from authorizing the other. No separate mint count or mint section exists: input_count counts mint inputs, and a transaction that mints nothing carries no mint bytes.

Mint inputs may appear at any input position and are committed in wire order. The no-repeat rule above permits at most one mint input per token ID. Mint inputs MUST exactly cover positive token deltas: one for every token whose output sum exceeds its consuming-input sum, and none for any other token. A mint input contributes no amount of its own; the positive delta is computed by accounting and bound into its invocation. Several mint inputs in one transaction mint several tokens. A real outpoint and a mint pseudo-outpoint use different hash domains (H_txid, H_branch) and different flags.

Branch order stays committed as supplied; every output has 1 <= branch_count <= 16 (MAX_OUTPUT_BRANCHES = 16 in P05) and its 32-byte entries in branches must be pairwise distinct (a repeated 32-byte entry rejects). For spendable outputs ((flags & 0x02) == 0), path_count is consensus-bounded to 1..16 (MAX_OUTPUT_PATHS = 16), and paths are nonempty and lexicographically ordered, with strictly increasing indices in 0..branch_count-1. For burn/commitment outputs ((flags & 0x02) != 0), path_count MUST be 0 (paths = []). Because path_count == 0 is valid if and only if (flags & 0x02) != 0, there is never any ambiguity between zero paths and an unrestricted spend, and uniqueness gives each branch entry a single index in 0..15, which the branch-requirement opcodes in P03 rely on.

Bounding outputs to at most 16 branches and 16 paths (and pruning IS_BURN outputs from UtxoRoot) eliminates Bitcoin's parent-transaction and oversized-UTXO out-of-memory hazards by construction:

  • Zero parent-transaction loading: Input resolution fetches only the compact UTXO Coin record (Outpoint || Bytes(Output) || creation_height || creation_parent_mtp || coinbase), never the creating transaction.
  • Bounded Output and Coin size: Because scripts live in witnesses and contract state lives in branches or branch-tree data leaves (P02), an Output contains only 32-byte branch_roots and path indices. With MAX_OUTPUT_BRANCHES = 16 and MAX_OUTPUT_PATHS = 16 (each path containing at most 16 one-byte branch indices in 0..15), every serialized Output is at most 812 bytes (1 + 8 + 32 + 1 + 16×32 + 1 + (1 + 16) + 15×(1 + 15) = 812 bytes: distinct paths allow at most one length-16 path, with the next 15 longest paths of length 15; standard 1-branch, 1-path outputs are 45B native / 77B token), and every Coin record in UtxoRoot is at most 868 bytes (865 bytes without the three-byte CS(len(Output)) prefix, so 36 + 3 + 812 + 8 + 8 + 1 = 868; IS_BURN outputs are never inserted into UtxoRoot). Spending 256 or 1,000 inputs from the largest transactions in history requires $< 225\text{ KB}$ or $< 870\text{ KB}$ of Coin memory.
  • $O(1)$ bitmask path checks in RAM: Because every branch index is in 0..15, a node represents each path in memory as a single uint16_t bitmask (uint16_t paths[16], 32 bytes total per coin), making UTXOREQUIRESBRANCH, OUTPUTREQUIRESBRANCH, OUTPUTEXCLUSIVEBRANCH, and OUTPUTCONTINUESBRANCH pure $O(1)$ bitwise operations.

Absolute and relative locks

All comparisons use the candidate block's derived height and its parent's median time, not local wall time. Define MTP(parent) as the sorted median of up to the last eleven available ancestor timestamps including the parent; with an even initial sample size use element floor(n/2) in zero-based sorted order. Genesis's pre-parent MTP is zero. Values are unsigned seconds since Unix epoch; differences/additions use checked wide intermediates.

lock_kind Rule
00 Disabled; lock_value MUST be zero
01 Candidate block height ≥ lock_value
02 MTP(parent) ≥ lock_value

No sequence value disables an absolute lock. Equality is valid, intentionally specified rather than inherited from Bitcoin's locktime rules. The 56-bit lock field avoids a 32-bit seconds horizon. Transactions that fail a contextual lock are not permanently invalid for every later block.

For consuming inputs, sequence=ffffffff disables relative locking. Otherwise only bits 0..15 and bit 22 may be set; any other set bit rejects. Let d = sequence & 65535:

  • Bit 22 clear: candidate height ≥ coin.creation_height + d.
  • Bit 22 set: MTP(parent) ≥ coin.creation_parent_mtp + 512*d.

creation_parent_mtp is the parent's MTP at the block that created the coin, stored in its authenticated coin record. Coinbase creation uses the same metadata. Maturity is a separate height check. Same-block ordinary outputs have creation_height equal to the candidate height and creation_parent_mtp equal to current parent MTP, so only zero relative delay can pass. Overflow rejects rather than wraps. Relative-lock encoding is independent of local replacement policy.

Coinbase maturity applies to consumption: height >= creation_height + COINBASE_MATURITY. Ordinary coins have no maturity delay and may be spent in the block that creates them. The maturity value is at least one and remains uncalibrated.

Core and complete identities

Let Input(i) be complete input i as serialized on the wire, and let InputCore(i) be input i with each spend/mint BranchWitness replaced by its CoreWitness, omitting only that witness's Vec(Bytes(arg)) (the argument count and argument byte strings). Each consuming input in InputCore(i) thus retains CS(path_index) and Vec(CoreWitness) (its witness count and each branch witness's Bytes(script) || Vec(h32 sibling)), and each mint input retains its 41 fixed bytes plus CoreWitness (Bytes(script) || Vec(h32 sibling)). CoinbaseData is not a BranchWitness or a method argument: the coinbase InputCore(0) retains its entire encoded CoinbaseData and is byte-identical to Input(0), though the leaf and identity domains still differ. Changing coinbase data changes both TxID and TxHash.

Following Lotus v1's Malfix design (101-implement-malfix.patch), TxID and TxHash commit to the transaction's 16-byte header (TxHeaderCore) and the canonical bottom-up indexed binary Merkle roots (IndexedTreeRoot in P02) of its inputs and outputs:

TxHeaderCore     = version:u32 || lock:u64 || input_count:u16 || output_count:u16
InputCoreLeaf(i) = H_inputcore(InputCore(i))
InputFullLeaf(i) = H_inputfull(Input(i))
OutputLeaf(j)    = H_output(Bytes(Output[j]))

InputsRoot       = IndexedTreeRoot(InputCoreLeaf[0 .. input_count - 1])
FullInputsRoot   = IndexedTreeRoot(InputFullLeaf[0 .. input_count - 1])
OutputsRoot      = IndexedTreeRoot(OutputLeaf[0 .. output_count - 1])

TxID             = H_txid(ChainID || TxHeaderCore || InputsRoot || OutputsRoot)
TxHash           = H_txhash(ChainID || TxHeaderCore || FullInputsRoot || OutputsRoot)

Both TxID and TxHash top-level hashes take an exact fixed 112-byte preimage (32 + 16 + 32 + 32 = 112 bytes, two BLAKE3 blocks), and OutputsRoot (along with every OutputLeaf(j)) is computed once per transaction and shared across TxID, TxHash, and partial signing modes 01 and 02. Furthermore, because InputsRoot and OutputsRoot are IndexedTreeRoot commitments and H_name(x) = BLAKE3(ASCII(tag) || 00 || x) (C08), a smart contract can verify any individual input InputCore(m) or output Output[k] of a parent or injected transaction (OUTPOINTTXID(i)) in $O(\log N)$ space—without pushing the entire parent transaction onto the stack—by folding its sibling proof with MERKLEROOT_INDEXED (0xc1, hash_alg = 0) and hashing the 112-byte TxID preimage with <"Lotus/v2/txid\x00"> SWAP CAT BLAKE3 (0xba).

Including the witnesses without their arguments in InputCore(i) is a security requirement. It binds InputsRoot and TxID directly to the selected path, every revealed spend or mint script (Bytes(script)), and every Merkle membership proof (Vec(h32 sibling)). A transaction therefore cannot have its executed methods, branch proofs, proof-hashing costs or instruction-boundary OP_SUCCESS_N scan status substituted while keeping the same TxID—even on branches or mints that execute no CHECKSIG, across chained outpoint references (prev_txid), TXID introspection, and mempool TxID deduplication. Keeping Vec(Bytes(arg)) outside InputCore(i) avoids signature self-reference, lets signers produce signatures in parallel, and lets presigned or chained transactions reference prev_txid before witness arguments are signed.

TxHash is the Lotus v1 name for the hash of the complete transaction, witnesses and arguments included; earlier v2 drafts called it WitnessID. H_name domains are defined in the commitment packet. The block transaction root commits, in order, to each transaction's TxHash and TxID together (P02). Duplicate TxIDs within a block reject regardless of witness-argument differences. Inserting any output whose outpoint already exists in the current state rejects; never overwrite a coin, including a coinbase coin. Coinbase parent/height identity provides distinct identities along a chain; optional data is not needed for uniqueness, and identical coinbases on competing siblings are valid if their own branch state permits them. No global duplicate-TxID ban or BIP30 exception applies. Replaying a transaction on a competing fork can be valid if the same inputs exist there; ChainID separates networks, not every future fork of one network.

Resolved outputs and committed authorization

Signers authorize the resolved input policies and the exact scripts and proofs committed in InputsRoot (TxID), not just the resulting outputs. A coinbase runs no script, so none of the following is defined for it. Define:

CoinEntry(spend) = Bytes(Output(resolved_coin))
CoinEntry(mint)  = Bytes(empty)
CoinLeaf(i)      = H_coinentry(CoinEntry(i))
CoinsRoot        = IndexedTreeRoot(CoinLeaf[0 .. input_count - 1])

InputsRoot (InputCore(i)) already commits, in input and selected-path order, to each spend input's CS(path_index) and Vec(CoreWitness) and each mint input's CoreWitness. Together with CoinsRoot, this fixes the resolved coin's branches and paths, the required branch index paths[path_index][j] for each positional witness j, and the exact revealed script bytes and membership proof at every spend and mint position; no separate AuthPlan structure is needed. Scripts and their proofs are checked against the resolved coin's roots (or the mint's token ID) before script execution.

CoinEntry(i) commits to the complete serialized output for each spend input in wire order; outpoints, flags, sequences and core witnesses are already in InputCore(i), and input_count is already bound in TxHeaderCore inside TxID. A mint input resolves no coin, so its CoinEntry is the single byte 00 (zero-length Bytes), which keeps CoinLeaf[0 .. input_count - 1] aligned with input indices and cannot be confused with a serialized output. It excludes confirmation height, creation MTP and coinbase status. Those fields remain authenticated contextual inputs for locks/maturity; they do not affect the signing digest. Moving the same ordinary coin to a different block can change contextual validity without changing the signature's intent.

Argument vectors (Vec(Bytes(arg))) are excluded from InputCore(i) (TxID) and SigMessage; they remain committed by FullInputsRoot (TxHash) and are validated at execution. This avoids signature self-reference and allows independent signature production. A method that needs authenticated application arguments must explicitly verify them or bind their effect to committed transaction fields. There is no general claim that argument bytes are signer-immutable. There is no TxHash introspection opcode in this proposal.

Exact CHECKSIG message

Three signing modes are proposed. The mode is always part of the message. A 64-byte signature selects mode 00; a 65-byte signature is 64 signature bytes followed by one mode byte, which MUST be 01 or 02. Any other length or trailing byte, including an explicit 00, is a script error. Because adding a mode later would take a hard fork, this set is meant to be complete: there is no NONE, no all-inputs-one-output mode, no CODESEPARATOR, signature deletion, or legacy fallback. More unusual commitments are built in script from introspection and CHECKDATASIG.

SpendSelector = 01 || input_index:u32 || branch_index:u32 || Leaf(script)
MintSelector  = 03 || token_id:h32 || positive_delta:u128 || Leaf(mint_script)

OwnInputHash(i) = H_owninput(InputCore(i) || Bytes(Output(resolved_coin_i)))

mode 00 FULL
  SigMessage = H_sighash(ChainID || 00 || TxID || CoinsRoot || Selector)
mode 01 OWN_INPUT_ALL_OUTPUTS
  SigMessage = H_sighash(ChainID || 01 || version:u32 || lock:u64
                         || OwnInputHash(i) || OutputsRoot || Selector)
mode 02 OWN_INPUT_ONE_OUTPUT
  SigMessage = H_sighash(ChainID || 02 || version:u32 || lock:u64
                         || OwnInputHash(i) || OutputLeaf(i) || Selector)

Modes 01 and 02 correspond to Bitcoin's ALL|ANYONECANPAY and SINGLE|ANYONECANPAY. i is input_index, the zero-based index of the input whose script is executing, and branch_index is paths[path_index][j], the index in the spent coin's branches array of the branch that witness j satisfies. Modes 01 and 02 are defined only for spend invocations; a 65-byte signature in a mint invocation is a script error. In mode 02 the paired output is the one at the same index i as the input (OutputLeaf(i) = H_output(Bytes(Output[i]))); i >= output_count is a script error (both in CHECKSIG and in SIGHASH), never a signature over a placeholder. Same-index pairing is what stops one output from satisfying two different signed inputs. P02's registry holds the tags inputcore = Lotus/v2/inputcore, inputfull = Lotus/v2/inputfull, coinentry = Lotus/v2/coinentry, owninput = Lotus/v2/owninput, and output = Lotus/v2/output.

Every SigMessage preimage across all three modes (00, 01, 02) is fixed-size—138 bytes in mode 00 spend, 150 bytes in modes 01 and 02, and 178 bytes in mode 00 mint (always $\le 4$ BLAKE3 64-byte compression blocks including the domain prefix). This eliminates Bitcoin's $O(N^2)$ sighash hashing bug in both full and partial modes: because InputCore(i) contains all revealed scripts and Merkle proofs for input i, hashing raw InputCore(i) inside H_sighash on every partial-mode signature would re-hash potentially kilobytes of witness scripts whenever an input executes multiple branches or checks multiple signatures. Instead, a validator computes OutputLeaf(j), OutputsRoot, InputCoreLeaf(i), InputsRoot, TxID, CoinsRoot, and OwnInputHash(i) in strictly linear $O(\text{tx bytes} + \text{resolved coin bytes})$ time, and every CHECKSIG or SIGHASH execution hashes at most 4 BLAKE3 blocks in $O(1)$ time.

A partial-mode signature covers the transaction version and lock, the 32-byte digest OwnInputHash(i) of the signer's own outpoint, sequence, path choice, revealed scripts, membership proofs (InputCore(i)) and resolved coin (Bytes(Output(resolved_coin_i))), the stated outputs (OutputsRoot or OutputLeaf(i)), and SpendSelector (including input_index, branch_index, and Leaf(script)). It does not cover any other input, any other input's coin, or in mode 02 any other output; anyone may add those at other indices. It is bound to one coin through the outpoint and to input index i (and in mode 02 output index i) through SpendSelector, and it remains usable in any transaction that satisfies it until that coin is spent. The absolute lock is a not-before bound, not an expiry. No script condition can express an expiry either (C22a): a signed offer stays usable until one of its inputs is spent, so withdrawing it means spending that coin. Wallets and signing devices must display the mode and must not treat a partial-mode request as an ordinary payment.

SpendSelector explicitly binds input_index:u32 and branch_index:u32 in addition to Leaf(script). Because witness argument vectors Vec(Bytes(arg)) are excluded from InputCore(i) (TxID) and SigMessage, omitting input_index and branch_index would allow a signature created for one input (or one branch of a multi-branch path) to be replayed on another input or branch in the same transaction that executes the same Leaf(script) with a different witness argument vector Vec(Bytes(arg)) (for example, when a parameterized script reads an argument index, amount, or payload that is checked against transaction state). Binding (input_index, branch_index, Leaf(script)) prevents cross-input and cross-branch signature replay over differing witness arguments while still allowing a (message, public key, signature) verification result to be reused if the same invocation checks the same signature more than once.

CHECKSIG verifies the stack signature against these 32 message bytes, using the BIP340 algorithm unmodified (including its SHA256-based challenge calculation). Do not substitute BLAKE3 inside BIP340 because Lotus uses BLAKE3 for its message construction. No current block hash/height/time, coin confirmation metadata, witness arguments (including signatures) or TxHash enters this preimage. Reorganizations still require rechecking contextual validity and caches.

CHECKSIG stack order is [..., signature, public_key]; it consumes both and pushes canonical int128 Boolean. Public key is exactly 32-byte BIP340 x-only encoding; the signature operand is exactly 64 or 65 bytes as defined above, of which the first 64 are the BIP340 signature. Wrong length or invalid key encoding is a script error; a correctly sized but invalid signature pushes false. CHECKSIGVERIFY consumes the Boolean and rejects false. No empty-signature special case. Wallets must not reuse signing nonces across messages or signature algorithms. BIP340 defines the signature algorithm; this packet defines Lotus's message.

Acceptance evidence still required

Generate exact primitive, ordinary/coinbase, core/full, CoinsRoot/selector and signing vectors in the independent reference tool; compare a second implementation. Test confirmation-metadata and witness-argument changes separately from output/method/proof changes. Account for the per-transaction construction cost of InputsRoot, OutputsRoot, CoinsRoot, and OwnInputHash(i), and per-invocation signature charges. Freeze ChainID, versions and limits in the parameter manifest. This packet resolves proposed byte meaning; it does not supply mainnet constants, signed fixtures, or acceptance of this three-mode set without review.
