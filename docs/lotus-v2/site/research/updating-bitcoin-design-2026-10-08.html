1. The "Updating Bitcoin" Philosophy: Invariants vs. Internals

Bitcoin was humanity's first successful implementation of decentralized digital scarcity. However, its 2008 architecture accumulated critical design compromises:

  • Storage Fragility: Uncommitted UTXO sets reliant on flat key-value databases (LevelDB), risking catastrophic unrecoverable corruption on unexpected power loss.
  • Serialization Inefficiencies: Variable-length integers (CompactSize / varint) causing non-aligned CPU memory access, quadratic serialization parsing overhead, and transaction malleability vulnerabilities.
  • Script Limitations: The CScriptNum sign-magnitude format (capping math at 32-bit signed integers with negative-zero malleability), disabled multiplication/division opcodes, and zero introspection capabilities.
  • Token Inadequacies: Reliance on fragile off-chain indexers (SLP / Colored Coins) where accidental spend of a token UTXO by a standard wallet permanently burns the asset.
  • Mining Bottlenecks: $O(n^2)$ CPFP ancestor-package graph recalculation during mempool admission, forcing artificial chain limits (25/50 tx limit) that cripple payment channels and high-velocity systems.
  • Macroeconomic Vulnerabilities: Rigid 4-year halving step-functions that inflict revenue shocks on miners, periodically destabilizing hashrate and spurring fee-market volatility.

The Zero-Hardfork Bifurcation

To eliminate these bottlenecks while guaranteeing that the protocol never needs a hardfork, the architecture strictly separates the Immutable Consensus Layer (rules locked at Genesis) from the Node Implementation Layer (local software optimizations):

3. Immutable Consensus Specification (Locked at Block 0)

3.1. The 116-Byte Header & 2-Minute Block Interval

Evolution from Lotus v1 Extended Header

Lotus v1 introduced an extended 160-byte block header (src/primitives/block.h). Lotus v2 consolidates and aligns this structure, replacing historical experimental fields with active cryptographic state commitments:

struct LotusHeader {
    int32_t  nVersion;             // 4 bytes: Protocol version
    uint256  hashPrevBlock;        // 32 bytes: Parent block hash (Single BLAKE3)
    uint256  hashTxMerklixRoot;    // 32 bytes: Single BLAKE3 Merklix root of block txs

Why hashUtxoMerklixRoot Replaces hashEpochBlock & hashExtendedMetadata:

  1. The "Lucky Block" Commitment is Obsolete: In Lotus v1, hashEpochBlock attempted to create an inter-block skip-list for Epoch SPV (ESPV) by pointing to blocks that undershot difficulty by a factor of 5,040. However, ESPV could only prove that block headers were linked under heavy PoW—it could not prove whether a transaction output was unspent. Light clients were still forced to trust third-party servers for UTXO existence. By committing to hashUtxoMerklixRoot in every single block, every node and wallet obtains cryptographic inclusion and exclusion proofs directly from the chain tip.
  2. Unlocking Stateless Validation: With hashUtxoMerklixRoot embedded in the header, blocks become self-authenticating. A transaction can carry compact Merklix branch proofs for its inputs; the node verifies these against hashUtxoMerklixRoot in RAM without touching a disk database.
  3. Hardware Memory Alignment: Replacing the 6-byte vTime and 7-byte vSize with standard 32-bit timestamps and 64-bit nonces guarantees that header arrays reside on clean 64-bit cache-line boundaries.

The 2-Minute Block Interval (The "Goldilocks Cadence")

  • Target Block Time: 120 seconds (2 minutes).
  • Cadence: Exactly 30 blocks/hour, 720 blocks/day, $\approx \mathbf{263,000 \text{ blocks/year}}$.
  • Physical Advantages:
  • $1.25\%$ Orphan Window: With global P2P block propagation averaging $1.5\text{ seconds}$, a 120-second interval spends only $1.25\%$ of time in transit, eliminating geographic centralization pressures on miners.
  • $5\times$ DAA Responsiveness: The ASERT difficulty algorithm updates target work every 120 seconds, smoothly tracking global hashrate changes without price-lag oscillations.
  • Continuous Background Pre-Validation: The 2-minute cadence gives validation nodes ample time to pre-verify mempool transactions in parallel background threads. When a block arrives, $>95\%$ of transactions are already verified in RAM.

3.2. Single BLAKE3 Domain-Separated Segmented Merklix Tree

The Elimination of Double Hashing (BLAKE3d Rejected)

Legacy Bitcoin utilizes double SHA-256 (SHA256(SHA256(x))) to prevent length-extension attacks. BLAKE3 is based on the Bao tree architecture and includes native domain separation flags in every compression call:

  • CHUNK_START (0x01), CHUNK_END (0x02), PARENT (0x04), ROOT (0x08).

Because interior nodes and leaf nodes operate under mathematically distinct domain flags, length-extension attacks and interior/leaf collision attacks are mathematically impossible. Performing double BLAKE3 (BLAKE3(BLAKE3(x))) wastes 50% of CPU cycles with zero added security. Single BLAKE3 is enforced across all consensus primitives.

The Segmented Merkle Tree Invariant (Resolving CVE-2012-2459)

To prevent leaf duplication vulnerabilities where an unconfirmed transaction can spoof an interior merkle node:

  1. Every leaf hash is hashed with domain prefix: $$\text{LeafHash} = \mathbf{BLAKE3}(\text{DOMAIN\_LEAF} \parallel \text{SerialTx})$$
  2. Interior nodes combine two 32-byte children: $$\text{ParentHash} = \mathbf{BLAKE3}(\text{DOMAIN\_NODE} \parallel \text{Left} \parallel \text{Right})$$
  3. Zero-Padded Odd Layers: If an odd number of elements exists at layer $L$, the dangling element is paired with a fixed 32-byte null constant ($\mathbf{0}_{256}$) committed with the layer depth: $$\text{DanglingParent} = \mathbf{BLAKE3}(\text{DOMAIN\_NODE} \parallel \text{Child} \parallel \mathbf{0}_{256} \parallel \text{uint8}(L))$$ Duplicating the right-hand leaf (the Satoshi bug) is strictly invalid.

3.3. Zero-Copy Wire Format, Inline Witnesses & Single-Asset Multi-Branch Outputs

Variable-length integers (CompactSize / varint) are eliminated from transaction headers and fixed records. Crucially, the BIP-141 soft-fork hack of a decoupled, trailing witness vector is completely discarded. In Lotus v2, witnesses map 1-to-1 directly inside vin, and minting proofs are structured per-asset at the transaction level.

Why Re-Using nValue Eliminates the "Dust Nightmare":

  1. Zero Dust Overhead: In legacy protocols (SLP, CashTokens), token outputs were mutant hybrids: they were forced to carry 546 satoshis of native crypto just to satisfy miner dust limits. In Lotus v2, token outputs carry 0 XPI satoshis.
  2. Zero Accidental Burn Risk: Because token outputs have no native XPI in them, an un-upgraded wallet cannot mistake a token coin for a satoshi coin and accidentally spend it as miner fees.
  3. Malleability Immunity by Construction: The TXID is defined as: $$\mathbf{TxID} = \mathbf{BLAKE3}\Big(\text{nVersion} \parallel \text{nLockTime} \parallel \text{vin\_stripped} \parallel \text{vout}\Big)$$ Where vin_stripped excludes all branch_witnesses, and mint_witnesses are excluded. Third parties can never malleate the TXID.

3.4. Native Layer-1 Assets & Universal Conservation

3.4.1. The Universal Conservation Law

In Lotus v2, the consensus engine runs a single, universal accounting loop across all assets in a transaction:

For every unique asset_id (where asset_id = 0 represents native XPI): $$\sum_{\text{in}} \text{nValue}[\text{asset}] \ge \sum_{\text{out}} \text{nValue}[\text{asset}]$$

  • For Native XPI (asset_id == 0): The difference is the Miner Fee: $$\text{Miner Fee} = \sum_{\text{in}} \text{nValue}[\text{XPI}] - \sum_{\text{out}} \text{nValue}[\text{XPI}] \ge 0$$
  • For Tokens (asset_id != 0): The difference is an Opt-in Burn.
  • Sub-Microsecond Validation: For 99.9% of transactions (standard peer-to-peer transfers), token validation requires zero script interpretation. It is a single SIMD 128-bit comparison (sum_in >= sum_out). Nodes validate over 100,000 token transfers per second per CPU core.

3.4.2. Token Scarcity & The Minting Engine ($\Delta > 0$)

When a transaction outputs more tokens than it inputs: $$\Delta[\text{TokenID}] = \sum_{\text{out}} \text{nValue}[\text{TokenID}] - \sum_{\text{in}} \text{nValue}[\text{TokenID}] > 0$$

Consensus strictly requires an entry in tx.mint_witnesses where: $$\mathbf{TokenID} = \mathbf{BLAKE3}(\text{mint\_witness}.\text{minting\_script})$$

The node executes minting_script with mint_witness.stack_args. If the script returns true, the expansion of supply is approved. If missing or false, the transaction is immediately rejected as counterfeit (bad-txns-unauthorized-mint).

3.4.3. The Three Minting & Governance Architectures (Zero Batons in Consensus)

Tracking physical "baton coins" in consensus creates massive codebase fragility (LevelDB capability flags, undo log bloat, accidental burn risks). Lotus v2 eliminates consensus batons entirely in favor of three clean architectures:

  1. Pattern 1: The Treasury Vault Pattern (Zero Minting Scripts After Genesis):
  2. At Genesis, total authorized supply (e.g. 10 Billion USDC) is minted into a Treasury Vault UTXO governed by an $m$-of-$n$ multisig. Circulating market supply is $0$.
  3. Issuance: When reserves arrive, the company spends from the Treasury UTXO: $50,000$ to the buyer, and $9,999,950,000$ change back to the Treasury.
  4. Key Rotation: The officers spend the Treasury coin to their new multisig address.
  5. Consensus: $\sum \text{in} \ge \sum \text{out}$ holds 100% of the time. The consensus engine never executes a minting script after Genesis.
  6. Pattern 2: Dynamic Delegated Minting (OP_CHECKDATASIG):
  7. For elastic tokens: MintingScript hardcodes a Cold Root Public Key (Root_PK).
  8. The cold key signs an off-chain Delegation Certificate: $$\text{Cert} = \text{Sign}_{\text{Root\_PK}}(\text{Epoch: 2}, \text{ Authorized: Frank}, \text{ Expiry: Block 600,000})$$
  9. When minting, mint_witnesses provides stack_args = [Frank_Sig, Cert_Bytes, Root_Sig].
  10. MintingScript verifies the certificate via OP_CHECKDATASIGVERIFY, extracts Frank's key, and verifies Frank's transaction signature with OP_CHECKSIG.
  11. Key Rotation: Cold Root signs a new certificate. TokenID never changes. Consensus tracks zero batons.
  12. Pattern 3: One-Time Hard-Capped Genesis (e.g. 21 Million Max Supply):
  13. Anchored to a unique Genesis outpoint (prevout = 0x1234...:0): ``forth OP_0 OP_PICKINPUTOUTPOINT <0x1234...:0> OP_EQUALVERIFY OP_0 OP_ENUMERATE_OUTPUTS OP_PICKOUTPUTVALUE OP_ADD OP_ENDENUMERATE 2100000000000000 OP_LESSTHANOREQUAL ``
  14. Because prevout can only be spent once in blockchain history, the script can only succeed once. Double-minting is mathematically prevented by UTXO double-spend rules.

3.4.4. Read-Only Reference Inputs (FLAG_READ_ONLY_REFERENCE)

To inspect on-chain vault or oracle state without double-spend contention:

  • Set FLAG_READ_ONLY_REFERENCE = 0x01 on LotusInput.
  • The coin is read, not spent. It remains in the UTXO set.
  • Enables 10,000 users to read and validate against a central vault in the exact same block with zero lock collisions.

3.5. Variadic Spending Paths, Branch Merklix Trees (MAST) & Intra-Transaction Validation Caching

3.5.1. The Variadic Spending Paths Architecture (Option B Positional Witnesses)

In smart contract and transaction design, spending authorization naturally resolves into two orthogonal dimensions:

  1. Horizontal Role Composition (Branches & Paths): "WHICH participants, covenants, or guardians must approve this spend?"
  2. Vertical Specialization (The MAST within each Branch): "WHICH specific method or execution path is that role running?"
Elimination of Fixed-Depth Tree Bottlenecks

Early iterations evaluated spending conditions using fixed boolean topologies (such as 4-leaf NAND trees). However, fixed-depth structures introduce severe limitations:

  • They artificially restrict an output to at most 4 leaves and 2 spending paths.
  • They cannot express simple, common structures like $A \lor B \lor C$ (three independent alternative spenders) or $A \land B \land C$ (three co-signers) without nested inlining acrobatics.
  • Forcing multi-spender and multi-method logic into a single fixed tree causes combinatorial inlining bloat: 3 co-signers and 3 contract methods would require duplicating code across $\binom{3}{2} \times 3 = 9$ separate leaves.

Lotus v2 replaces fixed wiring topologies with the Variadic Spending Paths Architecture: $$\text{branches} = [ \mathbf{root}_0, \mathbf{root}_1, \dots, \mathbf{root}_{N-1} ] \quad (1 \le N \le 65,535)$$ $$\text{paths} = [ \mathbf{path}_0, \mathbf{path}_1, \dots, \mathbf{path}_{M-1} ] \quad (1 \le M \le 65,535)$$

  • Branches: An explicit array of 32-byte Merklix Roots, each representing an autonomous role or policy (e.g. Owner, Co-Signer, Covenant, Protocol Fee Controller).
  • Paths: A list of valid spending paths. Each path is a canonical, strictly sorted vector of branch indices required: $$\mathbf{path}_p = [ b_{p,0}, b_{p,1}, \dots, b_{p,k-1} ] \quad \text{where } b_{p,0} < b_{p,1} < \dots < b_{p,k-1}$$
  • Expressiveness:
  • Standard Single-Key / P2SH: branches = [A], paths = [[0]]
  • 2-of-2 Covenant (Owner + Vault): branches = [Owner, Vault], paths = [[0, 1]]
  • 1-of-2 Recovery (Owner OR Backup Key): branches = [Owner, Backup], paths = [[0], [1]]
  • Quorum / Guarded Spending: branches = [Alice, Bob, Charlie, Vault], paths = [[0, 1, 3], [0, 2, 3], [1, 2, 3]] (Any 2 owners AND the vault).
Option B: Positional Witness Mapping

When spending an output, the transaction input chooses exactly which spending path to activate via input.path_index: $$\mathbf{active\_path} = \text{coin.paths}[\text{input.path\_index}]$$

To eliminate all redundant wire overhead, dummy witnesses, and placeholder padding:

  • The transaction input supplies an array of branch witnesses: input.branch_witnesses.
  • Positional Binding Invariant: The number of witnesses provided MUST exactly equal the number of required branches in the selected path: $$\mathbf{input.branch\_witnesses.size}() == \mathbf{active\_path.size}()$$
  • Witness element $i$ positionally binds to branch index $\mathbf{active\_path}[i]$: $$\mathbf{input.branch\_witnesses}[i] \iff \mathbf{coin.branches}[\mathbf{active\_path}[i]]$$
  • There is zero branch index byte within the witness, zero empty dummy witnesses, and zero unspent branch leakage. If the spending path requires branches [0, 2], branch_witnesses has length 2: witness[0] validates against branch[0], and witness[1] validates against branch[2].

3.5.2. Every Branch is a 32-Byte Merklix Root (MAST)

Every entry in coin.branches is uniformly a 32-byte Merklix Root. A branch can be either a single atomic script or an entire Merklized Alternative Script Tree (MAST):

┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 1. HORIZONTAL COMPOSITION (Branches & Paths on Output Wire)                            │
│    • Output defines: branches[0..N] and paths[0..M]                                    │
│    • e.g. Path 0: [Alice, Bob, LendingVault]                                          │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 2. VERTICAL SPECIALIZATION (MAST within each Branch Root)                              │
│    • Each branch root expands into its own Merklix tree of leaf methods                │
│    • Spender reveals ONLY the active leaf script + Merkle audit path                   │
│    • Unused methods remain completely private 32-byte hashes                           │
└────────────────────────────────────────────────────────────────────────────────────────┘
1-Leaf Fast Path vs Multi-Leaf Merklix Tree

When validating input.branch_witnesses[i] against branch root $\mathbf{R} = \text{coin.branches}[\mathbf{active\_path}[i]]$:

  1. 1-Leaf Tree Fast Path (merkle_proof.empty()): For standard single-key payments, basic multisig, or single-method scripts, the branch root is simply the BLAKE3 hash of the leaf script: $$\mathbf{BLAKE3}(\text{bw.script}) == \mathbf{R}$$ If bw.script is a standard public-key script (<PubKey> OP_CHECKSIG), the interpreter skips bytecode parsing and dispatches directly to AVX-512 batch Schnorr verification ($\approx 30\text{ ns}$).
  2. Multi-Leaf Tree (!merkle_proof.empty()): For smart contracts with multiple methods (e.g. deposit, borrow, liquidate, repay):
  3. Each method is an unhashed leaf in a BLAKE3 domain-separated Merklix tree: $$\mathbf{leaf\_hash} = \mathbf{BLAKE3}(\text{DOMAIN\_LEAF} \parallel \text{bw.script})$$
  4. The node verifies that leaf_hash is cryptographically included in $\mathbf{R}$ using bw.merkle_proof: $$\mathbf{VerifyMerklixProof}(\mathbf{leaf\_hash}, \text{bw.merkle\_proof}, \mathbf{R}) == \mathbf{true}$$
  5. The spender reveals only the active method script and its Merkle path. All other methods remain cryptographically unrevealed and zero-knowledge.

3.5.3. Wire-Level P2PKH Obsolescence: Universal Script Hashing & Address Resolution

In legacy Bitcoin (2008), the consensus protocol maintained distinct serialized wire formats for different output types (scriptPubKey bytecodes for P2PK, P2PKH, P2SH). This forced full nodes to inspect and branch on arbitrary, variable-length script bytecodes during UTXO database serialization and mempool validation.

Wire-Level Unification (All Outputs Are Branch Roots)

In Lotus v2, the distinct wire-level "P2PKH output" is obsolete. The consensus wire format recognizes only one unified output representation: an explicit array of 32-byte BLAKE3 branch roots evaluated through variadic spending paths: $$\mathbf{branch}[k] = \mathbf{BLAKE3}(\mathbf{script}_k) \quad \text{or} \quad \mathbf{branch}[k] = \mathbf{MerklixRoot}(\{\mathbf{script}_{k,m}\})$$

Every output in Lotus v2 is structurally a Pay-to-Script-Hash (P2SH) / Pay-to-MAST. Consensus does not know or care whether an output is a single-key payment, an address hash, a multisig vault, or an AMM covenant—they all exist as uniform 32-byte hashes.

Sending to a Hashed PubKey Address (pubkeyhash)

When a user shares an address, they provide a compact hashed public key (pubkeyhash): $$\mathbf{PubKeyHash} = \mathbf{BLAKE3}(\text{PubKey}) \quad \text{or} \quad \mathbf{RIPEMD160}(\mathbf{SHA256}(\text{PubKey}))$$

The sender only knows PubKeyHash—the sender does not know the recipient's raw public key.

Hashing the public key inside the script is therefore essential for address-based payments:

  1. Deterministic Script Construction by Sender: The sender's wallet constructs the canonical address-resolution script from PubKeyHash: $$\mathbf{script} = \mathbf{OP\_DUP} \;\; \mathbf{OP\_BLAKE3} \;\; \langle\mathbf{PubKeyHash}\rangle \;\; \mathbf{OP\_EQUALVERIFY} \;\; \mathbf{OP\_CHECKSIG}$$
  2. Commitment on the Wire: The sender computes the 32-byte branch root: $$\mathbf{branch}[0] = \mathbf{BLAKE3}(\mathbf{script})$$ and serializes it into the 45-byte output record with paths = [[0]]. The sender never needs the recipient's public key.
  3. Sub-Microsecond Wallet Indexing: The recipient's wallet knows its own PubKeyHash. The wallet precomputes: $$\mathbf{expected\_branch} = \mathbf{BLAKE3}\Big(\mathbf{OP\_DUP} \parallel \mathbf{OP\_BLAKE3} \parallel \mathbf{PubKeyHash} \parallel \mathbf{OP\_EQUALVERIFY} \parallel \mathbf{OP\_CHECKSIG}\Big)$$ The wallet registers expected_branch with Chronik. When a transaction is received, Chronik indexes the output by branch[0] in $O(1)$ time—enabling instantaneous payment discovery without scanning raw scripts.
  4. Execution at Spend Time: When spending the coin, the recipient's input supplies:
  5. input.path_index = 0
  6. input.branch_witnesses[0].script = OP_DUP OP_BLAKE3 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
  7. input.branch_witnesses[0].merkle_proof = []
  8. input.branch_witnesses[0].args = [ <64B Schnorr Sig>, <33B PubKey> ] The node verifies BLAKE3(script) == coin.branches[0], then executes the script: PubKey is duplicated, hashed with BLAKE3, verified equal to PubKeyHash, and the Schnorr signature is verified against PubKey.
Direct Public-Key Scripts (<PubKey> OP_CHECKSIG)

When the recipient's public key is known in advance (e.g. interactive payment channels, deterministic key exchanges, or Nostr/WebLN invoices), the sender skips the inner pubkey hash check: $$\mathbf{script} = \langle\text{33-byte PubKey}\rangle \;\; \mathbf{OP\_CHECKSIG} \quad (34\text{ bytes})$$ $$\mathbf{branch}[0] = \mathbf{BLAKE3}(\text{PubKey} \parallel \text{OP\_CHECKSIG})$$ At spend time, the witness provides only args = [ <64B Schnorr Sig> ] (saving 33 bytes on the wire), and node validators route directly to the AVX-512 batch Schnorr fast-path ($\approx 30\text{ ns}$).

3.5.4. Multi-Covenant Token Governance & The Linear Resource Model (Move Comparison)

In Ethereum, token balances and covenant states are stored in isolated, siloed smart contract storage tables (mapping(address => uint256)). This forces tokens to be manipulated through dynamic cross-contract calls (transferFrom), introducing reentrancy vulnerabilities and severe execution bottlenecks.

Lotus v2 adopts the Linear Resource Model (analogous to the Move language):

  1. Assets are Resources, Not Storage Mappings: An asset is a physical UTXO record. It has an explicit asset identity (token_id), cannot be cloned, cannot be silently destroyed, and obeys the immutable universal conservation law: $$\sum_{\text{in}} \text{nValue}[\text{asset}] \ge \sum_{\text{out}} \text{nValue}[\text{asset}]$$
  2. Orthogonal Separation: Asset Type vs. Owner vs. Covenant Logic:
  3. Asset Type (token_id): Distinguishes native XPI (miner fees) from specific tokens, enabling $O(1)$ SIMD conservation checks ($3\text{ ns}$) without executing any script.
  4. Owner (branch[0]): Authorizes the asset holder to approve transfers or reallocations.
  5. Covenant Rules (branch[1], etc.): Governs operational rules (liquidity pools, collateral vaults, vesting locks).
  6. Decoupled Composability: Because token_id is an explicit orthogonal field, a token can enter a lending vault, transition into an AMM pool, or be deposited into an escrow contract without mutating its underlying asset identity. The covenant simply occupies a branch on the coin, leaving the asset type immutable.

3.5.5. Intra-Transaction Validation Caching & Static Purity Analysis (OP_INPUTINDEX)

In complex transactions (such as vault consolidations, batch withdrawals, or multi-input swaps), multiple transaction inputs often execute identical covenant branch scripts. If every input naively re-executes the same covenant script from scratch, validation time scales linearly with input count ($O(K \cdot \text{ops})$).

The Reflected Data Hazard: Why Naive Caching Breaks

A naive node implementation might attempt to cache script execution results across companion inputs by script hash alone: $\mathbf{CacheKey} = \mathbf{BLAKE3}(\text{TxID} \parallel \text{ScriptHash})$. However, if a covenant uses reflected input data—specifically OP_INPUTINDEX (0xc0) or input-dependent introspection:

  • On vin[0], OP_INPUTINDEX pushes 0.
  • On vin[1], OP_INPUTINDEX pushes 1.
  • If vin[0] executes OP_INPUTINDEX OP_UTXOVALUE and sees $10,000\text{ XPI}$, but vin[1] only provides $1\text{ XPI}$, blindly reusing vin[0]'s cached TRUE result on vin[1] would allow an attacker to bypass all balance checks and drain the vault!
Solution 1: Static Purity Analysis (Node-Level Caching)

Before executing a branch script, the node validator performs a single $O(\text{script\_size})$ scan over the script bytecode: $$\mathbf{IsPureTxPredicate} = (\text{script does NOT contain } \mathbf{OP\_INPUTINDEX})$$

  • Pure Transaction Predicates (IsPureTxPredicate == true): The script only inspects global transaction invariants (tx.outputs, tx.locktime, tx.version, or literal inputs via 0 OP_UTXOVALUE). The script is a mathematically pure function of the transaction: $$f(\text{Tx}) \to \{\mathbf{TRUE}, \mathbf{FALSE}\}$$ Its result is 100% invariant across all inputs in the transaction. The node safely caches the result using: $$\mathbf{CacheKey} = \mathbf{BLAKE3}(\text{TxID} \parallel \text{ScriptHash})$$ The script executes exactly once for the first companion input; all subsequent companion inputs resolve the cache in $< 5\text{ nanoseconds}$.
  • Input-Dependent Predicates (IsPureTxPredicate == false): The script's outcome depends on which input is currently executing. The cache key commits to the executing input index: $$\mathbf{CacheKey} = \mathbf{BLAKE3}(\text{TxID} \parallel \text{ScriptHash} \parallel \mathbf{input\_index})$$ The script evaluates independently for each input, guaranteeing absolute consensus soundness.
Solution 2: The Master/Companion Script Pattern (Compiler-Level)

High-performance covenant compilers (such as the Lotus Contract Compiler) optimize multi-input covenants using the Master/Companion Pattern:

  • The covenant script checks whether it is running on the primary ("master") vault input: $$\mathbf{is\_master} = (\mathbf{OP\_INPUTINDEX} == \mathbf{master\_input\_index})$$
  • On the Master Input: The contract executes the comprehensive aggregation loop: iterating over all inputs, computing total vault balances, and verifying reserve constraints.
  • On Companion Inputs: The contract executes a 3-opcode fast-path: ``forth <master_input_index> OP_UTXOBRANCH <branch_k> OP_ACTIVEBYTECODE OP_BLAKE3 OP_EQUALVERIFY `` It simply asserts that the Master Input is present in this same transaction and executing the identical covenant.
  • Result: In a 5-input consolidation, 1 input executes the loop, and 4 inputs execute in 3 CPU instructions. Total execution cost drops by $> 75\%$.

3.5.6. Complete Output Authorization Validation Algorithm

bool VerifyLotusOutputAuthorization(const LotusOutput &coin, const LotusInput &input, size_t input_index, const CTransaction &tx) {
    // 1. Path Index Bounds Check
    if (input.path_index >= coin.paths.size()) {
        return false; // SCRIPT_ERR_INVALID_PATH_INDEX
    }
    const std::vector<CompactSize> &required_branches = coin.paths[input.path_index];

    // 2. Option B Positional Mapping Invariant
    if (input.branch_witnesses.size() != required_branches.size()) {
        return false; // SCRIPT_ERR_WITNESS_COUNT_MISMATCH
    }

    // 3. Execute Required Branch Witnesses Positionally
    for (size_t i = 0; i < required_branches.size(); ++i) {
        CompactSize branch_k = required_branches[i];
        if (branch_k >= coin.branches.size()) {
            return false; // SCRIPT_ERR_BRANCH_INDEX_OUT_OF_BOUNDS
        }
        const uint256 &expected_branch_root = coin.branches[branch_k];
        const BranchWitness &bw = input.branch_witnesses[i];

        // 4. Branch Root Cryptographic Verification
        if (bw.merkle_proof.empty()) {
            // 1-Leaf Tree Fast-Path: Preimage check
            if (BLAKE3(bw.script) != expected_branch_root) {
                return false; // SCRIPT_ERR_SCRIPT_HASH_MISMATCH
            }
        } else {
            // Multi-Leaf Merklix Tree Proof
            uint256 leaf_hash = BLAKE3(DOMAIN_LEAF, bw.script);
            if (!VerifyMerklixProof(leaf_hash, bw.merkle_proof, expected_branch_root)) {
                return false; // SCRIPT_ERR_MERKLE_PROOF_INVALID
            }
        }

        // 5. Script Execution with Intra-Transaction Caching
        bool script_passed = false;
        if (bw.script.IsP2PKFastPath()) {
            // AVX-512 batch Schnorr fast-path (~30ns)
            script_passed = VerifySchnorrFastPath(bw);
        } else {
            // Static Purity Analysis & Caching
            bool is_pure = !ScriptContainsInputIndex(bw.script);
            uint256 cache_key = is_pure
                ? BLAKE3(tx.GetId(), expected_branch_root)
                : BLAKE3(tx.GetId(), expected_branch_root, static_cast<uint32_t>(input_index));

            if (tx_validation_cache.Lookup(cache_key, script_passed)) {
                // Cache hit! Skip VM execution
            } else {
                script_passed = ExecuteScriptVM(bw.args, bw.script, input_index, tx);
                tx_validation_cache.Insert(cache_key, script_passed);
            }
        }

        if (!script_passed) {
            return false; // SCRIPT_ERR_EVAL_FALSE
        }
    }

    return true; // All required branches in selected path satisfied!
}

3.6. The 128-Bit Forth Stack Machine (int128_t)

All numerical values on the evaluation stack are native 128-bit signed two's-complement integers (int128_t / __int128_t, 16 bytes):

  • Elimination of CScriptNum:
  • Legacy Bitcoin stored integers as variable-length sign-magnitude byte arrays (1 to 4 bytes, later expanded to 8 bytes with quirky rules). This introduced sign-magnitude ambiguity, negative-zero (0x80) malleability bugs, and endianness mismatch.
  • In Lotus v2, numbers on the stack are fixed 16-byte signed two's-complement integers. Zero sign-magnitude quirks, zero negative-zero bugs, zero variable-byte allocations.
  • Direct Hardware Instruction Mapping:
  • On modern 64-bit architectures (x86-64 and ARM64), operations on int128_t map directly to pairs of native CPU instructions using carry/overflow flags (adcq, sbbq, mulq, umulh).
  • OP_ADD, OP_SUB, OP_MUL, OP_DIV, OP_MOD, OP_NEGATE, OP_ABS execute in nanoseconds without arbitrary-precision heap overhead.
  • High-Precision Financial Math & Scale:
  • 128-bit signed integers support values up to $\pm 1.7 \times 10^{38}$ ($\pm 2^{127}-1$).
  • Fully accommodates multi-asset automated market makers (AMMs), constant-product formulas ($x \cdot y = k$), loan collateralization ratios, and high-frequency compound interest without intermediate truncation or integer overflow.

3.7. Multi-Precision Math & Cryptographic Primitives

To empower smart contracts to compute arbitrary zero-knowledge proofs and cryptographic curves without requiring network hardforks:

3.7.1. Integer & Curve Arithmetic Opcodes

  • OP_MUL (0x95): 128-bit signed multiplication with explicit overflow checking.
  • OP_RAWLEFTBITSHIFT (0x98): Raw bitshift on byte vectors. A positive shift count shifts left; a negative shift count shifts right!
  • OP_MULPOW2 (0x99): Computes arithmetic power-of-two scaling ($x \cdot 2^k$ for $k > 0$, or $x / 2^{|k|}$ for $k < 0$).
  • OP_ADDCARRY (0xb4): Multi-precision add with carry. Pops $(a, b, c_{in})$, pushes $(sum, c_{out})$ where $c_{out} \in \{0, 1\}$.
  • OP_SUBCARRY (0xb5): Multi-precision subtract with borrow. Pops $(a, b, b_{in})$, pushes $(diff, b_{out})$ where $b_{out} \in \{0, 1\}$.
  • OP_MUL128_WIDE (0xb6): Full 128-bit $\times$ 128-bit $\to$ 256-bit unsigned wide multiply. Pops $(a, b)$, pushes $(prod_{high}, prod_{low})$.
  • OP_LOG (0xbd): Fixed-point base-2 logarithm using the Turner algorithm.
  • OP_SQRT (0xbe): Integer square root ($\lfloor\sqrt{x}\rfloor$).

By chaining OP_ADDCARRY, OP_SUBCARRY, and OP_MUL128_WIDE, user-space contracts can implement 256-bit (secp256k1, secp256r1, Ed25519) and 384-bit (BLS12-381) field arithmetic directly in Script.

3.7.2. Cryptographic Hashing & Signature Verification

  • OP_BLAKE3 (0xbf): Single-pass BLAKE3 hash ($\approx 12\text{ ns}$).
  • OP_SHA256 (0xa8): Single SHA-256 hash.
  • OP_HASH256 (0xaa / OP_SHA256D): Double SHA-256 for Bitcoin cross-chain header verification.
  • OP_CHECKSIG (0xac): Evaluates 64-byte Schnorr signatures (BIP340) by default, or 64-byte compact Low-S ECDSA.
  • OP_CHECKDATASIG (0xba): Verifies an arbitrary message hash against a public key.
  • Multi-Curve Algorithm Parameter: Evaluates a curve parameter byte on stack:
  • 0x00: secp256k1 (standard Bitcoin/Lotus curve)
  • 0x01: secp256r1 (NIST P-256) — Native support for Apple Secure Enclave (FaceID / TouchID), Google Titan M, and WebAuthn / FIDO2 Passkeys! Allows non-custodial mobile spending without seed phrases.
  • 0x02: Ed25519 — Fast Edwards-curve signatures for cross-ecosystem attestation.
  • OP_MERKLEVERIFY (0xbb): Verifies Merklix branch inclusion/exclusion proofs on stack against a state root.

3.9. Bounded Primitive Recursion (OP_ENUMERATE), Loop Depth ≤ 2 & Static Precomputed Cost Budget

3.9.1. Termination & Resource Bounds

A finite execution bound and an affordable validation budget are separate requirements. General loops can be bounded by runtime metering, but may require execution before their resource consumption is known. Lotus v2 uses structured, bounded enumeration so validators can compute a conservative cost bound before execution. Invalid transactions still consume parsing and validation resources; bounded loops alone do not eliminate mempool denial of service.

3.9.2. Primitive Recursion via OP_ENUMERATE

Lotus v2 restricts loop control flow to bounded enumeration through the OP_ENUMERATE opcode family:

  • Strict Physical Bounds: Loops can only iterate over physically bound quantities:
  • OP_ENUMERATE_INPUTS: Strictly bounded by tx.vin.size().
  • OP_ENUMERATE_OUTPUTS: Strictly bounded by tx.vout.size().
  • OP_ENUMERATE: Strictly bounded by integer $N \in [0, 256]$ popped from the stack.
  • Auto-Pushing Loop Index: On each iteration, the interpreter automatically pushes the current zero-based loop index ($i = 0, 1, \dots, \text{bound}-1$) onto the evaluation stack. In 95% of covenant loops, the body immediately consumes this index (e.g. OP_OUTPUTVALUE or OP_UTXOVALUE), eliminating index arithmetic overhead. If the index is not needed, the body opens with OP_DROP (1 byte).
  • Controlled Nesting (Depth ≤ 2) & Flat C++ Call Frame: Loop nesting MUST NOT exceed depth 2 (SCRIPT_ERR_MAX_LOOP_DEPTH_EXCEEDED). All combinations of input, output, and generic enumeration are permitted within this depth, including input × output, input × input, output × output, and generic × transaction loops. Covenants may require these combinations to compare input and output relationships. The $256 \times 256 = 65,536$ bound applies only to a pair of generic loops. Transaction enumerations use the validated transaction counts: an input × output loop has $I \times O$ inner iterations, where $I = \text{tx.vin.size()}$ and $O = \text{tx.vout.size()}$. There is no blanket 65,536-iteration limit. Loop nesting is bounded by two; total permitted work is bounded by the consensus resource budgets in §3.9.3. The node interpreter maintains loop state in a fixed-size array on the C++ stack: ``cpp struct LoopFrame { uint32_t index; uint32_t bound; const uint8_t *pc_start; const uint8_t *pc_end; }; LoopFrame loop_stack[2]; uint8_t loop_depth = 0; // Invariant: 0 <= loop_depth <= 2 `` Loop-frame management requires no dynamic heap allocations or recursive function calls; this does not bound allocations performed by script operations.
  • Multi-Level Early Exit (depth OP_BREAK): OP_BREAK pops a 128-bit integer depth from the evaluation stack ($1 \le \text{depth} \le \text{loop\_depth}$):
  • OP_1 OP_BREAK: Terminates the innermost loop, jumping past its corresponding OP_ENDENUMERATE.
  • OP_2 OP_BREAK: Unwinds both the inner and outer loops simultaneously in a single $O(1)$ jump past the outer OP_ENDENUMERATE.
  • If $\text{depth} < 1$ or $\text{depth} > \text{loop\_depth}$, script execution immediately aborts with SCRIPT_ERR_INVALID_BREAK_DEPTH.

3.9.3. Conservative Static Cost & Aggregate Resource Budgets

Before executing scripts, validators MUST compute a deterministic, conservative upper bound in abstract consensus cost units, never measured CPU cycles or elapsed time. The bound need not equal the exact worst-case execution cost. Input/output loop bounds come from validated transaction counts; generic loops use the conservative maximum of 256, including when their actual count is determined at runtime.

For one input × output loop, the structural charge is: $$C_{I \times O} = C_{\text{outer setup}} + I\left(C_{\text{outer iteration}} + C_{\text{inner setup}} + O\,C_{\text{inner iteration}}\right)$$

Iteration charges include index pushes, loop control, and all body operations. Sequential constructs add their charges; conditional alternatives use a conservative bound covering either alternative plus condition evaluation. Nested constructs are charged recursively without counting a body twice. OP_BREAK and other early exits MUST NOT reduce the static bound. All bytecode MUST be structurally decoded, with matching control-flow delimiters and nesting limits checked even in regions that may not execute.

A structural cost pass can run in $O(\text{script\_size})$ using fixed opcode charges or conservative operand-size bounds from consensus limits. It MUST NOT require executing the script to discover a tighter bound. Every opcode requires a defined charge or upper-bound formula, including operand-dependent hashing, signatures, byte-vector operations, and introspection. The cost model MUST satisfy: $$\operatorname{ActualChargedWork}(E) \le \operatorname{StaticBound}(E)$$ Increasing an allowed iteration or operand-size bound MUST NOT decrease the estimate. All cost additions and multiplications MUST use checked arithmetic; overflow or exceeding the applicable budget causes rejection before script execution.

Consensus MUST enforce both aggregate limits: $$C_{\text{tx}} = C_{\text{wire and parsing}} + C_{\text{non-script validation}} + \sum_{\text{required branch invocations}} C_{\text{branch}} + \sum_{\text{mint invocations}} C_{\text{mint}} \le \text{MAX\_TX\_COST}$$ $$C_{\text{block}} = C_{\text{block validation overhead}} + \sum_{\text{transactions}} C_{\text{tx}} \le \text{MAX\_BLOCK\_COST}$$

The accounting MUST cover proof verification, all required script invocations, and other validation work. A per-input or per-script limit may supplement these limits but MUST NOT replace them. If each of $I$ inputs executes an input × output scan, the transaction includes $I^2O$ inner iterations; every invocation is charged even when bytecode or arguments repeat.

Consensus charges MUST be independent of cache hits, batch verification, execution order, and other implementation optimizations. Independent consensus limits MUST bound wire sizes, counts, proof lengths, stack depth, stack-element sizes, and total VM memory. Parsers MUST enforce length and count limits before allocating from untrusted declarations. Over-budget transactions are rejected before script execution, but parsing, cost analysis, and rejected submissions still consume resources; local admission controls remain necessary.

Genesis blocker — parameters and semantics remain to be finalized: MAX_TX_COST, MAX_BLOCK_COST, the complete opcode and validation cost schedule, resource-limit values, and structured control-flow semantics MUST be fixed and tested before Block 0. This section establishes the required model; it does not supply calibrated numerical limits or constitute a completed resource-soundness proof.

4.2. State Commitments & Sub-Second Crash Recovery

The Bitcoin Core Failure Mode:

In Bitcoin Core, CCoinsViewDB in LevelDB is an uncommitted flat key-value store. If power fails during block write, LevelDB is left in an inconsistent state. Having no internal cryptographic root, Core prints "Corrupted block database detected. Please reindex", forcing a multi-hour rebuild from raw block files.

The Lotus v2 Recovery Guarantee:

  1. Every block commits to hashUtxoMerklixRoot.
  2. RocksDB commits an atomic batch at the end of each block: $$\mathbf{StateCommitment} = (\text{blockHeight}, \mathbf{hashUtxoMerklixRoot})$$
  3. On Startup / Reboot:
  4. The node reads the tip header's expected hashUtxoMerklixRoot.
  5. It checks its local database root pointer. If clean: LocalRoot == Header.hashUtxoMerklixRoot. The database is cryptographically proven uncorrupted in $< 1 \text{ second}$.
  6. If power failed mid-write: RocksDB rolls back to the previous block's committed root ($H - 1$) and replays the single missing block from blk*.dat.
  7. Zero full reindexing is ever required.
