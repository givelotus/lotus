Review handoff — October 9, 2026 (updated October 14, 2026)

The design is ready to begin isolated candidate implementation. It is not ready to freeze genesis. Start with I01 workspace routing and I02 independent reference semantics; investigate the historical v1 sync obstruction in parallel once its evidence is available. The V2 daemon uses its dedicated ABC-based series with selective verified V1 ports; see the restored implementation and launch plan for source routing, miner requirements and genesis gates.

October 14 specification corrections

The maintainer selected Avalanche-controlled payouts using ABC's staking-reward machinery; treasury-contract alternatives are removed. P06 distinguishes existing parking behavior from hard consensus and records outstanding network-profile choices. P05/C14b specify 1,000 atoms per decimal kB, with coinbase/envelope charges deducted from reward. All block work is charged, and frozen accounting costs alone update the monetary EMA; future opcode assignments may tighten enforcement without changing accepted state roots. P03 groups opcodes by function, backed by tools/opcodes.json; earlier draft bytecode and dependent commitments must be regenerated. Genesis initializes monetary state unchanged, with zero native issuance; height 1 executes issuance step 0.

Coinbase now has zero or one opaque vanity/extranonce payload, retained in both identities and never executed. Its parent/height fields remain context-validated. P06/rationale document Frank burn demand and conditional calibration; they do not select a dollar peg or freeze issuance parameters.

Principal proposals to review

  • Recursive header groups and pure tagged BLAKE3 PoW (D12): preserve v1's compact partial-header rationale while unifying the entire protocol on tagged BLAKE3 (H_headerbody, H_headerwork, H_blockid in P04; memory-hard/GPU-specific PoW rejected). P04 specifies 134 bytes, a StateRoot commitment, no epoch/lucky-block pointer, and v1's 64-bit nonce and 48-bit timestamp. The 64-byte linkage and 82-byte work disclosures are exact candidate sizes.
  • Explicit signed intent and $O(1)$ sighash preimages (D01, D04): P01 defines transaction framing, Merkleized core/full identities (TxID and TxHash over 112-byte header+roots preimages with scripts and proofs in InputsRoot and only witness arguments excluded), hard output caps (MAX_OUTPUT_BRANCHES = 16, MAX_OUTPUT_PATHS = 16, bounding every Output to $\le 812\text{ B}$ and every Coin to $\le 868\text{ B}$), a 41-byte SpendSelector binding (input_index, branch_index, Leaf(script)), and fixed-size signing preimages across all three modes (00, 01, 02) using CoinsRoot, OwnInputHash(i), and OutputsRoot / OutputLeaf(i) so every signature check hashes at most 4 BLAKE3 blocks in $O(1)$ time.
  • Typed commitments and 56-byte MonetaryState (D02, D13): P02 distinguishes unordered branch membership, bottom-up indexed binary Merkle trees (IndexedTreeRoot over merkleidx for InputsRoot, FullInputsRoot, OutputsRoot, CoinsRoot, and in-contract maps), ordered block transaction inclusion, and a compact single-leaf-collapsed sparse UTXO tree (~27 hashes per key/proof at $10^8$ coins). StateRoot commits the canonical 56-byte MonetaryState record (bootstrap_reserve:u64 || tail_subsidy:u64 || prev_work:u256 || ema_block_cost:u64; D11 selects Avalanche-controlled payouts without treasury state).
  • Closed VM (D07, D15): P03 specifies 215 assigned opcode bytes and 41 OP_SUCCESS_N bytes, arithmetic, structured loops, branch continuation (OUTPUTCONTINUESBRANCH), multi-hash (hash_alg in 0..3) Merkle root verification/update (MERKLEROOT_SORTED, MERKLEROOT_INDEXED) and signature profiles. No opcode reads block height, block time or global UtxoRoot, so a script's result cannot change as blocks arrive (C22a); input × output loops remain permitted.
  • Unified Cost Units (cu), parabolic cost curves, and additive issuance (D08, D10): P05 unifies wire bytes (1 byte = 1 cu), hashes, signatures, and static VM charges into $L(\text{tx})$, replacing arbitrary MAX_TX_BYTES and MAX_BLOCK_BYTES walls with a parabolic transaction cost $C_{\text{tx}} = L + ((L^2) \gg S_{\text{tx\_knee}})$ and a parabolic block fee-burn floor against ema_block_cost $E_n$ enforced via C16's 50% fee burn. P06 specifies the 6-decimal denomination (1 XPI = 10^6 atoms, 2-decimal UI display with 4 hidden sub-cent decimals) and the additive block subsidy $S_n = B_n + T_n$ active from Block 1, combining the exact-telescoping bootstrap reserve $B_n = \max(1, R_n \gg 20), R_{n+1} = R_n - B_n$ ($\sum B_n = R_0$) with the integer work-responsive tail $T_n$.

Production blockers that remain real

The decision register owns the complete list. With structural formulas specified for D08, D10, D12, and MonetaryState, the remaining launch blockers are confirming the candidate shift/initial constants ($k_{\text{boot}} = 20, B_0 = T_0 = 250{,}000\text{ XPI}, R_0 = 2^{20} B_0, S_{\text{tx\_knee}} = 17, w = 10, E_{\min}, S_{\text{linear}}, S_{\text{quad}}$) via simulation and hardware benchmarks, freezing future-time eligibility and primitive cu weights, and generating independent parser, signature, VM and state conformance vectors.

Timestamp truthfulness is still an economic research question. P06 defines the objective and feasible-history analysis needed to compare mobile and persistent miners; square-root issuance plus decay is not presently established as a truthful-timestamp mechanism. The paper has not been changed by this planning pass.

Evidence and limits

The small structural model checks framing, hashing, tree proofs, header sizes, 56-byte MonetaryState / StateRoot commitments, telescoping bootstrap reserve conservation, parabolic transaction/block cost curves and selected integer algorithms. It records its own source and six packet digests. Those results are construction checks from one model, not independent consensus review or signed-payment validation. The validation ledger separates these from unrun daemon, live-sync, monetary and performance gates.

No daemon build, patch replay, live-network operation or benchmark was attempted. The faster-machine handoff and bounded implementation contracts describe the next execution steps. No external tickets or changes have been published.
