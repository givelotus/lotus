Lotus V2 peering implementation milestones

Status: implementation plan for review, 2026-10-15. The peering candidate is the protocol contract proposed here. The maintainer selected ABC TCP first, QUIC second, new development netmagic and Lotus port defaults P2P 10605, RPC 10604. This plan authorizes no node launch, production parameter freeze or network-code implementation before the specification review gate.

Baseline: monorepo 8914db5177d7b97fa7aa7d04172f71ead633775c; native ABC 1fb7db17c176cdea8a2c60d887891589382ee4e3 plus 57 patches 000–056, native commit 6a7849b1887bfe814c4e1679d7e01ffedb9a52d8, tree 9a3e3e57aa6ee0c0430144ee1200ab9cbe48f6e7. All work belongs on the V2 development branch and isolated replay/build trees. Chronik stays off for these milestones. Preserve V1 workspaces, nodes, data, main checkout, tags and releases.

Review gate before implementation

  1. Review N01–N08 in the peering candidate, specifically message layouts, identity negotiation, full TxHash retrieval, compact reconstruction, the P05 transport-size mismatch and scoped receive-limit negotiation. Record accepted allocations and unresolved changes in a follow-up review; do not silently edit P01–P06 to make a network test pass.
  2. Review the concrete separate development profile proposal, including its reproducible complete genesis, first-block budget and test-only cost schedule. The current fixture's time 0x010203040506, bits 0x1d00ffff, previous work 9 and header-only empty body do not establish a usable network. Derive and test valid complete genesis/first-block examples, including resource charges, with separately selected test parameters. Preserve D10–D14 mainnet choices as open; the selected port defaults do not resolve them.
  3. Reconcile native validator/chainstate conformance findings from the separate compiler/native audit. Require one deterministic validation path, atomic persistent state/undo and explicit unsupported-stage failures. Network parsing must not be added ahead of a validator that can safely reject and connect peer-supplied blocks.

The specification can be reviewed now. A runnable development-network claim must wait for gates 2 and 3 as well as the TCP acceptance below. No existing passing fixture, compiler test or native primitive build is sufficient evidence of network readiness.

Follow-on milestones — commitment-based state sync and hostile suppliers

Maintainer request (2026-10-15): implement these after the existing V2 chain and local testnet work. They are important long-term synchronization capabilities, not prerequisites for the first working network. No snapshot protocol, proof encoding, default mode or Avalanche policy is selected by this plan.

The primary threat here is availability after selecting a tip and state root: peers repeatedly send invalid UTXO subtrees or stall to prevent a new node from finishing synchronization. The proposed mode uses the enclosing PoW/Avalanche tip selection policy; specifying and implementing that policy remains separate. This plan does not claim that the current V2 runtime already implements Avalanche.

STATE-01: opt-in state bootstrap and historical backfill

Provide an explicit, non-default mode that imports state authenticated to the selected header commitment and can then obtain earlier chain data in the background. Expose the exact selected BlockID/height/root and profile, source policy and current verification status. Review whether explicit supplier nodes are required or merely configurable; no implicit trusted supplier list is added. Snapshots must bind the complete required state, including coin metadata and the monetary envelope committed by the header, rather than UTXO values alone.

Historical blocks may be downloaded backwards from the selected tip. Execution validation still follows parent-to-child dependencies from an authenticated starting state, with separate progress reporting. This is a secondary assurance track; it must not obscure the primary hostile-supplier availability goal. Persist verified state-import progress and provide explicit interruption, selected-root change and restart behavior without mixing roots or generations.

STATE-02: authenticated subtrees from multiple suppliers

Use the existing authenticated UTXO tree commitment as the anchor. Review a bounded manifest/proof format that authenticates subtree hashes and key/prefix coverage to that fixed root, so request identity is independent of a supplier. It must detect omitted ranges, overlapping coverage, duplicate leaves and noncanonical encodings as well as changed coins. Do not silently change tree ordering, header roots or P02 proof formats to implement transport.

Verify each bounded response before admitting it to the imported state. Retain verified subtrees across retries and restart; invalid responses cannot erase valid progress. Split requests among peers, cap outstanding work and proof processing, enforce fixed deadlines, and retry stalled or corrupt ranges with alternate suppliers. Peer rotation/reconnection must not reset global admission budgets or earn unlimited retries. A peer must not indefinitely own a range. Local capacity refusal remains operational and is not evidence of poisoned data.

Multiple suppliers improve availability; their agreement is not the proof. Every accepted chunk must independently authenticate to the selected root. Resource bounds must include decoding, verification, queued bytes, disk writes and restart bookkeeping, with fair scheduling for honest responses during spam. Selection of a different tip must explicitly reconcile or retire the old import; reuse is permitted only where authenticated subtree hashes remain identical.

STATE-03: verifiable poison evidence and relay research

Investigate compact evidence of a malformed response, invalid subtree or invalid claimed transition. Separate evidence about bytes from attribution to a supplier: an independently invalid payload alone does not prove which peer sent it. Review whether signed response commitments or another attribution mechanism is needed before any transferable accusation can affect peer selection. Do not add a broadcast message or automatic peer punishment until evidence encoding, verifier cost, replay scope, attribution and false-accusation resistance are specified.

A timeout, unavailable subtree, local resource limit or unverifiable allegation is not a cryptographic poison proof. Evidence must identify the exact chain, selected root, requested subtree and offending claim, and recipients must verify it independently under bounded work. Proof gossip must itself resist flooding. Do not promise that every failure has a succinct transferable proof.

Acceptance evidence

Demonstrate sync completion and continued verified progress with honest suppliers available while hostile peers send corrupt proofs/subtrees, withhold ranges, trickle bytes, reconnect and equivocate. Test mixed-root responses, malformed coverage, oversized/computationally expensive proofs, exhaustion and restart. Measure completion time, wasted bandwidth, verification CPU, peak retained memory and disk use under named hardware, chain-growth and adversarial-load conditions. State the honest-connectivity and resource assumptions; full eclipse or saturated resources cannot be treated as a successful availability test.

Also measure sustained validation/import throughput against new-chain arrival rate. A fast initial snapshot alone does not establish that a node can keep up or finish historical backfill. The milestone must report which operating envelope allows catch-up and continued operation, rather than only a small static-fixture success. These requirements remain deferred while baseline node integration is completed.

Required adversarial corpus and handoff

Use independent serializers/reference fixtures for the 134-byte header, P01 TxID/TxHash, ordered block root, complete block framing, compact selector and receive-limit negotiation. Include valid baselines before each negative mutation. Exercise 252/253 CompactSize boundaries, exact limits, overflow and truncation, with no allocation based solely on an untrusted count. Compact tests must force collisions deterministically rather than wait for random collisions. Compare full-block fallback against independently validated bytes.

Transport tests must cover late responses after timeout/reorg, wrong peer/BlockID, half-open connections, repeated variant spam, unavailable/pruned bodies and failure midway through persistent commit. Measure peak memory/disk usage and fairness during the largest supported object retrieval; P05's absence of a consensus byte cap does not eliminate local resource constraints. Prove refusal is recoverable and does not permanently reject a valid header or transaction.

Each handoff records changed source paths, protocol revision, parameter/genesis artifact digest, exact replay tree, test commands/results, known limits and remaining decisions. Preserve per-milestone acceptance: working TCP does not imply working QUIC, isolated development synchronization does not imply V1 interoperability, and either transport says nothing about finalized D10–D14 production parameters.

This documentation-only change must run docs/lotus-v2/tools/spec_candidate_checks.py using the existing isolated compiler-review Python environment. That checker verifies existing candidate fixtures/registry consistency; it does not validate this new peering protocol or implement its tests.
