Additional actionable source findings after foundation review

V04 — repeated whole-transaction preparation (demonstrated source complexity, no timing claim). P01 “Exact CHECKSIG message”, paragraph beginning “Every SigMessage preimage”, requires the transaction/coin commitments to be computed in strictly linear transaction-plus-resolved-coin bytes, followed by constant-size per-signature hashing. In final src/lotus_v2/vm.cpp around1586–1614, every contextual EvaluateVmCharged creates a new PreparedSigningContext and calls PrepareSigningContext before success scanning. ordinary_validation.cpp invokes that entry point for every input witness. Preparation traverses/encodes the full transaction, computes all identities/coin roots/own-input hashes and verifies every input's memberships. For n constant-size spending inputs with one trivial witness each, whole-transaction work is repeated n times, producing quadratic preparation work before any signature opcode. ApplyDerivedFieldSizes additionally traverses all coins/outputs per invocation. Existing caching only reuses preparation for opcodes within one invocation; it does not establish transaction-wide linear preparation. The connector preview plus ApplyOrdinaryCandidate repeats ordinary validation again, multiplying this work without changing its asymptotic form.

VM/signing owner: authenticate a reusable immutable prepared transaction context once at the ordinary validator boundary, including commitments/memberships/field-size vectors, then bind each invocation without recomputing unrelated inputs. Preserve direct standalone API authentication and stale-context rejection. Add an instrumented work-count regression across increasing input/branch counts and repeated CHECKSIG/SIGHASH; independently preserve both signature correctness and P05 charges. A host-time benchmark can supplement a deterministic counted-work test. Do not fix this by bypassing outer membership on OP_SUCCESS or merely caching one signature within an invocation. Finding sent to root and VM owner before implementation.

S02 — header store rejects complete block size (demonstrated restriction). P04 “Concrete recursive candidate” defines header size as exact complete encoded block length including header, count and transaction frames. persistent_header.cpp DecodeHeaderBytes around106 and Commit around464 reject header.size != HEADER_SIZE, i.e. anything other than134. The store format stores134 header bytes, but that is different from the header's declared full-block size. Therefore the existing store cannot persist a header for a real nonempty complete block. Later durable/daemon integration owns adapting semantic validation while retaining fixed134-byte header framing, and a store/reopen fixture with a valid full-block size greater than134. Existing header-only fixtures must remain explicitly scoped. Finding sent to root and header owner.

H04 — ASERT caller-profile validation (demonstrated API permissiveness; repair underway elsewhere). 055 validates positive half-life and bounded target/powLimit, but does not reject nonpositive spacing or genesis target above powLimit. These are not failures of ASERT arithmetic under a valid profile. Contextual profile must require positive spacing and a canonical accepted genesis target. Root reports the header owner has already added these validations in its separate candidate; this audit changes no source and does not count the pending candidate as merged evidence.

M03 — token units counted as native explicit burn (demonstrated arithmetic path). In029 monetary.cpp, AccountValidatedOrdinary unconditionally adds every output value to total_outputs, and every IsBurn value to explicit_burn, including outputs with HasToken. It reconstructs native_inputs = effects.native_fee + total_outputs, so fee subtraction still yields the expected native fee; fee-only tests can miss the error. AdvanceMonetary subsequently subtracts the supplied explicit_native_burn from spendable_supply_delta, so burning q token units spuriously subtracts q native atoms. This contradicts C04's asset distinction, C14's separate native/token sums and P05/P06 native monetary accounting. Monetary owner must derive native aggregates only from outputs without HasToken; test a signed/validated mixed transaction with a token-burn output and assert adapter native fields plus native supply delta against independently resolved coins. Reported immediately to root/monetary owner. No runtime execution or measured impact asserted by this source audit.
