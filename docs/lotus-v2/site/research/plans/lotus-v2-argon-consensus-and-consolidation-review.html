Consensus findings

1. Reserving 256 state-tree levels is intentional development accounting

Disposition: reject the proposed immediate consensus fix. Retain calibration work as an open design obligation.

P02, “UTXO map,” specifies a single-leaf-collapsed tree. Its typical depth near 27 for 100 million coins is an estimate; it also explicitly allows proof depth 0 <= k <= 256. Collapsing singleton subtrees does not bound every occupied split to 27. Shared prefixes can require deeper paths. A fixed expected-depth constant is not a worst-case bound.

P05, item 7 of transaction base cost, explicitly permits a conservative per-key charge. Its primitive weights and economic shifts remain subject to calibration. The development profile, section 3, explicitly selects conservative-block-cost-1 and gives its complete state-key formula:

h(n) = 1 + (n + 64)
state_key(n) = h(36) + h(33 + CompactSizeWidth(n) + n) + 256*h(67)

Here n is the serialized coin size. Native block_cost.cpp::StateKey and reference block_cost.py implement that formula. Native block_cost.h describes it as an abstract, uncalibrated development schedule. Neither requires the storage engine to materialize an uncollapsed tree.

Argon's displayed CostBenchmarkParams, state_lookup_step, and state_key_base are absent from the pinned code and the actual 069/071 payloads. The real type is BlockCostProfile {hash_base, hash_byte, resolve_byte, asset_comparison}. For unit coefficients the reserved branch component is 256*132 = 33,792 per key, or 101,376 for three keys; coin/key hashing is additional and depends on encoded size. The report's fixed 34,049 complete per-key total therefore does not describe this implementation. Its comparison with a launch-style L≈500 example establishes that this development profile is expensive, not a departure from its selected accounting rule. Its claimed 2^24 hard block-cost cap is not a selected parameter of this profile.

No code replacement is justified by this claim. A future calibrated candidate must specify a deterministic state-work bound, cover adversarial deep-prefix keys and insertion/deletion collapse, and reproduce costs across backends. Do not substitute 27, local cache state, measured I/O, or runtime work counters for the existing consensus charge. If a new formula is approved, implement it in both engines, regenerate profile artifacts and fixtures, and use a newly identified disposable development profile as required by its migration rules. Do not silently reinterpret an existing chain's cost/EMA state.

2. Squared comparison allowances are real and explicitly selected

Disposition: confirm the arithmetic consequence; reject classification as an unintentional current consensus divergence.

Native AuthenticatedTransactionCostsResolved adds (r*r + r + spends)*asset_comparison, where r=I+O. AuthenticatedEnvelopeCost adds (N*N+N)*asset_comparison. Both terms are explicitly documented in the development profile and implemented in the Python reference. P05 item 6 also requires bounded native/token aggregation and mint lookup; its subsequent paragraph explicitly rejects an expected hash-table bound as sufficient consensus reasoning. The report's claim that no aggregation term exists in P05 is incorrect.

The algebra has the consequence identified by the report: a base charge quadratic in r can produce a fourth-degree transaction effective charge after L + ((L*L) >> tx_knee_shift). An envelope quadratic in N can produce a fourth-degree block burn term after squaring block cost. For a fixed number of transactions whose individual fourth-degree effective costs dominate, squaring that block cost can even give eighth-degree dependence on transaction record count. These are statements about charged formulas before integer truncation, width limits and structural caps; they are not measured CPU complexity. The input/output caps in the development profile are 256 each.

monetary.cpp::TransactionEffectiveCost, BlockEffectiveCost and RequiredBlockBurn make these stages explicit. No implementation bug follows solely from the variable name “linear”: it means the base charge before the parabolic surcharge, and the selected profile deliberately reserves quadratic comparison work. The profile also acknowledges unpriced oracle bookkeeping and does not claim a calibrated resource guarantee.

Argon's suggested linear adjacent-TxID-order pass is not the actual decoder: block_wire.cpp::CompleteTransactionRoot uses a std::set<Hash> to reject repeated TxIDs while retaining block transaction order. DecodeBlockWire invokes that routine. A unique sequence need not be sorted by TxID. Removing this work on the premise that canonical ID sorting is already checked would change the wrong requirement.

A useful follow-up is a calibration proposal comparing the current bound with a specified deterministic comparison schedule, including mint/path lookups and block duplicate detection. Establish an upper bound and rounding/overflow rules before replacing any quadratic term. Test exact costs, transaction knees, block burn, EMA recurrence, minimal-block affordability, maximum allowed counts, and whole-block post-state roots in both engines. Keep this source change separate from consolidation and include an explicit new profile/migration decision. No production coefficient is proposed here.

7. Branch-query width differences implement the written semantics

Disposition: no VM semantic change; a small prose correction and stronger conformance coverage are justified.

P03 already distinguishes these cases:

Opcode Width rule with an otherwise valid context/index Evidence
dd UTXOREQUIRESBRANCH Non-32-byte root returns false P03 every-path predicate paragraph; native RequiresBranch; reference vm_context.requires_branch
e8 OUTPUTREQUIRESBRANCH Non-32-byte root returns false Same predicate and both engines
e9 OUTPUTEXCLUSIVEBRANCH Non-32-byte root errors P03 “root operand must be exactly 32 bytes”; explicit checks in both engines
ea OUTPUTCONTINUESBRANCH Non-32-byte root errors; requires a spend invocation P03 explicit “MUST be exactly 32 bytes, else error”; native ContinuesBranch and reference evaluator

The dd/e8 predicate is true iff the root is exactly 32 bytes and the other conditions hold. Existing native test_vm.cpp also explicitly checks the e9 width failure. Both engines therefore agree on the relevant acceptance behavior; the asymmetry is not evidence of an accidental implementation mismatch. Changing dd/e8 to error would invalidate programs that handle their false result. Changing e9/ea to false would permit programs currently rejected. Neither belongs in a history cleanup.

The two prose occurrences of OUTPUTCONTINUESBRANCH (cf) in P03's continuation and indexed-proof discussions should say (ea). The opcode table and engines already use ea; cf is CHAINID, contrary to the report's BIN2NUM statement. Recommended bounded follow-up: correct those two prose references, clarify that e9 malformed width errors, and qualify the burn-output false statement to valid operands/context so it does not appear to override width errors. Add a shared test matrix for root lengths 0/31/32/33, matching/nonmatching roots, spendable/burn outputs, invalid indices and spend/mint contexts. Compare acceptance and result values, without requiring identical diagnostic ordering when several operands are invalid. Run the spec candidate checker if editing P03, and update any document-digest artifacts through their prescribed generator.

Workstream B: separately reviewed changes

Consensus fixes, profile calibration, VM wording/tests, prototype retirement, shared-parser refactors, and removing audit JSON are separate changes with explicit final-tree deltas. They cannot be included under the exact-tree claim. They may be reviewed before consolidation, but then establish a new agreed baseline and record the separate delta before producing any consolidated series.

The prototype “unused” conclusion is too strong. The actual APIs are PersistentUtxoStore, PersistentMonetaryStore, PersistentHeaderStore, SealChildHeader and SealChildHeaderWithTxRoot, not several class names quoted by the report. Current block.h::ConnectOrdinaryBlock exposes optional store arguments and block.cpp has storage/rollback paths. Existing callers include test_block_store.cpp, test_block_monetary_store.cpp, test_block_seal_store.cpp, test_block_dev_coinbase.cpp, and the dedicated persistent-store tests.

The integrated CMake file explicitly registers check-lotus-v2-persistent-utxo, check-lotus-v2-persistent-monetary and check-lotus-v2-persistent-header. It also links the retained block.cpp oracle and prototype storage dependencies into disk/reorg tests. Standalone block_test, block_seal_test and persistent_header_test projects exercise additional seal/store paths. At this pin, lotus_v2_validation itself does not list block.cpp or the prototype stores as production source; the report's claimed production-library linkage does not match the current CMake file.

A retirement owner must first enumerate all symbol/include/build/script users and identify which tests provide independent oracle or crash/undo coverage. Migrate valuable coverage to the current transition/LevelDB implementation or retain an explicitly test-only oracle, then remove obsolete APIs, callers, targets and files together in a reviewed source-change commit. Verify the replacement tests and full registered suite; provide the before/after coverage mapping. “Not used by the node” is insufficient proof that deletion is free. Likewise audit JSON with no build reader can still be review evidence; archive or relocate it with provenance only after checking repository/tool references.
