Lotus V2 consolidation ownership and dependency ledger

Status: review candidate; ownership complete; construction and bisectability unproved. This is a docs/data design artifact from monorepo 9ab0c7c783de2fbc881fe9e90ae34c74ed5262f7. No patches, source, active manifest, nodes or published assets were changed. No builds or test binaries were run.

The machine-readable ledger maps all 318 mailboxes, 000–317, to 51 proposed topic commits. It records 1,051 original file diffs as 1,053 exclusive ownership units: almost all are complete file diffs; the three hunks of patch178's block_transition.cpp are individually assigned because template preview and complete-block validation are different features. Every original mailbox appears once in the source inventory. A mailbox may contribute different files to different topics; this is an explicit split, not duplicate application.

The immutable replay reference is v2-series-replay-317.json, base 1fb7db17c176cdea8a2c60d887891589382ee4e3, expected final tree a14a946342d31ee07ee8851906500746800b0c46. Original intermediate trees identify the source material; they are not expected trees for reordered topics. New boundary trees remain null until independently constructed and replayed. Native follow-ups absent from maintained000–317 are excluded even if a newer live checkout contains them. Extending this scope requires a new source pin, complete manifest/evidence hashes, ownership coverage and final-tree target.

Why 51, and what remains unresolved

The requested end state is self-contained, bisectable topic commits with their tests and build integration. The count follows those boundaries, not a fixed 58-commit target. Build-only and late repair mailboxes are folded into the feature whose behavior they complete. No prototype, audit artifact, test or binary fixture is deleted. The prior consensus/consolidation review explains why cost/VM semantic changes do not belong in this operation.

A first split produced 54 topics. Source inspection found that the proposed schema3 model/query/store/service boundaries were not self-contained: patch278 registers the model/query modules and changes store signatures used by patch280/281 consumers. Those four subdivisions are now one complete explorer topic, giving 51. It is large; a future finer split needs an explicit API/hunk plan and passing intermediate Rust/bridge tests before increasing the count.

The proposed semantic dependency graph is acyclic. This does not mean the original mailboxes can be applied in that order. Their exact shared-file context graph contains 17 backward edges and three strongly connected components. The full edges and affected ownership-unit IDs are recorded under unresolved. They identify rebase/context work, not proven semantic dependency cycles. No claim of clean replay, successful compilation or bisectability is made.

First candidate boundary and concrete conflict procedure

Begin with topic inherited: mailboxes000–006,173,253,255–257,260,310, 64 exact file-diff units, on the pinned ABC base. The JSON's construction_policy.first_boundary lists those unit IDs. In a new source checkout, apply only these selected deltas in original ordinal/file order, record context conflicts, and create one draft commit containing the complete inherited policy/mining/identity change and its assigned regressions. Do not apply later feature changes from the source replay. Its expected tree is not yet known. Capture the constructed tree and configure/build/test evidence before marking this boundary accepted.

The builder may save unvalidated draft commits while constructing the candidate, with every gate explicitly pending. That does not waive any intermediate gate or authorize promotion. Start implementation with this concrete first boundary rather than waiting to invent a guaranteed final count.

For each subsequent topic, preserve original ordinal/file/hunk order within its ownership set. If all changes to a path belong to the current prefix, its exact final blob is a safe construction shortcut; otherwise translate only the owned deltas. Record the source unit, original parent/result blob, rewritten context and resulting candidate blob. A three-way application is a tool for finding conflicts, not permission to import unowned future code.

Resolve the three context SCCs as follows:

  • Large native/shared-registration SCC: construct CMake targets from the already introduced source/link/guard changes, then rebase the owned source and fixture deltas onto that prefix. Use the enumerated backward edges as the work queue. If an owned hunk actually needs a future API, refine its explicit hunk ownership/dependency or merge the topics; do not add stubs or a new fix.
  • Client/submission SCC: construct171/172 with315's scoped flag-restoration class and call substitutions, run its descriptor regression, then add182's submission interface. Compare the final client blob and rerun the regression.
  • Avalanche-node/explorer-node SCC: compose startup/recovery, IBD and peer outcomes before adding schema3 namespace/token publication. Inspect overlaps in startup/poll/stop and authority calls. A real later-service dependency needs an explicit hunk reassignment or merged boundary; it cannot be hidden behind a provisional authority stub.

After resolving each SCC, update this ledger with the actual candidate trees and replay results. Context rewriting may change commit boundaries and messages; source semantics, every original change's ownership and the final tree remain fixed. An independent reviewer checks the conflict resolutions before accepting the candidate history.

Executable construction and verification contract

Construction is a later task in a new isolated checkout from the pinned ABC base. Preserve the current maintained series and replay evidence. Process topics in proposed_order, loading only their owned original file sections/hunks. Existing section_sha256, hunk_sha256, mailbox digest and source-tree provenance make that selection auditable. Recontextualizing a diff must preserve its owned behavior and final bytes; unresolved overlaps require review. Never substitute an entire final file with future-topic changes merely to make a patch apply.

Before finalizing each candidate commit, save its tree and actual target/test inventory and execute the applicable commands under verification_recipes and that group's verification. The recipes use explicit variables, not paths to production or someone else's active build. Required variables are SRC, BUILD, EVIDENCE, BUILD_TYPE, CHRONIK, PYTHON, JOBS, plus the exact standalone project/dependency paths. REFERENCE, MONOREPO and MANIFEST must identify the pinned reference/profile artifacts. Use fresh build/evidence directories for each boundary/configuration; same-boundary secp/ABC archives for standalone tests.

The final candidate matrix is Debug and Release, each with Chronik OFF and ON, wallet ON, plugins/Qt/seeder/ZMQ OFF, pinned Rust1.93.0 and Python<=3.13. Apply relevant matrix rows earlier when a boundary changes configuration dependencies; record the triggering dependency. Ordinary boundaries use one coherent Debug configuration: Chronik OFF before chronik_query, ON afterward. This defines the candidate review matrix; it makes no other-platform/plugin/GUI claim. Additional supported configurations remain explicit final gates, not implicit passes.

At every candidate commit:

  • Configure and record cmake --build "$BUILD" --target help and CTest JSON.
  • Build daemon, CLI, wallet tool and native tests; build the V2 wallet pilot/client when introduced. Run cumulative native suites check-bitcoin, check-bitcoin-upgrade-activated, check-avalanche, check-pow, check-secp256k1, check-univalue and check-leveldb. Run affected inherited regressions at the feature boundary that owns the behavior.
  • Run every cumulative V2 custom check-* target. CTest alone does not execute these custom targets. Run CTest separately.
  • Configure/build/run each cumulative standalone project and its registered CTest suite. Enable LOTUS_INITIAL_DOWNLOAD_NATIVE_AUTHORITY=ON for the real authority test; it is not covered by the default lightweight latch test alone.
  • With Chronik ON, run the registered CMake check-crates target using the exact generated CXX bridge and Python environment.
  • Run auxiliary VM/reference/FD/relay queue commands recorded in the JSON at their introduction, when covered code changes, and at final acceptance. Add the pinned node/process scripts' complete documented invocations and inputs to the relevant boundary record before acceptance. No node script is run by this docs-only task.

At the final candidate, run the complete inherited functional suite, including all registered variants, through check-all and check-upgrade-activated-extended, together with the complete native, Rust, standalone and custom-check gates across the required final matrix. Earlier configuration changes require the relevant configuration-dependent checks; repeat a full inherited functional suite earlier only when a concrete behavior risk justifies it. No exclusion, environmental failure or timeout counts as a pass.

Finally export the candidate and replay it in a second fresh checkout, comparing every recorded candidate boundary tree and the exact final tree above. Compare all blobs/modes, including patch033's binary fixture. Independently review the ledger, source attribution, all intermediate build/test evidence and equality. Do not replace the active manifest or publish merely because coverage/count validation passes. Source changes, prototype retirement, resource calibration and semantic fixes remain separate reviewed work.

Reproduce the docs/data validation

Run the following from the pinned monorepo root. It checks manifest/evidence hashes, all 318 mailbox records, every original file/hunk ownership unit, the proposed DAG, binary-section retention and registration references. It writes nothing and runs no builds or nodes.

from pathlib import Path
import collections
import hashlib
import json
import re

root = Path.cwd()
ledger = json.loads((root / "docs/plans/lotus-v2-consolidation-ledger.json").read_text())
digest = lambda data: hashlib.sha256(data).hexdigest()
manifest_path = root / ledger["source_manifest"]
evidence_path = root / ledger["replay_evidence"]
assert digest(manifest_path.read_bytes()) == ledger["source_manifest_sha256"]
assert digest(evidence_path.read_bytes()) == ledger["replay_evidence_sha256"]
names = [s for s in manifest_path.read_text().splitlines() if s and not s.startswith("#")]
evidence = json.loads(evidence_path.read_text())
assert len(names) == len(ledger["mailboxes"]) == 318
assert evidence["base"] == ledger["base_commit"]
assert evidence["final_tree"] == ledger["expected_final_tree"]
groups = {g["id"]: g for g in ledger["groups"]}
order = ledger["proposed_order"]
assert len(groups) == len(order) == ledger["proposed_group_count"] == 51
assert set(order) == set(groups)
positions = {g: i for i, g in enumerate(order)}
for gid, group in groups.items():
    assert group["proposed_position"] == positions[gid] + 1
    assert all(positions[d] < positions[gid] for d in group["depends_on"])
    assert group["result_tree"] is None  # This is an unexecuted design ledger.
units = {}
for n, (name, entry, recorded) in enumerate(zip(names, ledger["mailboxes"], evidence["entries"])):
    assert entry["ordinal"] == int(name[:3]) == n
    assert name == entry["mailbox"] == recorded["file"]
    raw = (manifest_path.parent / name).read_bytes()
    assert digest(raw) == entry["mailbox_sha256"] == recorded["sha256"]
    assert entry["original_result_tree"] == recorded["tree"]
    markers = list(re.finditer(rb"^diff --git a/(.+?) b/(.+)$", raw, re.M))
    partition = collections.defaultdict(list)
    for unit in entry["units"]:
        assert unit["id"] not in units
        units[unit["id"]] = unit
        parent = unit.get("parent_section_id", unit["id"])
        partition[parent].append(unit)
    assert set(partition) == {f"{n:03}:{j:02}" for j in range(len(markers))}
    for j, marker in enumerate(markers):
        end = markers[j + 1].start() if j + 1 < len(markers) else len(raw)
        section = raw[marker.start():end]
        if j + 1 == len(markers) and b"\n-- \n" in section:
            section = section[:section.rfind(b"\n-- \n") + 1]
        owned = partition[f"{n:03}:{j:02}"]
        for unit in owned:
            assert unit["path"] == marker.group(2).decode()
            assert unit["section_sha256"] == digest(section)
            assert unit["binary"] == (b"GIT binary patch" in section)
            assert unit["group"] in groups
        if owned[0]["ownership"] == "whole_file_diff":
            assert len(owned) == 1
        else:
            hunks = list(re.finditer(rb"^@@.*?@@.*$", section, re.M))
            assert sorted(u["hunk_index"] for u in owned) == list(range(len(hunks)))
            for unit in owned:
                k = unit["hunk_index"]
                stop = hunks[k + 1].start() if k + 1 < len(hunks) else len(section)
                assert unit["ownership"] == "hunk"
                assert unit["hunk_sha256"] == digest(section[hunks[k].start():stop])
assigned = [u for group in groups.values() for u in group["units"]]
assert len(assigned) == len(set(assigned)) == len(units) == 1053
assert set(assigned) == set(units)
for gid, group in groups.items():
    assert all(units[u]["group"] == gid for u in group["units"])
for edge in ledger["unresolved"]["patch_context_edges"]:
    assert edge["before_unit"] in units and edge["after_unit"] in units
    assert edge["order_reversed"] == (positions[edge["before_group"]] > positions[edge["after_group"]])
assert not ledger["unresolved"]["file_introduction_conflicts"]
binary = ledger["binary_preservation"]
assert units[binary["unit"]]["binary"]
assert units[binary["unit"]]["section_sha256"] == binary["section_sha256"]
assert binary["bytes"] == 6892
assert all(p["introduced_by_group"] in groups for p in ledger["registration_catalog"]["standalone_projects"])
assert all(c["introduced_by_group"] in groups for c in ledger["registration_catalog"]["lotus_checks"])
print("PASS: 318 mailboxes; 1051 file diffs; 1053 exclusive units; 51 proposed topics; source hashes and DAG valid.")
print("NOT RUN: candidate replay, per-boundary builds/tests, final candidate tree comparison.")

The source replay's CSV was also read by its exact Git blob and checked against the recorded SHA256/length during ledger preparation. No new candidate source or build evidence was generated. Independent review is required before treating this design as an approved construction plan.
