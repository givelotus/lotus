3. Core Architectural Choices & Why They Work

A. Storage Engine: libmdbx + 4-Level (16-ary) Jellyfish Merkle Tree Subtree Packing

  1. Why We Replaced LevelDB with libmdbx (ecash/003–004, v2/011):
  2. LevelDB's LSM-tree compaction causes unpredictable latency spikes and read amplification on random 32-byte UTXO/SMT keys.
  3. libmdbx (MDBX_WRITEMAP | MDBX_LIFORECLAIM | MDBX_UTTERLY_NOSYNC) maps the B+Tree directly into virtual memory, giving zero-copy std::string_view reads (RawGetView) and deterministic single-writer MVCC transactions without reader locks.
  4. Block bodies (blk*.dat) and undo data (rev*.dat) are stored in append-only flat segment files via pread/pwrite, keeping the libmdbx B+Tree compact and in RAM.
  5. Bit-Reversed Prefix Key Layout (v2/011, v2/027):
  6. In DiskStateStore (src/lotus_v2/disk_state.cpp), SMT node keys are stored as 'N' || ReverseByte(prefix[0..31]) || uint16_le(depth) so tree bit depth % 8 == 0 sits at MSB 0x80. Deep SMT ancestors that share a logical bit prefix also share a lexicographic byte prefix inside 4 KB libmdbx B+Tree pages.
  7. Lazy In-Transaction Node Cache (v2/027) & EraseAt Sibling Read Elimination (v2/029):
  8. During a block commit (CommitFinalizedOverlay), InsertAt and EraseAt mutate an in-memory unordered_map<Path, CachedNode, PathHash> node_cache with SetBranchLazy (marking digest_dirty = true without calling BLAKE3 UtxoNode on every coin mutation).
  9. EnsureBranchDigests() computes each modified internal branch's BLAKE3 digest once bottom-up right before FlushNodes().
  10. 4-Level (16-ary) Jellyfish Merkle Tree (JMT) Subtree Value Packing (v2/032):
  11. Problem: A binary Sparse Merkle Tree has up to 256 levels. Storing every binary depth d as its own separate MDBX key/value in dbi_smt_nodes caused 4–8 separate B+Tree page lookups and writes per leaf path.
  12. Solution (src/lotus_v2/disk_state.cpp): We group every 4 binary tree levels (anchor_depth = depth & ~3u, relative depth rel_depth = depth & 3u $\in \{0, 1, 2, 3\}$) into a 16-ary Jellyfish Merkle Tree (JMT) subtree pack containing up to $1 + 2 + 4 + 8 = 15$ binary nodes (slot = ((1u << rel_depth) - 1u) + rel_bits $\in [0..14]$) under a single 34-byte anchor key in dbi_smt_nodes: $$\text{Record} = \texttt{'J'} \;\|\; \texttt{uint16\_le(present\_mask)} \;\|\; \big[\texttt{uint32\_le(len)} \;\|\; \texttt{node\_bytes}\big]_{\text{slot} \in \text{present\_mask}}$$
  13. Consensus Invariance: On-disk packing is 100% transparent to consensus—UtxoNode(depth, left, right) still computes the exact same binary BLAKE3 hashes, so StateRoot and CoinProof are bit-for-bit unchanged.
  14. L1 Subtree Pack Cache & Write Coalescing: Walking 4 binary levels (d, d+1, d+2, d+3) performs 1 mdbx_get (at d & ~3u) and serves the next 3 levels from cached_jmt_views in L1 cache with zero allocations. On commit, all dirty nodes within a 4-level subtree coalesce into a single mdbx_put.

B. Speculative Mempool Overlay, Merklix Epochs & Set Reconciliation (ecash/005–010, 022–025, 035, 038, 040)

  1. How Merklix Epochs & Set Reconciliation Work Together:
  2. Rather than rebuilding a block template from scratch on getblocktemplate or shipping megabytes of raw txids between peers, every node maintains a Persistent Merklix Overlay Arena (src/lotus_v2/mempool_overlay.cpp) anchored at the current chain tip.
  3. Incoming transactions enter a lock-free/deferred pending buffer (ecash/038) and are periodically frozen into a deterministic Epoch (FreezeEpoch in ~21.9 ms).
  4. $\text{GF}(2^{64})$ Algebraic Sketches (ecash/006, 010, 022, 035):
  5. Each Merklix bucket/subtree maintains XOR/algebraic power-sum syndromes $(S_1, S_3, S_5)$ in $\text{GF}(2^{64})$ over key-salted 64-bit SipHash short IDs (short_id), accelerated via hardware carry-less multiplication (_mm_clmulepi64_si128 on x86_64 / vmull_p64 on ARM64 NEON).
  6. When two peers compare an epoch root:
  7. If their root hashes match, they agree on the exact transaction set in $O(1)$.
  8. If a bucket differs by $\le 2$ transactions, the receiver solves the quadratic syndrome polynomial $x^2 + S_1 x + (S_1^2 + S_3 / S_1) = 0$ in $\text{GF}(2^{64})$ in ~25 nanoseconds (Mysticeti 1-RTT Optimistic Fast Path, ecash/023) without even descending the tree!
  9. For larger differences, $D=3$ (8-way) sub-bucket summaries (ecash/022) pinpoint the exact missing short_ids in 1–2 RTTs.
  10. $O(1)$ Block Assembly & Speculative UTXO Cut-Through (ecash/007–008, 040, v2/017, 027):
  11. CTxMemPool maintains a speculative MempoolOverlayLayer with a flat open-addressed linear-probing Cut-Through Table (ecash/040): if Tx A creates output $O_1$ and Tx B spends $O_1$ in the same block/epoch, $O_1$ is cut through in memory so DiskStateStore only ever touches net-erased pre-block UTXOs and net-inserted unspent outputs.
  12. BlockAssembler::CreateNewBlock reads the pre-sorted transactions and pre-computed StateRoot directly from the frozen Merklix overlay in $O(1)$ (< 1 ms).

C. Why We Explicitly Dropped $\text{GF}(2^8)$ Cauchy Reed-Solomon (Turbine) Shredding

During Round 10 planning, we evaluated adding Solana-style $\text{GF}(2^8)$ Cauchy Reed-Solomon (txshred / blkshred) erasure coding and explicitly dropped it:

  1. Transport Mismatch (Reliable TCP vs. Unreliable UDP): Solana's Turbine uses $\text{GF}(2^8)$ Reed-Solomon shreds because it streams blocks over raw UDP where individual 1.2 KB packets are routinely dropped. Lotus V2 and eCash run over TCP alongside Merklix Set Reconciliation + MinedHeader Compact Relay (ecash/009, 033), where peers already hold >99% of transactions in their mempool overlay and only transmit a 134-byte MinedHeader + short-ID sketch delta.
  2. Erasure-Coding Poisoning / Computational DDoS Vector: On a permissionless P2P network without a single slot-scheduled leader signing every shred, a Merkle root alone only proves internal consistency with whatever tree an anonymous sender constructed—not that the parity shreds are valid Reed-Solomon linear combinations of honest data shreds. Adding stake-bound originator signatures and full-tree reconstruction checks over TCP adds complexity and CPU overhead with zero throughput benefit over MinedHeader + Merklix set reconciliation.

D. Mempool Ingestion & Memory Layout (ecash/024, 027, 032, 039, 042, 043)

  1. Firedancer-Style Pre-cs_main Parallel Transaction Pipeline (ecash/032, 042, v2/028):
  2. Before acquiring cs_main, worker threads decode raw hex transactions in parallel (ecash/032), warm GetId()/GetHash(), run context-free CheckRegularTransaction, and precompute BIP143/V2 sighash midstates (ecash/042), using a stack-allocated fast path (v2/028) that eliminates heap allocations on transactions with $\le 8$ inputs/outputs.
  3. One-Wave Chained Batch AcceptToMemoryPool (ecash/039, v2/029):
  4. Resolves in-batch parent-child transaction chains in a single pass using an in-batch output lookup map (PeekCoin) and $O(1)$ parent txiter linking, eliminating multi-wave retry loops on topologies with chained spends.
  5. TigerBeetle Portable ChunkedSlabAllocator (ecash/043):
  6. Replaces per-node ::operator new heap allocations in CTxMemPool::mapTx (boost::multi_index_container) and CTxMemPool::mapNextTx (indirectmap) with src/support/allocators/chunked_slab.h (16,384 slots/chunk + $O(1)$ intrusive freelist), eliminating allocator contention and pointer-chasing L3 cache misses under high mempool churn.

E. ConnectBlock & Signature Validation (ecash/018–020, 026, 050–052, v2/025–026)

  1. CCoinsViewCache::Reserve Pre-Allocation (ecash/050):
  2. Pre-reserves view.Reserve(block.vtx.size() * 4) in ConnectBlock and cacheCoins.reserve(cacheCoins.size() + cursor.GetDirtyCount()) in CCoinsViewCache::BatchWrite, eliminating 13 full unordered_map bucket rehashes per 2,000-tx block.
  3. Fused Single-Lookup SpendCoins + CheckTxInputsFromSpentCoins (ecash/051):
  4. Previously, ConnectBlock hashed and looked up every txin.prevout in CCoinsViewCache 3 separate times (CheckTxInputs, prevheights, and SpendCoins).
  5. Now ConnectBlock calls view.SpendCoin(txin.prevout, &txundo.vprevout[j]) once per input, then validates input maturities/amounts/fees (CheckTxInputsFromSpentCoins) and reads prevheights[j] directly from the contiguous txundo.vprevout vector in L1 cache—cutting UTXO hash table lookups in ConnectBlock by 3x.
  6. Anchored Speculative Overlay Hit in ConnectBlock (ecash/008, 052, v2/025):
  7. When an incoming block's transactions match the speculative mempool overlay anchored at pindex->pprev:
  8. Script/signature checks are satisfied in $O(1)$ from the pre-validated overlay (!prevalidated_overlay_sigchecks.empty()),
  9. Redundant prevheights + BIP68 SequenceLocks re-evaluations are skipped (ecash/052), and
  10. Redundant BIP30 disk lookups are skipped on height-committed V2 coinbases (v2/025).
  11. 16-Shard TLS SignatureCache & BatchSigCollector (ecash/018–019):
  12. Cache misses during parallel script verification are collected into lotus::v2::BatchSigCollector and verified via multi-scalar Schnorr batch verification with automatic FirstFailingIndex() binary-search fallback on invalid signatures.

F. Avalanche, P2P, Chronik & RPC Concurrency (ecash/013–014, 044–049)

  1. Avalanche Batch Schnorr Verification & Lock-Free Proof::verify (ecash/044–047):
  2. ecash/044: Hoists getStakeCommitment() out of the per-stake verification loop in Proof::verify.
  3. ecash/045: Batch-verifies all stake + master Schnorr signatures in Proof::verify and Delegation::verify via BatchSigCollector.
  4. ecash/046: Runs context-free Proof::verify outside cs_main in PeerManager::registerProofWithState, holding cs_main only for the fast CoinsTip() UTXO lookup (Proof::verifyUtxos).
  5. ecash/047: Coalesces incoming NetMsgType::AVARESPONSE bursts in PeerManagerImpl::ProcessMessages (ProcessAvaResponseBatch) and batch-verifies peer vote Schnorr signatures in a single BatchSigCollector::VerifyAll() call.
  6. Chronik Lock-Free entry_time & Dedicated Async Worker Queue (ecash/048–049):
  7. ecash/048: Captures entry_time synchronously in ValidationSignals and passes it directly to ChronikValidationInterface::TransactionAddedToMempool, eliminating 1,000 m_node.mempool->info(txid) LOCK(mempool.cs) acquisitions per batch.
  8. ecash/049: Offloads ChronikValidationInterface mempool callbacks onto a dedicated background worker thread + bounded FIFO queue (m_worker) with a synchronization barrier (FlushWorkerQueue) before block/finalization events so -chronik=1 never stalls the shared ValidationSignals thread.
  9. Boost.Asio Coroutine HTTP RPC + Lock-Free RCU Snapshots (ecash/013–014, 021, 037):
  10. Read-only RPCs (getblockchaininfo, getmempoolinfo, getrawmempool, getblocktemplate) read an atomic std::shared_ptr<const ChainAndMempoolSnapshot> published on tip/mempool updates with zero cs_main or mempool.cs locks.
