## Exact amount entry (2026-10-14)

- Financial amount conversion and formatting in `vase-client/lib/utils/currency.dart` must use decimal strings and `BigInt` base units, never `double`, `/`, or `BigInt.toInt()`. ## Restored arithmetic calculator (2026-10-14)

- The user requested the pre-redesign, Venmo-like arithmetic keypad. Restore its four-column digit/operator layout using the existing NumpadModel/View, not the old listener-based implementation or removed wallet/network code. The model owns the complete expression; providers and hooks own/dispose listeners and controllers. Same-total expression changes still notify and repaint.
- Operations evaluate **left to right**, matching the historical calculator: `8-2+3*4` is 36, not 18. This is a running arithmetic keypad, not a postfix stack editor or standard-precedence parser. Accept modern `− × ÷` buttons and historical `➖ ➕ ✖️ ➗` aliases. Pending operators replace one another; AC, backspace and equals are explicit controls.
- BigInt rational intermediates never round: `1/3*3` finishes as exactly 1 XPI. Incomplete expressions, division by zero, negative final values and results not exactly representable in six XPI decimals cannot transfer to payments; show the reason. Intermediate negative or fractional values may recover through subsequent operations. Equals collapses only a valid result. Zero is editable but Done requires a positive amount. Retain the existing 19-digit operand/6-decimal input limits, with a 256-character expression bound; these are editing bounds, not monetary consensus rules.
- Each amount sheet creates a fresh draft initialized with explicit base-unit-to-decimal conversion. Drafts survive rebuilds, cancel without updating either SendModel or request state, and dispose when the sheet closes. Done commits once; reopening starts from the committed decimal amount rather than a previous expression. Request state is route-local and may exceed the wallet balance; send validation still requires sufficient spendable balance (including existing headroom for fees). There is no listener/event-bus synchronization between these states.
- Scan and clipboard payment updates atomically replace address and base-unit amount, including clearing stale amounts when a URI has no amount. A fresh manual Send clears the prior payment. Request QR and copied URI both encode exact base units and do not mutate SendModel. Direct Receive opens without inheriting a prior calculator/request amount.
- Validation: all 99 Flutter tests pass (73 existing plus 19 arithmetic model and seven widget flow regressions); analyzer has zero errors and the same 528 inherited warning/info notices; production web build passes, and all 19 arithmetic regressions also pass in headless Chrome. Tests exercise rebuilds, identical totals/different expressions, draft cancel/reopen, scan/paste unit boundaries, zero-balance requests, duplicate Done events and compact layout. No real wallet, storage, camera, network or broadcast is involved. Native mobile builds/device interaction remain unverified because platform SDKs are absent.
