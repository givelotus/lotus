## Current ownership and contracts

`src/common/bloom.h:101–137` documents CRollingBloomFilter as probabilistic: contains must return true for the last N to 1.5N insertions, and may return true for never-inserted keys. Three half-N generations provide that retention. `bloom.cpp:215–246` rotates before the next insertion when the current generation fills, clears cells carrying the generation about to be reused, then inserts the new generation. Both generation planes and all counters/tweak are ordinary memory protected by caller synchronization. `reset` changes hash tweak, resets count/generation and clears all words. Bloom source is identical at the native tip.

Peer known-inventory filter is 50,000 entries / 10^-6 false-positive rate under `m_tx_inventory_mutex` (net_processing.cpp 511). The same mutex also protects pending inventory and Avalanche-stalled IDs. AddKnownTx inserts AND erases queued inventory under that lock; DrainRelayQueue queries it for all new-arrival/peer pairs; SendMessages queries/inserts it while deciding announcements. Merely making filter bits atomic cannot remove the enclosing consistency lock.

Other instances are not interchangeable: recently-announced inventory/proofs are guarded by g_msgproc_mutex; recent rejects and reconsiderable rejects by cs_main; recently confirmed transactions by their own mutex; address-known has its address relay/sending ownership. Reject filters reset when the tip changes (3796–3797); confirmed filter resets on BlockDisconnected under its mutex (3599); address-known resets for a periodic self-announcement (10568). A global replacement expands the proof obligation to every caller and reset.

The global relay ingress is `vector<RelayQueueEntry>` under `m_relay_queue_mutex` (1600–1610). Entry is TxId + local-origin flag + monotonic queued timestamp, not a retained transaction body. RelayTransaction classifies unbroadcast status and updates the short-ID index, appends one record under the mutex, then sets m_txrelay_wake. RelayTransactionBatch classifies under one mempool view, indexes valid bodies, reserves/appends all non-null records under one queue lock with one timestamp, then wakes (3853–3897). Its batch append is contiguous relative to other producers. Neither void API has a capacity/rejection result or drops on overflow today.

MaybeDrainRelayQueue/DrainRelayQueue require g_msgproc_mutex, advance one global next-drain tick and swap the entire arrival vector under a short queue lock (4210–4230). That global consumer selects fanout, uses parent routes, updates per-peer inventory and route history. The scheduler only exchanges the wake flag and wakes message processing; it does not consume (3518 onward). Producer examples include ProcessValidTx while holding cs_main AND g_msgproc_mutex (5608 onward), forced relay, scheduled unbroadcast retry (2777), and RPC batch relay (rpc/mempool.cpp 1781). Native retains the same queue algorithm. Causal queue owner is `676af0e7933d29090e8ad64a1a8be989698a3d43`; tick owner is `f8750a3a1a2a387b98aa44cb6f19ed6a4cee22f4`.

## W3-9: generation clear/publish races

### Publish-before-sweep loses a fresh insert

1. Rotator publishes generation G as active before clearing G's old cells.
2. Inserter reads G, writes all of key X's atomic cells, and returns.
3. Rotator clears a cell containing G, including X's just-written data.
4. A later contains(X), with no subsequent N insertions or reset, returns false.

This violates recent-key retention even if every access is atomic and the publication uses release/acquire. A seq_cst store does not distinguish old and new occupants of the same reused generation label. A sweep based on stale word snapshots can also overwrite concurrent updates to unrelated bits in the same word. Plain load/modify/store on atomics is insufficient; CAS against the actual old value prevents some lost updates, but cannot distinguish equal generation-tag ABA by itself.

### Sweep-before-publish is insufficient without old-writer exclusion

A producer may capture a generation/bank and pause before writing. The rotator can clear/reuse that bank while the producer remains in flight. When resumed, the old producer can repopulate retired data or overwrite a new generation's cell/planes. With the existing 2-bit representation, independent plane atomics do not form an atomic generation tag: a reader or sweeper can observe a hybrid 01/10/11 label, and a delayed old writer can clear a plane set by a newer writer. Reusing labels 1,2,3 requires a real reuse/lifetime protocol, not an extra current-generation atomic.

Concurrent increments/reset of entriesThisGeneration have a separate race. Fetch_add followed by reset/store(0) can erase other reservations, undercount/overfill a generation, cause multiple rotations, or advance epochs too far. Fetch_add tickets alone do not define when a multi-hash insertion becomes logically present. Specify insertion/expiration linearization, whether overlapping operations may query either state, and how a delayed reservation remains safe. A writer that started before rotation/reset cannot silently contribute old tweak/epoch bits to a new logical filter after returning success.

Explicit reset is harder than ordinary turnover: changing tweak while clearing data allows a key to be hashed with mixed configuration; old in-flight inserts can repopulate reset state or write an obsolete buffer. Readers need a coherent immutable configuration identity (tweak, size, hash count, epoch/bank pointers); buffers must outlive every reader/writer using them. Atomic pointer publication does not provide reclamation, and atomic shared_ptr is not a portable lock-free guarantee. PeerRef/filter lifetime also has to outlive operations admitted before FinalizeNode; the existing FinalizeNode comment explicitly warns other PeerRefs can survive map removal. Constructor defaults and shutdown must not expose partially initialized arrays.

### Hash bucket/cell correlation and false positives

Current RollingBloomHash varies the seed per hash function. It takes cell bit from h's low six bits, and uses FastRange32 (upper-bit multiply/range mapping) for the bucket pair. That choice is explicitly documented at bloom.cpp 237–241. A proposed bucket = h % power_of_two_bucket_count AND cell = h % 64 reuses the same low bits. Many nominal bucket/cell combinations become unreachable, worsening effective capacity and false-positive behavior. Preserve distinct bit usage or derive sufficiently decorrelated keyed hashes; retain the configured hash-function count. “One atomic cell per hash” changes both memory cost and collision distribution, so validate sizing/FPR and cache pressure rather than importing the old formula unchanged.

There is no general no-false-positive promise for a Bloom filter: these callsites already accept a small probability of suppressing unnecessary/possibly useful requests or announcements, with explicit recent-reject rationale. A filter positive cannot become exact dedup, proof of mempool membership, or a replacement for TxId equality/request tracking. Conversely, the recent-insert no-false-negative retention promise matters: a newly inserted known/reject key must not disappear due to a rotation race. A concurrent query overlapping insertion/reset may have a documented before/after result, but completed inserts inside the retained window cannot vanish without expiration or explicit reset. Preserve the existing FPR target, capacity, reset rationale and all remaining AlreadyHaveTx stores. Do not reinterpret “lock-free” as “false positives impossible.”

### Small corrected candidates

1. **Measure/batch existing calls first, independently of a new filter.** Instrument sampled wait/hold time and operation counts on the actual inventory/reject/address locks; distinguish rotation sweep cost from lock contention and from unrelated pending-inventory/Bloom state under the same lock. Batch AddKnownTx/announcement updates per incoming INV/INVSHORT under the current lock, preserving all queue erasures and request side effects. This is already scoped by Wave1 item9; avoid duplicate ownership. No atomic filter change is required to test that candidate.
2. **If a proven filter hotspot remains, introduce a new experimental class behind focused tests only.** Keep writer/rotation/reset serialized initially, allow concurrent contains only with a coherent immutable configuration and safe retained-bank lifetime; use atomic cells or immutable bank publication so readers never race plain data. Rotation needs a writer exclusion/quiescence protocol before clearing/reusing an old bank; reset similarly retires an entire old configuration only after old operations finish. This may be a reader-concurrent filter, not lock-free; name and measure it honestly. Integrate at one caller only after proving its surrounding lock can actually be shortened without losing compound-state consistency.
3. A fully concurrent alternative using monotonic per-cell epoch tags and CAS/max updates must first prove collision refresh, epoch reuse/wrap, per-insert ticket accounting and reset reclamation. Avoid in-place sweeps that erase equal recycled tags. Do not ship this as a small memory-order substitution. Reader-pinned retired epochs need a bound; a stalled reader/writer cannot grow retired banks forever. When that bound is reached, a blocking/quiescent fallback may be correct but changes the progress claim and needs explicit shutdown behavior.

Tests must schedule barriers at publish/clear, between two plane/cell writes, after generation reservation and around reset/tweak publication. After completed insertion, assert retention for every non-expired key across multiple full rotations under colliding hashes; test repeated same-key insertions and near-boundary concurrent increments. Test reset old-writer resume and old-reader buffer lifetime, forced tiny generation counters/wrap, delayed participants and bounded retirement. Run TSAN where supported plus deterministic schedules; stress success alone is insufficient. Retain existing bloom_tests and their assertions (including the old implementation's deterministic FPR counts); do not weaken them to accommodate a global replacement. A separately implemented class gets its own well-justified statistical tests and configured sizing checks.

## W3-10: a 65,536-slot fetch_add ring is not a complete queue

### Reservation is not publication

`slot = tail.fetch_add(1) & 65535` merely assigns a modulo address. It neither checks free capacity nor says the payload has been constructed. Two producers separated by 65,536 reservations can write the same slot; a slow old producer can overwrite a later generation. A consumer seeing tail > head may read partial/default data, or race the producer. Adding ready=true is still ABA after slot reuse: it cannot identify the expected lap.

Use per-slot monotonic sequence/lap identities and a capacity-aware claim protocol. A conventional bounded candidate initializes slot.sequence=i. Producer for logical position p may claim only sequence==p, constructs the payload, then release-publishes sequence=p+1. Consumer for h acquire-checks sequence==h+1, takes/destroys the payload exactly once, then release-marks sequence=h+capacity. The producer's claim cursor must not be irrevocably advanced when TryEnqueue returns full: use capacity/sequence validation and CAS reservation, or an explicitly published cancellation/completion record for every consumed ticket. An unconditional fetch_add followed by “full, return false” leaves a permanent hole. No ordinary payload memory may be read before acquire publication or written before the matching free-slot acquire.

This describes a candidate protocol, not a verified implementation. Unsigned counter wrap and distance arithmetic need a stated invariant (capacity far below half the sequence space, bounded outstanding distance, no arbitrary signed-overflow subtraction). Force near-wrap tests; resetting head/tail while producers are live is invalid. Distinguish count, byte memory and in-flight reservations; ring records hold only TxIds/metadata, but separately allocated batches/chunks/fallbacks also count toward memory accounting.

### Full and overflow cannot silently change relay behavior

The existing void relay API is lossless while allocation succeeds. At 65,536 records, a burst above capacity or a stalled consumer cannot be translated into drop/overwrite: already-admitted local/peer transactions would lose relay work, route affinity and first-seen timestamps. A batch may exceed capacity and currently appends contiguously. “250K/s × 10ms is only 2,500” is not a capacity proof: valid RPC bursts, multi-producer bursts and scheduler overruns can exceed one tick or 65,536 records.

A correct candidate must explicitly choose overflow behavior before integration:

- TryEnqueue/TryEnqueueBatch rejects **before reservation/ownership transfer**; caller retains exact records, local flags and queued timestamp.
- A lossless overflow FIFO/chunk fallback can preserve current semantics, but needs one ordering protocol across ring and fallback (logical sequence/epoch plus completion) and must never leave an unfilled ring ticket. Do not drain the fallback first and reorder batches/parent route processing. If fallback is dynamically sized, advertise a bounded fast path, not a globally bounded queue.
- Blocking for capacity is not an acceptable default here. ProcessValidTx can enqueue while owning g_msgproc_mutex and cs_main, and the consumer needs global message serialization and mempool access. Waiting can make the producer wait for its own consumer/locks and deadlock. “Run inline” must not invoke fanout/drain recursively under producer-held locks or outside the consumer owner. An oversized batch must not partially publish and then block indefinitely on its remaining suffix.

The additive queue API must report reservation/full/stopping separately, preserve per-producer order and current contiguous batch behavior, and define the global ordering of overlapping batches. Existing producer order is mutex serialization, not start-time order; a changed reservation point must still leave an allowed serial order and preserve each committed batch as one contiguous append.

### Stalled producer and progress claims

Pause P1 after claiming head position h. P2 may publish h+1 and return, but a FIFO consumer cannot skip h without reading uninitialized data or changing order. Spinning until P1 resumes can freeze message processing; returning “not ready” must leave pending work/wakeup armed. This is head-of-line blocking, so per-slot sequences alone do not establish lock-free system progress. A thread crash/abandoned reservation or exception after claim can strand the queue forever. The payload is simple, so prove no-throw emplacement with static assertions or provide a guaranteed completion/cancellation guard; process/thread termination still requires a shutdown model. Helping requires an independently published immutable payload that another thread can finish; that is additional design, not an atomic flag.

Wake only after release publication; the wake boolean is a scheduling hint, not a memory-publication fence. If wake is set before payload publication, the scheduler may clear it, the consumer may see a hole, and a later publication can sleep indefinitely unless it re-arms wake. Empty/size/overrun metrics must distinguish reserved/unpublished from committed records. A consumer that stops at a hole needs guaranteed later wake/tick progress without a busy loop.

### Single-consumer ownership and shutdown

At these tips, g_msgproc_mutex gives one logical consumer even though SendMessages is called for many peers. The planned per-peer strands remove that serialization: each peer's SendMessages would otherwise call MaybeDrainRelayQueue, racing global next_relay_drain, route map/order, RNG and target selection as well as the ring head. Do not assume “per-peer serial” means “global single consumer.”

Keep one explicit global relay coordinator/strand, or retain a narrow single-consumer gate for the entire tick/fanout/routing operation. Choosing a truly multi-consumer queue would not by itself make the surrounding routing state safe. Establish that owner before the queue implementation; do not combine global-consumer refactoring, strand dispatch and a new ring in one commit.

Queue lifetime must fence all producers and the consumer before destruction. Existing shutdown unregisters validation callbacks, stops admission, stops networking, then stops the scheduler and destroys PeerManager (init.cpp 328–363). A new queue must audit RPC producers, scheduled unbroadcast retry and callbacks already executing, not just network threads. Close admission to new enqueues, finish/cancel all existing reservations, join/drain owning operations, then release slots. Decide whether pending relay may be discarded during final shutdown (current vector destructor discards unprocessed arrivals after producers stop) separately from normal-operation losslessness. Do not spin forever waiting on a producer that shutdown has prevented from completing. Avoid storing CNode/Peer raw pointers in ring records; current records need none.

### Small corrected candidates

1. **Instrumentation-only:** sample relay-queue mutex wait/hold, append count/batch sizes, vector reallocations, swapped/drained count, producer concurrency and max depth; capture tick overrun and all-peer completion. Existing queue-depth/tick-overrun metrics are not direct evidence this mutex is a bottleneck. Compare queue lock time with fanout O(peers × new arrivals), mempool lookup time and the known O(backlog)-per-peer heap work from item7. Do not optimize the ingress mutex based on the latter profile.
2. **Lossless allocation/batching improvement under the current mutex:** append producer-built immutable chunks under one short lock and swap chunks at the existing single consumer, keeping batch ordering and current overflow semantics. This avoids reserve/reallocation/copy inside the lock without inventing bounded dropping or slot reuse. Keep it independent from the item7 persistent inventory queue and measure allocation/memory overhead. RPC already has a batch path; do not recreate one per transaction.
3. **Only if measured contention remains, a standalone tested bounded TryEnqueue primitive:** per-slot generation protocol, no consumed tickets on failed full, no-throw slot ownership, tiny-capacity deterministic tests, and an explicit correct lossless fallback design. Do not integrate into RelayTransaction until fallback/batch semantics and the global consumer owner are reviewed. Do not call it lock-free without proving stalled-producer/system progress on supported platforms.

Required tests: capacity 1/2/4 and 65,536, empty/full/full->drain->reuse, many laps/near-counter-wrap, producer stalled before/after claim and before publish, consumer stalled while full, no early read/no duplicate/no lost entry, non-null/null batch packing and oversized batch, overflow interleaving, producer exception/cancel, wake races, stop during each phase, and delayed producer with stop. Reference model checks TxId/local/timestamp and per-batch contiguity. Assert no unbounded tombstone/reservation accumulation, no raw-pointer lifetime regressions, and no blocking while consumer-required locks are held. Integration gates include shared/native txrelay_tests and v2_protocol_handler_tests plus p2p_tx_relay_invshort.py and p2p_tx_relay_fanout.py, with shutdown/reorg/retry scenarios and strict diagnostics. Performance adoption still requires at least three alternating before/after controlled all-peer completion pairs; microbench enqueue rates are a different metric.

## Recommendation

Reject generation publish+clear and unconditional fetch_add modulo-slot sketches as sufficient implementations. Keep current filter and relay ingress semantics while measuring the actual lock cost. First consider already-owned batch lock work and a small lossless chunk-queue candidate. If a concurrent filter or bounded ring is justified, prove it as a standalone primitive with adversarial schedules and explicit lifetime/progress contracts before one-caller integration. These decisions are independent of changing exact dedup structures or per-peer ranked backlogs; do not merge all four optimizations into one patch.

Wave3 W3-4 fetch_add reservation before concurrent insertion can publish ID2 before reserved ID1; advancing the watermark then loses ID1. This is the same reserve-versus-publish distinction as the MPSC holes above; no reservation counter may be treated as completed publication.
