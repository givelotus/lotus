# Wave 3 admission concurrency review (W3-3 through W3-8)

Status: **read-only design review; no source implementation, build, test or performance measurement**. Prepared against native `8b55e7c8de373d2097da1ebacfcf14fd1098d046` / tree `2ac7093521dcf926c15eb9b77babb881ddff771a` and shared `fec2cab9ce9d8f2ba2bb451ce2bdcdc3a7897830`. Reads used immutable Git objects in the existing canonical source repository; its working checkout is undergoing root-owned prefix builds. No checkout/ref/module pin was changed, and no worktree/clone was created. This document is uncommitted for root's reviewed artifact checkpoint.

The proposed direction—parallel preparation and concurrent commits for independent transactions—is viable engineering work. **The supplied ten-commit recipe does not yet establish a safe concurrent mempool.** Input ownership is one part of a transaction commit, not the complete commit. Atomic counters and an admission/block barrier do not make the retained containers or compound state transitions safe. Do not remove the old locking annotations until replacement ownership is implemented and tested.

## Immediate conclusions

| Proposal | Assessment / required correction |
|---|---|
| W3-3 derive graph edges | Possible from a **coherent committed view**. Independently reading two live indexes and skipping pending children is insufficient for removal/mining/package decisions. `prefix_nibbles=256` is wrong for the proposed nibble API: a TxId prefix is **64 nibbles**, outpoint keys total 72. Linear `small_vector` membership dedup can become quadratic. |
| W3-4 atomics | Useful for selected independent statistics and allocation IDs, but not a substitute for a coherent commit frontier, capacity reservations, index updates or ordered events. `nTransactionsUpdated` is already atomic at this native revision. |
| W3-5 CAS input claiming | Requires unique **attempt/descriptor identity**, explicit pending/committed/aborted states, exact rollback ownership, resource preallocation, parent lifecycle protection and request outcomes tied to final owner status. A pending owner is not a committed duplicate/conflict. |
| W3-6 script-cache sharding | A plausible small shared prerequisite. Preserve key/sigcheck/capacity semantics and guard every cache operation. The coin-read helper is only conditionally safe: the complete cache/backend writer set must actually be fenced. |
| W3-7 chain snapshot / barrier | Needs full chainstate/DB lifetime and mutation coverage, a proved gate protocol and explicit lock order. It is a reader/writer admission barrier, not wait-free admission. It does not freeze mempool parents/removals. |
| W3-8 remove global locks | **Not ready.** `mapTx`, its allocator/indexes, fee state, dirty/unbroadcast logs, snapshot defer state, native removals and event sequencing still need replacement ownership. Queuing only overlay additions leaves contradictory add/remove/publication views. |

The exact generic shared tier has no native input flags, SMT or monetary state. Native `ChainTipSnapshot` members must be adapters or native extensions, not unconditional shared-header dependencies. The actual fixed revisions also do **not** yet contain the hypothetical W2 `RadixTreeMap`, live `m_tx_tree` and CAS claim APIs. Those prerequisites must be implemented and reviewed, not assumed present because their prompt exists.

## Concrete counterexamples to the suggested transitions

### 1. Input claims are not transaction commit records

T claims input A, pauses, and has not claimed B or published a transaction. U spends A. Treating T's partial slot as a committed conflict can reject U even if T next fails to claim B and rolls back. If U is the same transaction, returning `TX_DUPLICATE` / `txn-already-in-mempool` is especially misleading: T may never enter the mempool. Scripts-first reduces how long claims usually live; it does not prove the pending state is unobservable or bounded when the owner is descheduled, encounters allocation failure or loses the duplicate-TxId race.

Use an explicit pending intent. A contender must help, retry, await a bounded completion/cancellation path or report an explicitly defined transient internal outcome; it must not manufacture the existing committed duplicate result. Preserve ordinary finalized/nonfinal conflict result distinctions. **Do not change RPC error semantics while calling this a synchronization-only change.**

### 2. `CTransactionRef` pointer identity is not claim ownership

Two submissions can share the same `CTransactionRef` object. Attempt A's rollback predicate `owner.get() == tx.get()` can then remove a slot installed by attempt B. This can happen even with identical TxId and no allocator ABA. Use a unique admission descriptor/token per attempt, retained by the slot, and remove only the exact descriptor/version. TxId is the transaction identity for committed duplicate semantics; full TxHash/witness identity is required for prepared verification reuse; neither substitutes for an attempt token.

Canonical input sorting is useful but does not itself establish transaction atomicity, starvation freedom or crash/descheduling recovery. Reject repeated input keys according to existing regular-transaction checks before claiming. Track exactly the successfully installed prefix; a rollback handle must not include keys it never owned. If acquisition is “fail immediately, roll back”, there is no ABBA wait cycle in the first place, but contention/retry fairness still needs specification.

### 3. Skipping an unpublished child can lose descendant closure

C claims an input of mempool parent P but has not yet published in `m_tx_tree`. Removal R traverses P's spend prefix, sees the claimed C but its tree lookup is null, and follows the proposed instruction to skip C. R removes P. C then publishes. The live mempool now contains an admitted child of a missing, unconfirmed parent. A chain-tip barrier does not prevent this: P can leave through expiry, manual removal, capacity eviction or finalization bookkeeping without a new block.

The reverse race also exists: C resolves a committed P, R removes P, then C claims/publishes. A last “P exists” check followed by a separate commit CAS still leaves a time-of-check/time-of-use window. A parent-lifecycle reservation/edge protocol, multi-key transaction descriptor or coherent version commit must couple these transitions. Skipping pending entries may be acceptable for a best-effort diagnostic, not for authoritative descendant removal or block-template ancestor closure.

### 4. Allocated entry IDs are not a committed watermark

A reserves ID 1 and pauses before insertion. B reserves ID 2 and inserts. A then inserts ID 1. The current `addUnchecked` assertion that the newly inserted item is the end of the entry-ID index (`txmempool.cpp:204–208`) fails. More importantly, a relay/reconciliation reader that records maximum observed ID 2 and later scans `entry_id > 2` misses A permanently.

Parent-before-child numeric IDs can still be maintained if only fully committed parents are resolvable before a child allocates its ID, but **that does not preserve global publication order**. Define a contiguous committed frontier (including aborted reservations), separate allocation and publication sequences, or update every consumer to use a gap-aware cursor. Root's item-7 admission-suffix optimization depends on this distinction. Do not silently remove the assertion while retaining old watermark semantics.

### 5. A cold eviction lock is ineffective against lock-free producers

E acquires `pool.cs` and traverses/removes Boost `mapTx`. A new admission that no longer takes that lock simultaneously inserts into the same index. E's lock excludes nobody relevant. Atomic counters do not fix the container race or prevent two independent “fits” decisions overcommitting capacity.

Current `LimitSize` additionally requires **both** `cs_main` and `pool.cs` and calls `CoinsTip().Uncache` (`txmempool.cpp:1286–1300`). W3's “take only pool.cs on the cold path” does not satisfy existing semantics. If admission takes `cs_main` while holding the proposed active-admission lease, and a block writer already holds `cs_main` while waiting for active admissions to drain, the two wait forever. A similar cycle is possible through callbacks, flush or RCU grace waits. Cold operations must explicitly transition out of the read lease and enter a correctly ordered maintenance protocol, or operate under the new descriptor/version machinery without the old locks.

### 6. Individual atomic fields do not publish a coherent mempool

Publishing an entry, then its count/bytes, then its spent flags, then dirty/overlay events exposes intermediate combinations. Removal can observe the entry between those operations and subtract a counter that has not yet been incremented. Independently loading all atomic fields does not yield an exact snapshot. Statistics may intentionally tolerate staleness, but package capacity, conflict decisions and root membership require one defined committed generation or descriptor state.

Also, native `Finalize` currently releases a workspace entry, calls `addUnchecked`, acquires/constructs spent-coin payloads, allocates notification vectors and then emits events. Marking `TryClaimInputs` `noexcept` while it grows `small_vector`, allocates radix leaves/path copies or calls allocating fast-filter code converts allocation failure into termination. Either preallocate all resources before publishing an intent, return explicit failure with RAII rollback, or retain throwing semantics with tested strong rollback. `noexcept` is not an allocation guarantee.

### 7. Packages require a shared outcome, not independent per-member claims

Raw batch admission currently validates all transactions and reserves projected whole-package space **before** `SubmitPackage` (`validation.cpp:2490–2519`). `SubmitPackage:1789–1885` inserts topologically, defers snapshots, batches events and trims only afterward. The raw-batch API's all-or-nothing contract cannot be replaced by independent concurrent `Finalize` calls: a package could expose its first member and then lose an input or capacity race for a later member. A competing admission may also spend an output from a package that subsequently aborts.

Give the entire atomic package one commit descriptor and resource reservation; outputs become authoritative together, or are explicitly private to that descriptor until commit. Preserve fee grouping, exact error/result association and limits. Ordinary package APIs may intentionally have different partial-result semantics; do not conflate them with atomic `submitrawtxbatch` or individual staged admission.

## Coin reads and chain-epoch gate

The W3-6 observation is correct: const coin-cache reads can mutate. `CCoinsViewCache::FetchCoin` (`coins.cpp:98–122`) inserts/erases the unordered map, updates usage, expiration and metrics; `GetCoin` calls it. Existing `PeekCoin:132` already provides a non-inserting cache lookup, but is not safe against concurrent writers. A new `ReadCoinSideEffectFree` can be a useful **guarded** primitive; its own “no concurrent writer” precondition must be enforced everywhere.

Freezing block connection alone is insufficient. Current `AcceptToMemoryPool:2848–2886` uncaches failures and invokes `FlushStateToDisk(PERIODIC)` after admission. Other RPCs/cache reads, cache resize/reset/import, active-chain changes and maintenance can mutate cache/backend state under `cs_main` without necessarily going through `ConnectTip`/`DisconnectTip`. The proposed epoch guard must fence every authoritative cache mutation and every cache-filling reader, or admission must resolve from an actually immutable provider instead.

The existing fixed-read provider review remains relevant: `daemon/patch-intake/20261023/atomic-performance-series/snapshot-review/CONFIRMED-COIN-PROVIDER-REVIEW.md`. `CCoinsViewDB::GetCoin` uses separately acquired MDBX read transactions. `CCoinsViewDB::BatchWrite` (`txdb.cpp:231–300`) clears BEST_BLOCK, writes HEAD_BLOCKS, commits partial batches, and finally publishes the new BEST_BLOCK. Reads from a captured tip combined with a database allowed to flush concurrently can span mixed states. The barrier alternative can be correct only if it prevents **all such writes** for the entire read phase, including admission-triggered flush and cache resize. A fixed DB epoch plus immutable dirty/tombstone overlay avoids holding the barrier across verification and permits actual chain progress; native SMT may be used when its complete Coin/context coverage is proved.

`CoinsTip().GetDirtyCount() == 0` is not, by itself, proof that an arbitrary SMT root is the exact authoritative Coin view. Bind the root to the tip/incarnation, full Coin metadata and successful publication lifecycle. A native absent/stale coverage hint remains advisory; never authoritatively reject from it. Coordinate native script-verdict details with `atomic-performance-series/commit11/REVIEW.md` (full TxHash, Coins, context, verified signatures and completed record-free deferred results).

The epoch counter protects neither a raw snapshot pointer nor the active-chainstate object by itself. Enter an RCU section **before** loading a raw published pointer and acquire a retained reference before exiting; retire replaced snapshots through the actual refcount/RCU protocol. Guard manager/pool/DB lifetimes and chainstate incarnation across switch/shutdown. Capture height/MTP/script flags/coin state in one coherent publication; use only snapshot data while unlocked, not a saved tip pointer plus live mutable chain fields.

The current `RCULock` is **non-nestable** (`rcu.h:35–47`: readLock asserts `!isLocked()`). Holding one throughout admission and then calling ordinary radix `get` (which opens its own read section) is not valid. Use short pin scopes and retained references, or explicit within-read-section APIs where the scope is already held. Do not hold global RCU read sections across blocking I/O/pool waits/maintenance that might require a grace period.

An even/odd epoch plus active-reader count still needs a written acquire/recheck/drain/publication proof for the exact memory orders and all exit/failure paths. Multiple block/maintenance writers require exclusive writer ownership; blindly toggling via `fetch_add` can make the epoch even while one writer remains active if callers are not already serialized. Reuse of `cs_main` can serialize cold chain writers while hot readers use a new lease, but prove lock order and do not call such a design wholly lock-free or wait-free. Block connection waits at least as long as the longest admission lease, potentially milliseconds or longer; “50 ns” is unsupported.

## A corrected staged route to real parallel commits

This is a dependency plan, **not** an implementation proof or a proposal to stop permanently at serialized commits.

1. **Establish independent preparation prerequisites.** Make script-cache access thread-safe as a small shared change; retain exact cache keys/sigcheck counts and total memory budget. Publish coherent immutable chain/confirmed-coin views with lifecycle/flush/reorg tests, and finish native exact-verdict reuse separately. Keep authoritative commit locked during these prerequisite commits so each is reviewable and behaviorally comparable.
2. **Specify a transaction/package commit descriptor.** Unique attempt ID, full request identity, reserved inputs/TxId(s)/parent lifecycles, immutable prepared entries, capacity reservation and phases `PREPARED → INSTALLING → COMMITTED` or `ABORTED`. Install slot references before a release commit transition; all authoritative lookups filter by acquire-loaded descriptor status. Pending owners have retry/help semantics, not committed duplicate results. All publication resources must be preallocated or rollback-safe before INSTALLING. Give atomic packages one shared outcome.
3. **Replace authoritative mutable indexes.** A second lookup radix alongside writable Boost indexes is insufficient. Either migrate authoritative lookup/spend/entry-ID structures to a reviewed multi-writer/version protocol with committed descriptors, or make an explicit immutable commit-version representation. The old fee/time/multi-index can remain only as a **derived maintenance view**, never as an unsynchronized authority read by admission/mining/eviction. Preserve exact current fee/time/entry ordering and adapt callers deliberately. Concurrent allocation and reclamation are separate prerequisites.
4. **Couple removals and parent lifecycles to commit.** Parent “alive/closing/removed” transition must coordinate pending child reservations/committed edges; eviction/removal cannot skip invisible children and then let them publish. Design a bounded retry/help/cancellation protocol and deterministic conflict-resolution ownership order. Revalidate the complete read set/context against the commit generation. A final read followed by an unrelated CAS is not sufficient. Capacity budgets reserve before visibility; release exactly once on abort/removal.
5. **Publish coherent counters, events and overlay cuts.** Introduce a committed frontier and immutable event/dirty records keyed by descriptor/sequence. Maintain a gap-aware publication frontier for entry-ID consumers. An ordered outbox can serialize external notification order off the hot commit path while independent commits proceed; duplicate/removal events must preserve causal order. Overlay worker consumes add/remove/reset/tip events in one defined order and can pin the exact committed cut; queued but unmaterialized events are not silently absent from a claimed current root.
6. **Enable independent concurrent commit partitions.** With the above authority and lifecycle protocol proven, allow disjoint transactions/packages to install/commit concurrently without `cs_main`/`pool.cs`; conflicts touch only their specific keys/parent lifecycles. Define cold chain/eviction/config maintenance transitions, release hot read leases before entering incompatible legacy maintenance and revalidate on return. If genuine nonblocking progress is a requirement, pending descriptors need helping or a safe cancellation protocol; a thread paused while owning a slot must not permanently stop unrelated or conflicting work. Do not declare a fixed ring buffer or CAS loop nonblocking merely because it contains no mutex calls.
7. **Measure separately and tune.** Instrument preparation/commit/read-set retry, claim conflict/retry, frontier lag, parent-close retries, capacity waits, snapshot/overlay lag and notification backlog. Then compare validated admission, exact all-peer convergence and block processing separately. A temporary serialized commit baseline is useful evidence for each step; it is not fulfillment of the final concurrent-commit objective.

Different design choices may need more than the ten proposed commits. Do not fold an independent new concurrent-mempool feature wholesale into a historical performance fix merely to make `git log -n10` look prescribed. Preserve source input bundles, exact old→new owner ledger and shared/native gates when later relocating actual repairs. Prompt target labels/hashes are also stale: W2-5 is binary snapshot IDs, **not** the proposed outpoint map (W2-3).

## Required correctness and performance evidence

No tests were run for this read-only report. The proposed broad suites remain necessary but do not replace deterministic race cases:

- Pause an input owner after each partial claim; race a same-pointer duplicate, independently allocated duplicate, different-witness same-TxId request and true conflict; force owner abort. Assert request outcomes and exact slot ownership match final committed state, with no phantom duplicate/conflict. Include repeated inputs and allocation failure at every preparation/install boundary.
- Pause child commit before/after its parent reservation/publication; race parent expiry/manual removal/trim, clear and reorg. Assert no committed orphan, no removal missing a live descendant and no use-after-free. Repeat fork/diamond/high-fanout graphs; verify dedup never becomes O(n²), and assert prefix bit/nibble units with boundary keys.
- Force ID-allocation/publication inversion; assert gap-aware frontier consumers never miss the later lower-ID commit and parent IDs precede all committed children. Verify notification added/removed/block events and RPC completion barriers remain causally ordered.
- Race two large atomic packages that separately fit but jointly exceed budget; include shared parents, overlapping inputs, package fee subsidy, a late failure and concurrent eviction. Assert exact all-or-nothing raw-batch results, no leaked claims/budget, no partial observer visibility and unchanged fee/error semantics.
- Hold a chain writer after it enters the epoch barrier; force admission cold-capacity/flush/callback paths. Prove completion or bounded cancellation without lock-order cycles. Repeat shutdown, active-chain switch, cache resize and failed block connect/disconnect. Use owned Coin copies and distinguish DB errors from absence.
- Validate coin snapshots across every partial DB flush boundary, cache fills/uncaches/reset and same-height reorg. Run TSAN/ASAN stress where supported, plus deterministic interleaving/fault injection; “8 threads ran” is weak evidence without the forced races above.
- Sharded script-cache tests must cover insert versus get with both erase flags, cache budget/zero-small configuration, cache lifetime reuse, full key and sigcheck parity; preserve current assertion coverage. Do not turn advisory native warmup into authoritative VM success.
- Only after these gates: at least three alternating isolated before/after pairs, sufficiently long signed workloads, exact source/binary/config hashes, and separate admission / all-peer completion / accepted-block processing tables. No >500K or 1M claim follows from mutex removal alone.

Root owns the next implementation allocations and source integration. The review does not authorize modifying module pins or applying stacks to the base-only submodules before their active migration gates.


## Clarification: on-demand tree snapshots, independent commit atomicity

The governing target is a **mutable live generation**, with immutable views pinned **on demand** and Merkle hashes computed lazily when a consumer actually needs a commitment. A successful admission does not require a new immutable whole-tree version, a new global snapshot publication or an eagerly calculated Merkle root. Exclusively owned live nodes may be updated in place under the reviewed concurrent-writer protocol; pinning must establish the snapshot cut and preserve shared reachable nodes against later mutation. Root-CAS immutable-tree-per-update designs are comparison alternatives, not the selected default.

The transaction/package descriptors proposed above solve a different problem: consistent visibility and rollback across transaction membership, input claims, parent lifecycles, capacity reservations and notifications. Their commit transition defines when those logical effects become authoritative; it **does not dictate how frequently the radix/Merklix tree is snapshotted or hashed**. Descriptors can coordinate mutations in the current live generation and be retired once safe, while an explicit snapshot request pins a coherent committed cut. That cut must exclude partial/aborted intents and retain complete package semantics, but may share the existing live structure without copying or hashing the whole tree.

Accordingly, interpret “coherent committed view/generation” in this review as the required logical visibility contract, not an instruction to build an immutable tree or full snapshot for each transaction. Keep snapshot pin frequency, structural CoW costs and lazy commitment computation separate from cross-index admission atomicity in both the implementation and benchmarks. The objective remains genuinely parallel admission for independent transactions/packages with exact validation, conflict, dependency and lifetime semantics.
