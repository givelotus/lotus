# Native staged script-verdict reuse (Wave 1, item 11)

Read-only review of exact native `8b55e7c8de373d2097da1ebacfcf14fd1098d046`, tree `2ac7093521dcf926c15eb9b77babb881ddff771a`, using Git object reads in the existing canonical source repository. The active base-only submodules remain unchanged; this candidate is not promoted module content.

## Decision

Implement a **native-only, request-local, completed-success preparation** for staged admission. It can remove V7 script/VM work from Phase C when the current transaction, full coins and execution context match. It does not require the generic shared confirmed-coin provider from item 10: native already has immutable SMT and mempool snapshots. It must not extend the existing legacy `vector<CTxOut>` reuse predicate or turn the existing public advisory warmup object into an authoritative error cache.

The useful scope includes ordinary signed native spends and complex record-free VM programs, not only OP_TRUE. Record-producing programs, incomplete checks and failures fall back to authoritative execution. Keep the current snapshot eligibility restrictions initially unless explicitly extending their structural/input-resolution rules; mint/locked/relative-sequence paths outside that eligibility still execute correctly in Phase C. A later broader preparer can support them by resolving every non-mint input and binding the full transaction; mint inputs are not real spent outpoints.

## Request-local native preparation

Use an owned, immutable `NativeAdmissionPreparation`, attached separately from the existing legacy fields. Prefer a private constructor/factory returning an optional complete success; a freely mutable bag of `ran=true` booleans is easier to misuse. No global native verdict cache is needed.

| Field / dependency | What to retain and what Phase C must compare |
|---|---|
| Transaction | Immutable `CTransactionRef` or full `TxHash` plus owned identity; full input/witness/output/lock content is covered by `GetHash()`, not `GetId()`. Verify transaction hash before regular-result or script-outcome access. Never copy legacy regular-result fields for V7 based on TxId alone. |
| Ordered Coins | Full `Coin` for every real spent input, corresponding ordered outpoints, and explicit mint placeholders only if mint eligibility is added. Compare spentness, `GetTxOut()` semantics, creation height, coinbase flag, `nFeePerOutput` and **explicit** `nExpirationHeight` against the current authoritative view. Comparing derived expiration only hides different overrides. |
| Owners / lifetime | Expected chainman and mempool identity, owned by the node/caller until all preparation work drains. Phase C resolves the current active chainstate and verifies its pool matches. No live chainstate/pool dereference from a worker. Snapshot ownership pins the snapshot, not the node. |
| Tip / contextual token | Captured best block hash, height, MTP and next-block script flags from one coherent snapshot. Initially require the same tip/hash/rules at reuse; all contextual checks still run in Phase C. Any tip change takes fallback even if the height is equal. Mempool generation equality is unnecessary when exact coins and current admission checks match; unrelated mempool arrivals must not invalidate useful preparations. |
| Native chain identity | Preparation uses `chainman.GetParams().V2ChainId()` explicitly. Current ordinary authoritative native checks use `GetActiveV2ChainId()` when no override is supplied, so reuse must match that selected authoritative identity too, or explicitly thread the manager-owned identity through the authoritative path in a separately reviewed change. Do not assume the inherited global cannot change in tests. |
| Native rule binding | `DefaultTxProfile` fields, `NodeV2VmProfile`, `NodeV2VmCost`, opcode semantics and consensus deferred registry. They are immutable for this process/build today. Capture one process-local immutable rules identity/token (or a once-computed digest including every relevant field), not a costly full schedule hash on every transaction. `VmProfileDigest` covers VM profile/cost, **not** the separate `TxProfile` or deferred kinds. Any future selectable/mutable registry must change the token. |
| Per-flags success | Separate complete standard and consensus outcomes and exact sigcheck totals. Run both flag sets, or share only when they are identical. Do not infer flag independence from `nVersion==7`/`nFlags==1`: native spends can enter the flag-sensitive legacy bridge. |
| Completion | Every input completed, every primitive signature verified, fresh deferred run `Accepted()==true`, `RuleFailure()` absent, `ProducedRecords()==false`. `ProducedRecords()==false` alone is not success: a state output can be unauthorized despite producing no records. |

`Coin::GetTxOut()` equality compares native value/type, flags, token ID, state root, branches and paths (`primitives/transaction.h:213–223`). Full `Coin` metadata is additional (`coins.h:25–96`); do not use only CTxOut equality. For native outputs the scriptPubKey is a derived encoding; consume structurally validated immutable Coins from the existing resolver rather than trust a hand-built inconsistent representation.

`CScriptCheck::CheckInput`, `validation.cpp:4425–4645`, consumes the complete native transaction, every resolved output, chain identity, VM/profile/cost and current invocation. Mint positive delta depends on **all** resolved token inputs and transaction outputs. No direct height/MTP field is passed to `VmExecutionContext` (`lotus_v2/vm.h:91–107`); those are admission dependencies and must remain checked by Phase C, not imaginary VM fields. `PreparedVmTransaction::MatchesIdentityAndCoins` is preparation binding only, never a completed verdict.

## Smallest safe implementation sequence

1. Keep `PrecomputeMempoolAdmission`'s current advisory V7 behavior and legacy fields/tests unchanged. Add a separate internal native preparation factory for the staged path. Native-only staging already has the expected pool identity and immutable native coin resolver, so no new lock-taking Phase A is needed.
2. Pin **one** eligible immutable snapshot for the staged call; pass it into native resolver workers instead of separately loading a generation per transaction. Resolve into owned Coins and scalar context, then release the snapshot when no longer needed; retaining the whole old mempool tree through Phase C is unnecessary. Snapshot absence, stale/missing data, cheap hinted failures and unsupported input shapes produce `Unavailable`, not authoritative rejection. Do not fall back to `cs_main` inside executor jobs: the documented locked-batch/executor lock cycle remains real.
3. Refactor the existing ordinary `CScriptCheck` loop into a native-only success preparer, or use a verified native helper with explicit chain identity. Use a fresh `V2DeferredTxChecks` for each flag run and **no batch signature collector** in this first commit. With no collector, returned script success includes primitive verification. Inspect `Accepted`, `RuleFailure`, `ProducedRecords` and exact sigcheck total after the loop. Any unsuccessful/incomplete/record-producing run returns unavailable, retaining only existing primitive-cache warming. Run policy flags first; run consensus only after policy success. If consensus fails, leave no reusable pair.
4. Add an optional native preparation member/parameter to the internal admission result bridge. In `AcceptToMemoryPoolStaged`, keep a separate readiness mask from the legacy `verify` mask. Do not change legacy `StagedAdmissionStats::precomputed` semantics; add a separate native preparation/reuse diagnostic only if needed. No existing assertion should be relaxed from zero to “some” merely because the implementation changed.
5. `AcceptSingleTransaction` accepts a native preparation only after full transaction/owner/context matching and never imports its legacy regular-result fields. Current regular/contextual prechecks still execute normally. Immediately before standard/consensus script checks, compare the prepared Coins to the live private view. If mismatch/unsupported flags/rules/tip, use current `CheckInputScripts` for exact ordinary verdict/error behavior. Failures are never replayed from snapshots.
6. A successful native reuse path returns the matching per-flags sigcheck count and preserves transaction limiter behavior, exact standard/consensus count equality, normal script-cache lookup/erase/store behavior and cache-lookup metrics. Global script execution cache access remains under `cs_main`. Only a complete record-free success may be inserted into that cache, under the exact flags. `ScriptCacheKey` already hashes full `tx.GetHash()` plus flags (`script/scriptcache.cpp:16–25`); keep that existing key rather than invent a TxId-only native key.

Do not change raw package admission, submission batching, signing collector APIs, thread pools or wire/RPC schemas in this commit. The new native preparation is request-local and fully computed before locked commit; only primitive signature-cache effects occur during preparation. This keeps the work independently reviewable and avoids conflating item 10's package lock-scope work with item 11.

## Deferred/stateful cases

- Record-free success is reusable only after final rules pass. OP_TRUE/CHECKSIG creating a forbidden HAS_STATE output must not become reusable, even if every signature cached successfully.
- Successful ENFORCEOUTPUT/state authorizations/output claims produce records; return unavailable and rerun authoritatively. This preserves the explicit current rule that record-producing executions are never served from a pass/fail cache (`validation.cpp:4854–4868`). Do not retain/reuse a `DeferredTxRun` object: it owns mutable per-run accumulators.
- Mint input slots are symbolic, not UTXO lookups. If supported in the new preparation, skip them in Coin matching but bind the entire transaction, all real coins and resulting signing delta. Current snapshot restrictions excluding mint may remain explicit fallback in the first change; do not fabricate a coin for a mint outpoint and compare it to live storage.
- Legacy bridge inputs can be native flag1 spends of legacy outputs. Their interpreter/nullfail/collector behavior depends on flags (`validation.cpp:4353–4415`). Prepare both policy and consensus independently; the existing batch path's broad native-only shortcut is not a sufficient proof for this new reuse path.
- State changes, stale snapshots or incompatible contexts do not become fresh rejection reasons. Authoritative fallback retains current error precedence and partial-success individual staging semantics.

## Meaningful gates

Use the existing `test_between_phases` hook to compare full serial/advisory/reuse admission results. Preserve all current advisory checks in `lotus_v2_tests.cpp:648–978`, particularly same TxId/different witness, changed authoritative value, metadata maturity, unauthorized state output, stale/missing rules/coverage and wrong ownership. Add focused tests for the new API/path:

1. Valid ordinary signed and nontrivial record-free VM spends: identical result, sigcheck/vsize/fees, mempool graph and notifications to authoritative control, with native preparation reused at Phase C. Include uneven multi-input work so last-input deferred completion matters.
2. Same TxId with changed witness/invalid signature cannot inherit a valid preparation; exact full TxHash mismatch must cause ordinary re-verification. Also test attempts to attach a preparation from another transaction/chainman/pool.
3. Between phases, change input amount, token/state/branches/path or another input's coin. Compare to authoritative control; no stale success. Metadata-only creation-height/coinbase/fee-per-output/explicit-expiration changes must prevent reuse and preserve maturity/expiration/conservation rejection semantics.
4. Same-height alternate tip, tip disconnect/connect, MTP/flags changes, global selected chain-ID mismatch and stale publication: no reuse; exact ordinary results. Current contextual checks must run even if preparation would otherwise match.
5. Valid signatures plus unauthorized state output; successful record-producing state/claim program; incomplete deferred execution; collected-but-unverified signatures if a future collector is attempted. None produces reusable success. Stateful valid transactions must still admit through fallback, not be categorically rejected.
6. Legacy-bridge policy-versus-consensus flag differences and exact sigcheck totals. Standard failure goes through ordinary error classification; consensus behavior is not inferred from native flag1.
7. Parent removal/re-admission, parent confirmation, newly admitted staged parent/child, conflicts, changed fees/hysteresis and capacity. Native preparation may be unavailable for a child not in the initial snapshot; it must still admit correctly after its parent in Phase C. No package atomicity change.
8. Busy/nested common executor and missing snapshot: preparation returns without taking `cs_main`; no worker invokes locked fallback. Shutdown joins preparation before chainman/pool destruction.

To prove skipped work, use narrowly scoped native reuse/fallback counters and, if needed, test-only VM execution instrumentation. Existing `VmPreparationWorkCounts` counts preparation, not VM execution, so it alone cannot prove no locked VM rerun. Assert **zero extra Phase C executions** for reusable successes and authoritative execution for mismatches. “Exactly once” means once per required invocation/flag-set in Phase B; distinct standard/consensus flags may intentionally require separate runs. Do not turn a production cache into a configurable test backdoor or infer performance from a hit flag alone.

Required suites: `lotus_v2_tests`, `mempool_admission_tests`, `txvalidationcache_tests`, affected native staged/bridge/deferred suites as registered, plus integration/functional admission coverage. Build and test the exact native candidate with zero new warnings before committing. Pairing uses at least three alternating isolated before/after runs for signed native staging, a complex record-free VM workload and a stateful-fallback control. Record `cs_main` hold/wait separately from throughput, and report RPC admission versus exact all-peer completion separately. None of these tests or benchmarks ran in this review.

## Ownership and limitations

This is a distinct native optimization atop the exact reviewed shared boundary. Capture/match/native-completion helpers and their tests belong to one standalone native item-11 commit; no shared dependency on `lotus::v2` is introduced and no archival mailbox is edited. Native API adapters, if needed during later owner-aware integration, must be recorded explicitly. Broader raw-package preparation, generic confirmed-coin snapshots and aggregate signature verification remain separate commits.

Open implementation choice for root: keep old single-RPC advisory warmup unchanged initially, or add a separately named native-preparation call to that dispatcher once the staged path is proven. Do not silently change the existing public advisory API contract to claim both paths optimized. Exact rates and speedup are unproven.
