`DrainRelayQueue` (shared 4228–4394) swaps *new* global arrivals, chooses peers, then inserts only TxIds into each peer's `std::set<TxId> m_tx_inventory_to_send`. It has no ranked persistent candidate state. It scans target peers once per arrival batch for known/stalled eligibility and looks up parents for route affinity. Keep routing/randomness/local-origin behavior unchanged.

`SendMessages` (11252 onward) holds cs_main and peer inventory mutex, allocates a vector covering the whole remaining set, looks up every rank under one mempool.cs lock, then make_heap. On pop it erases the queued TxId, checks known/stalled, calls `m_mempool.info(txid)` (locking and lookup again), applies fee and Bloom filters, and eventually emits. The local vector dies at the end of every turn; only the unordered-by-rank set persists. The Bloom mutex covers the entire pop/filter loop. The existing rank patch removes comparator lookups/recursive locking, not these scans, allocations or pop lookups.

## Remaining cost

Let N be a peer backlog, B its successful-announcement budget, M live mempool size, P selected peers, and D new arrivals. A normal tick still costs O(N) rank lookups, vector storage and heap construction plus O(B log N) heap work and up to O(B) info lookups. mapTx is a hashed index here, so expected O(1) lookup is the relevant default, not an assumed ordered-map O(log M). The whole scan remains inside cs_main and inventory lock; rank resolution also holds mempool.cs. Filtered/stale candidates do not consume B, so one turn can inspect the whole backlog under inventory/Bloom locks.

For a fixed all-valid backlog drained B at a time, repeated rank scans visit approximately N²/(2B)+N/2 records per peer. Defaults are 10 ms and 250,000 tx/s, hence B=2,500. A one-million-entry backlog implies 400 turns and about 200.5 million rank visits per peer before pop/filter work. This is an operation-count illustration, not measured performance. With continuing arrivals exceeding per-peer service, both backlog storage and per-turn global lock hold time grow. The incoming fanout pass is O(PD) separately and should not be rolled into an asserted speedup.

## Exact semantics to preserve

1. First post-handshake send marks relay-ready; earlier handshake traffic does not become an immediate announcement. Per-peer tick alignment, ceil(rate*tick), minimum budget 1, wake flag and no-burst rules remain.
2. Global fanout selects peers missing the TxId or stalled on it. Local-origin arrivals go to all eligible peers; ordinary arrivals sample configured fanout plus remembered parent routes. Queue insertion deduplicates by TxId.
3. Live transactions precede absent/stale ones; live order is increasing current mempool admission ID. IDs are unique, admission is topological, and a removal/re-admission gets a new larger ID. Equal/absent-rank heap order is unspecified and produces no announcements. No new fee-priority ordering or FIFO-by-enqueue ordering.
4. Pop removes inventory before filters. Known suppresses unless Avalanche-stalled; mempool absence suppresses; base fee must satisfy the peer's captured feefilter; Bloom `IsRelevantAndUpdate` runs only after those checks, in actual selected order. Only emitted transactions count against B. Emission updates recently-announced and known filters and removes the stalled marker. A filter failure is discarded, not retried merely because a later fee/Bloom policy changes.
5. `m_mempool.info` returns base fee, vsize and a transaction ref, plus a fee delta separately. The relay comparison uses `txinfo.fee`, not modified fee. Do not silently use priority deltas. Live metadata/body refs must be refreshed for a new admission incarnation.
6. All `AddKnownTx`, batch known-marking and BIP35 paths must erase the same queue record. `relay_txs=false` clears it. BIP35 removes each queued TxId before its own fee/Bloom decision and bypasses the recently-announced filter. Peer teardown destroys every record/reverse subscription.
7. Transport choice remains: opted-in high-bandwidth body push only with option and at least 16 selected transactions, otherwise negotiated INVSHORT with current epoch/chunking, otherwise full INV. Preserve selection order for all representations, 4096 body chunking and MAX_INV_SZ inventory chunking.

## Proposed independent repair

Implement one logical **persistent ranked inventory queue** change, with its necessary mempool read adapter. Keep fanout, scheduling, admission, protocol negotiation, fee policy, global message serialization and Bloom lock ownership unchanged. Suggested internal owner is PeerManagerImpl/Peer::TxRelay in net_processing.cpp, plus a small mempool.cs-annotated read adapter in txmempool.h/.cpp. It must compile in shared and use no native consensus structures. Queue code may be extracted to an internal net helper for meaningful deterministic tests.

Use an indexed min-heap for live candidates plus an indexed stale tail, with one owning record per queued TxId. A record captures TxId, admission ID/incarnation, base fee and vsize. Resolve a CTransactionRef in the coherent enqueue batch, but do not retain an unbounded strong body ref for every persistent peer record; keep body refs only in bounded active selection snapshots. See the retention qualification below. Keep heap positions in the TxId membership index so erase/update are O(log N) with no abandoned heap nodes. A deque of stale IDs must also support exact erase, or use a linked list with stable record iterators. Do not keep raw mempool iterators or retain a mutable CTxMemPoolEntry as proof of a current admission. Body lifetime does not prove current membership or metadata consistency.

Resolve new global arrivals once in a coherent mempool view in DrainRelayQueue, alongside its existing parent lookup, then share those immutable facts across selected peer records. Any direct queue insertion path must use the same API. Duplicate arrivals do not duplicate pending records; refreshed incarnation data must update the one record. Avoid one separate mempool lookup per selected peer for the same new body.

### Detecting re-admission without a full backlog scan

A persistent heap plus lazy pop revalidation alone is incomplete. A record captured while absent is ranked at the stale tail. If it is later admitted, its new rank can precede other subsequently admitted queued bodies, yet it will not reach the heap top to be repaired. Similarly, cached old ranks must not authorize relay after removal.

A bounded, read-only alternative to introducing another mutation journal is available in these exact tips: `CTxMemPool::addUnchecked` assigns `nextEntryId++` and mapTx has an ordered entry_id index. `_clear` does **not** reset nextEntryId. Propose `ReadRelayAdmissionsAfter(cursor)` under mempool.cs, returning only currently-live entries with ID greater than cursor and an advanced watermark equal to the captured allocation cursor. It is an ordered-index suffix walk, O(log M + K), not a mempool/backlog scan. Return copied immutable facts, not iterators into a released lock. Do not reuse `SnapshotChangedEntries`: it is cleared by snapshot publication and is not a durable multi-consumer log. Async validation callbacks alone also do not establish an authoritative before-send view.

PeerManager holds one global admission watermark and an exact TxId-to-queued-peer-record subscription index. Before serving ranked inventory under cs_main, read the new-live suffix once and update/rekey subscribed records (including stale->live and changed incarnation); unsubscribed entries require no queue allocation. Advance watermark only after applying the complete returned suffix, with cs_main still preventing admission/removal interleaving for the relay turn. Newly queued IDs are directly resolved even when their current admission predates that watermark. Capture and test initialization, clear/reorg re-admission, empty suffix, and entry-ID lifetime assumptions explicitly; no numeric wrap/reuse assumption stronger than the existing unique-ID index is allowed.

**Dependency on serialized admission publication (Wave3 W3-4):** the suffix-watermark design is valid only while rank assignment and insertion are serialized as in these exact inspected tips. It is not compatible with replacing nextEntryId++ by fetch_add followed by concurrent insertion. Counterexample: A reserves ID1 and pauses; B publishes ID2; a relay reader consumes through watermark2; A later publishes ID1 and will never appear in the >2 suffix. This also violates the current rbegin/new-entry assertion and can invalidate admission/topological rank semantics. A parallel-admission implementation must expose a **committed contiguous publication frontier** (readers never advance past a missing lower ticket), or a durable publication journal with consumer cursors/overflow/reset handling. A reservation counter or highest visible ID is not that frontier. Keep item7 on current serialized-publication semantics until that API contract is reviewed jointly with Wave3 admission work; do not silently port the suffix shortcut onto parallel reservation IDs.

This adds expected O(K + affected queue updates), plus the ordered-index seek, per set of new live admissions, rather than O(PN) per unchanged backlog tick. The reverse subscriber map adds one small index link per existing queue record; use peer lifetime-safe ownership and erase it on every known/drop/BIP35/clear/finalization path. This is required bookkeeping for this optimization, not a new peer scheduler.

Before accepting an output prefix, batch-resolve the current heap candidates under one mempool.cs acquisition. Compare TxId **and incarnation ID**, refresh current authoritative ref/base fee/vsize, rekey mismatches, move removed entries to stale tail, then continue until B sends or no candidates remain. Refresh newly admitted IDs before this pop selection. Removal cannot make a cached rank a valid membership proof. Revalidate all speculative chunks before stateful Bloom updates; do not call Bloom on candidates that later rekey behind others. A final authority check is still required even with immutable transaction refs.

### Bounded stale retention/removal

Do not add an arbitrary TTL, backlog cap, oldest-drop rule, or “drop absent at enqueue” shortcut: those can lose an announcement if the TxId is re-admitted while original stale inventory would still be queued. Preserve the current stale-tail behavior. On authoritative absence, release any active cached body ref immediately, retain only one small TxId record in stale tail, and keep its subscription so a new admission promotes it before ranked selection. Once no live record precedes it and the successful-send budget is not exhausted, purge stale records as the original loop would. If B is exhausted, preserve stale inventory for the next turn. No additional lazy tombstones are retained: physical records <= logical queued unique TxIds, and empty/clear destroys all storage/subscriptions. Stale count can still equal the existing logical backlog; this proposal adds no unbounded second accumulation and does not claim a bounded absolute backlog absent a separately reviewed policy.

Do not impose a new examined-record budget inside this commit: current B counts successful sends only, so a rejected/stale run can be drained in one turn. A time-sliced cleanup/fairness policy would be a distinct behavior change. Admission suffix refresh makes missing->live detection independent of sweeping the stale backlog each tick. When no live sends remain, stale cleanup is amortized once per logical record; continuous removals/re-admissions incur work proportional to actual changes.

**Body-retention qualification:** “Resolve ref once in Drain” cannot safely mean keeping every body alive until its slowest peer drains. Removed mempool bodies could then accumulate behind a rate-limited backlog; this would add a body-retention budget problem to a queue-index optimization. Prefer persistent ID/rank/fee/vsize records and transient, byte-bounded selected-body snapshots, obtaining authoritative refs in a single pop batch. This retains O(B) body selection rather than O(N) peer-backlog bodies. A shared bounded body cache could later reuse the enqueue ref, but cache eviction must drop only the optimization/ref, never the queued announcement; missing refs fall back to the same authoritative batched lookup. The existing incoming SHORTTX 64 MiB retention reservation does not cover outgoing peer backlog references and must not be reused without explicit ownership/accounting. Do not assume weak_ptr solves this: CTransactionRef uses shared_ptr, and the combined transaction/control allocation can remain allocated until weak owners disappear. This deliberately qualifies the ref-caching part of the item7 wording; persistent rank reuse is independently useful and needs no unbounded body cache.

Keep thread annotations. Existing SendMessages order is cs_main -> peer inventory -> mempool.cs and inventory -> Bloom; Drain currently avoids holding mempool and inventory simultaneously. Prefer new global admission refresh under cs_main before taking per-peer inventory locks, and copy mempool facts before applying queue edits, so no new mempool.cs -> inventory versus inventory -> mempool.cs inversion appears. Do not introduce a new mutex acquisition from addUnchecked or asynchronous callbacks. Explicitly assert no admission gap between refresh and authoritative selection; future strand work must revisit that dependency.

## Gates and acceptance criteria

- Deterministic queue unit tests with a reference implementation of the existing full-rank-per-turn algorithm. Compare emitted TxId order, pending membership, fee/Bloom effects and budget accounting over multiple ticks; stale-only internal ordering need not be fixed.
- Parent/child queued out of order; low B across at least three turns; new lower/higher rank insertions; duplicate enqueue; known-before-send; stalled-known exception; known batch erase; BIP35 erase despite fee/Bloom failure; opt-out/clear/disconnect.
- Remove one/all queued bodies; same TxId remove/re-add with a newer entry ID both before/after enqueue; an initially missing TxId becomes live below another queued new rank; clear followed by re-admission; eviction/mining/reorg; fee/vsize incarnation refresh. Explicitly prove the stale-tail case that breaks plain lazy-pop heaps.
- Use test counters to show a second unchanged-backlog tick does not resolve N ranks or allocate/build an N-element temporary heap. Count suffix enumeration/record updates as well; no hidden full stale or reverse-index scan. Test 100K queued, B=small without needing a wall-clock claim.
- Assert one physical record per pending unique ID after repeated known/remove/re-add churn, no stale CTransactionRef after authoritative absence, empty membership/reverse indexes after clear/finalization; test all insertion and erasure sites listed above.
- Existing txrelay_tests (per_tick_rate_budget, fanout_selection, negotiated modes and default no-body-push) and v2_protocol_handler_tests (fixed tick, 16-body ordered relay, suppression, bursts) in shared; corresponding native target after exact shared parent integration. Functional p2p_tx_relay_invshort.py and p2p_tx_relay_fanout.py; strict warning comparison.
- Adoption/performance evidence requires at least three alternating before/after all-peer convergence pairs under controlled backlog and comparable initial/final mempools. Report all-peer completion separately from admission/RPC or microbench operation counts. No such measurement was run for this review.

## Decision

Proceed only with persistent queue/lifecycle handling, not a second cached-comparator patch. The admission-suffix adapter and one-record indexed queue are a concrete candidate to prototype independently. Review the reverse subscription and watermark proofs before implementation. If that scope is rejected, a simpler persistent heap must explicitly retain an O(stale-backlog) refresh fallback; it cannot claim exact missing->live semantics or complete backlog-scan elimination using lazy pop alone.
