# Lotus V2 TypeScript compiler

Start with the [contract gallery](examples/gallery/README.md) for payments, helpers, hash references, token minting, mandatory transfer rules and a burn-to-upgrade method. The schema-2 compiler has a bounded fixed-point optimizer, generated TypeScript/Python bindings, and maintained call runtimes. The [transaction planner](TRANSACTION-RUNTIME.md) builds multi-input spend/mint calls with explicit coins and selected paths. Reference VM and native checks are independent; full block validation remains outstanding.

## Historical schema-1 payment slice


This package compiles only the example `Payment<owner: PublicKey>` contract with one `spend(signature: Signature)` method and `require(checksig(signature, owner));`. Identifiers, whitespace and comments may vary. Other statements, methods, types, opcodes and `OP_SUCCESS_N` are rejected. `owner` is a supplied 32-byte x-only public key, so compilation is deterministic and has no wallet, network, signing or RPC side effect.

The CLI emits a versioned JSON artifact with the P03 `PUSH_32 owner CHECKSIG` script, P02 one-leaf branch root and path, source byte spans, static stack report, and thin TypeScript and Python binding sources. The schema-1 Python binding declares an injected runtime protocol; schema 2 has its own maintained Python runtime. Both bindings keep signing separate from call preparation. This legacy TypeScript runtime implements only one native spending input, FULL-mode BIP340 signatures, one branch/path with zero siblings, and native spendable outputs. It requires explicit `chainId`, outpoint, sequence, resolved coin, outputs and profile. Amounts are `bigint`; bytes are `Uint8Array` internally. The fixture-only profile name prevents treating this as production network validation.

```sh
cd tools/lotus-v2-compiler
npm ci
npm test
node dist/cli.js examples/payment.lotus f9308a019258c31049344f85f89d5229b531c845836f99b08601f113bce036f9 /tmp/lotus-payment-abi
node examples/run-payment.mjs
```

`run-payment.mjs` signs with the public BIP340 test key 3 and zero auxiliary randomness. It prints actual transaction bytes and machine-readable stage results. Its signed wire, TxID, TxHash and signing digest match the independent Python reference candidate at `c0126889`; the same values appear in native C++ candidate `40a5479a` tests. These candidates are pending integration review. No VM invocation, contextual coin/lock check, block fee-floor check, connect or disconnect is claimed. The `stages` fields report these as `unavailable`.

## Offline test fixtures

`buildPaymentFixture(input)` in `@lotus/v2-payment-compiler/fixtures` accepts explicit source, 32-byte x-only owner, deterministic public test secret, ChainID, outpoint, sequence, lock, resolved coin, output list, profile and signing mode `0` (FULL). Its amounts and lock use `bigint`; the JSON CLI accepts canonical decimal strings. The test secret is an input to the offline builder and is **never included in exported fixtures**. The fixture has schema `lotus-v2/payment-fixture/1`, a signature-valid baseline with complete transaction bytes, and three named mutations: changed output value, changed ChainID and changed owner. Each mutation retains the original signature and records `expectedStage: signature` and the rejection reason. These are stage expectations, not full consensus-valid/invalid claims.

```sh
npm run build
node examples/generate-fixtures.mjs
node dist/fixture-cli.js input.json output.json
```

The CLI input uses schema `lotus-v2/payment-fixture-input/1`. It has the same fields as `PaymentFixtureInput`, except `coin.value` and output values are `valueAtoms` decimal strings and `lock` is a decimal string. Each output has `flags: 0`, `branches: [lowercase-h32]`, and `paths: [[0]]` for this slice. `profile` must be `payment-fixture-p01-v1`, `signingMode` must be `0`, and the first output must be positive so a changed-value mutation is possible. The builder rejects a test secret whose public key differs from `owner`. Its JSON output can be consumed by daemon fixture generators or native tests without importing the TypeScript compiler into consensus code.

The checked-in key-3 one-output fixture reproduces the independent hand vector. The key-4 two-output fixture varies the script/policy, input outpoint, amounts and output count. Generated TypeScript and Python wrappers are executed in tests and produce the same signed witness bytes. This legacy Python test supplies a wire adapter through the generated runtime protocol. Schema-2 tests execute the maintained Python call and transaction runtimes.

To check those newly generated bytes against the separate native signing candidate:

```sh
cmake -S test/native-check -B /tmp/lotus-compiler-native -GNinja \
  -DLOTUS_V2_CPP=/path/to/native-candidate/src/lotus_v2 \
  -DLOTUS_SECP_LIBRARY=/path/to/libsecp256k1.a
cmake --build /tmp/lotus-compiler-native
node test/run-native-fixtures.mjs /tmp/lotus-compiler-native/compiler_fixture_native_check
```

This checker runs native framing, identities, signing message and BIP340 verification for both baseline transactions and all six changed-context/signature mutations. It does not run VM execution. The gallery adds mint and transfer fixtures through the separate transaction runtime; stateful contracts and delayed recovery remain future work.

The separate token checker now also runs the native P03/P05 VM. Build it against
the reviewed V2 native series (through patch 025):

```sh
cmake -S test/native-token-check -B /tmp/lotus-native-token-vm \
  -DLOTUS_V2_CPP=/path/to/native-source/src/lotus_v2 \
  -DLOTUS_SECP_LIBRARY=/path/to/libsecp256k1.a
cmake --build /tmp/lotus-native-token-vm
node test/run-native-token-fixtures.mjs /tmp/lotus-native-token-vm/compiler_token_native_check
```

This target requires OpenSSL Crypto. It verifies the signed Payment and all ten
mint/transfer/merge witness invocations under an explicit illustrative cost profile.
Negative probes reach the VM for an unauthorized issuer, re-signed transfer and
merge outputs removing the mandatory rules or wallet path, and a mint input's
nonexistent coin. These invocation
checks still leave complete transaction, lock, monetary and block validation to
the daemon integration work.

The artifact schema is `lotus-v2/payment-artifact/1`; its target is `P01-P02-P03-candidate-2026-10-14`. JSON hashes and bytecode are lowercase hex; user-facing native amounts must be decimal atom strings and parsed to checked `bigint`. The runtime accepts no implicit network and rejects an artifact whose policy root does not match its script. Generated clients must pin this schema and supply a separately reviewed signer; they must not assume that a valid signature alone makes a transaction valid.

Schema-1 source mapping retains UTF-16 offsets (JavaScript string offsets); schema 2 uses UTF-8 byte offsets.

## Promise scheduler and executable optimizer demo

Run the [compiler pipeline demo](examples/compiler-pipeline/README.md) to see a
forward-reference dependency diamond, a shared compilation job, before/after
bytecode, and independent VM execution of valid and malformed inputs.

`compileContractAsync(source, options, onEvent?)` parses once and registers the
retained declarations. Promise jobs compile method leaves and contract roots after
awaiting their dependencies. Pure helpers are expanded within method jobs. Shared
jobs are memoized per compilation; unused declarations are not compiled. The
scheduler checks cycles before starting jobs and reports their declaration spans.
It bounds jobs, dependency edges, depth, and helper dependency discovery. These are
single-threaded dependency jobs, not CPU worker threads.

`compileContractWithTrace(source, options)` returns `{ artifact, trace }`; events
include `start`, `await`, `resolve`, and `reject`. The generic CLI now uses the
scheduler and accepts a final `--trace` flag to write `scheduler-trace.json` next
to the artifact and generated clients. The synchronous `compileContract` API
remains available and produces the same artifacts for accepted inputs.

## Bounded template and method frontend (artifact schema 2)

`compileContract(source, { contract, bindings })` in `@lotus/v2-payment-compiler/generic` compiles one selected `contract` or `token` tree from a source that may contain multiple trees and free pure helpers. Every constructor value for every referenced tree must be supplied explicitly. It emits `lotus-v2/contract-artifact/2` with ordered method arguments, each method's script, leaf, bottom-up membership proof, source map and static size/stack report. A contract root is a spending branch; a token root is its token ID. The `kind` and per-method `invocation` fields identify these different uses. Token methods require a first `Amount` parameter in source; that parameter is omitted from `method.args` because the node pushes the positive mint delta above witness arguments. The policy is one P02 branch root with path `[[0]]`. The deterministic method tree sorts distinct method leaves as unsigned little-endian hashes, splits at the greatest power of two below the leaf count, and uses P02's sorted-child node hash. Method names select an ABI entry; consensus sees the revealed script and proof, with no numeric method index.

Compilation optimizes `CHECKSIG; VERIFY` into `CHECKSIGVERIFY`, `EQUAL; VERIFY` into `EQUALVERIFY`, and `ZERO; PICK` into `DUP` using a bounded fixed-point pass. It recursively reduces adjacent known literal expressions for checked int128 arithmetic, canonical Boolean operations, equality and hashing. A known true verification can disappear; false verification, overflow and malformed values retain their failing operations. Constructor bindings and cross-contract hashes are opaque to equality folding so policy roots still commit to them. The symbolic stack pass tracks argument identities and canonical Boolean facts established by `IF` and successful `VERIFY`. It recursively analyzes both branch arms, merges compatible identities, and removes redundant pure stack reads and proven checks. Loop bodies are analyzed with fresh incoming identities and no inherited facts; loop exit also discards identities, so mutable locals cannot be mistaken for invariants. The combined literal, peephole and symbolic passes repeat to a bounded fixed point. This is a conservative supported subset, without general expression common-subexpression elimination, arithmetic theorem proving, or loop unrolling. For a straight-line method with exactly one argument and one depth-zero use, it also consumes that argument directly and removes its copy and final drop; loops and all non-allowlisted operations disable that rewrite. For example, `require(checksig(sig, owner))` lowers to `PUSH_32 owner; CHECKSIGVERIFY; ONE` (35 bytes, three opcodes). `optimize: false` emits the original lowering for differential testing. `staticResources` and byte offsets describe the final script; a fused source-map entry records original instructions in `optimizedFrom`. Fewer bytes and opcodes lower cost only under a profile that prices those instructions accordingly. Because the script changes, so do its method leaf, contract root, signature digest and signed transaction fixture. Regenerate any schema 2 fixture from the compiler when switching modes; schema 1 Payment fixtures remain separate.

```text
function digest(x: Bytes32): Bytes32 { return sha256(x); }
contract Vault<owner: PublicKey, target: Bytes32> {
    function spend(sig: Signature) { require(checksig(sig, owner)); }
    function reveal(data: Bytes32) { require(digest(data) == target); }
}
```

Supported constructor and method types are `PublicKey` (validated BIP340 x-only point), `Signature`, `Bytes32`, `Bytes(N)` (up to N bytes, N in 1..8192), signed 128-bit `Int` and `Amount`, exact 32-byte `TokenId`, `Bool`, and distinct `MethodLeafHash` / `ContractRootHash` values. Constructor byte values are lowercase hex, numeric values canonical decimal strings or `bigint`, and Bool values booleans. Methods take ordered wire arguments. Expressions include `checksig`, `sha256`, `hash256`, `blake3`, equality, limited checked integer arithmetic/comparison, Boolean operators and unary `!`/`-`. The full signed Int range, including `-2^127`, is accepted; values outside it reject. Statements include `require`, bounded `if`, local numeric assignments, and `for input in tx.inputs` / `for output in tx.outputs` with at most two nested loops. Introspection supports input spend flags and resolved coin fields, output token/value fields, `this.root`, and `output.requires_branch(root)`. Mint methods cannot read `this.coin`; input coin reads in a mint loop must be guarded by `input.is_spend` because mint inputs resolve no coin. A method finishes with exactly one true value after its requirements pass. Free expression helpers inline at calls with scoped parameters and source origin spans. Arbitrary opcodes and external effects remain unsupported.

Boolean `&&` and `||` short-circuit through P03 conditionals. This lets `input.is_spend && input.coin.token_id == old_token` avoid reading a coin for a mint input. A helper call substitutes its argument expression at each parameter use (call-by-name), so a helper that uses `x` twice evaluates `x` twice in the emitted script. This can repeat `checksig` or hash work. The compiler reports script size, opcode count and a conservative maximum signature-check count after expansion, multiplying loop bodies by their maximum transaction count. It bounds emitted helper expansions and type-inference visits. A direct method expression avoids repeated evaluation of an expensive value.

`leaf_hash(Other.method)` yields a `MethodLeafHash` of a fully bound compiled method. `contract_root(Other)` yields a `ContractRootHash` of a fully bound contract. Their types are distinct from plain `Bytes32`. A self or mutual dependency through these builtins is rejected, as are recursive helpers. Source spans in schema 2 are **UTF-8 byte offsets**; schema 1 Payment artifacts retain their historical UTF-16 code-unit offsets. Schema 2 limits source to 65536 UTF-8 bytes, methods to 16, scripts to 8192 bytes, opcodes to 4096, helper expansions to 256, inference visits to 8192, and expression/control nesting to 64/16. Normal compilation emits only assigned P03 opcodes and rejects unsupported syntax, including an `OP_SUCCESS_N` spelling. Source names use a portable TypeScript/Python namespace; reserved names and case-folded method collisions reject before binding generation.

The v2 CLI reads source plus an options JSON object, then writes `artifact.json` and generated TypeScript and Python call wrappers:

```sh
node dist/generic-cli.js vault.lotus options.json /tmp/vault-artifact
```

For the example, `options.json` is `{"contract":"Vault","bindings":{"Vault":{"owner":"<32-byte lowercase hex>","target":"<32-byte lowercase hex>"}}}`. The schema is [artifact-v2.schema.json](artifact-v2.schema.json). Schema 1 artifacts are not reinterpreted as schema 2; its signed fixture remains an independent historical vector. The generated TypeScript and Python wrappers call maintained small runtime interfaces to prepare and finalize canonical bytes; neither signs or contacts a node. Single-file compilation has no RPC, wallet, filesystem import, or signing side effect; the CLI only reads its declared source/options and writes requested artifact files. Package builds (below) read the lock, declared files and, when the graph names a module path, the local cache or `vendor/` tree.

## Local packages and explicit imports (CABI-07)

`compilePackage(dir, { contract, bindings, optimize?, limits? })` in `@lotus/v2-payment-compiler/packages` builds the root package in `dir` from `lotus.toml`, `lotus.lock` and declared local files. It is build-time only, has no network, registry, clock or environment input, and touches no consensus, VM, runtime or transaction code. `compileContract(source, ...)` is unchanged: it is a wrapper over one in-memory module, rejects `import`, never emits a `build` field, and single-file artifacts and fixtures are byte-identical to the previous compiler. See [examples/packages](examples/packages/README.md) for the diamond fixture.

```sh
node dist/package-lock-cli.js DIR            # rewrite DIR/lotus.lock from local files only
node dist/package-lock-cli.js DIR --check    # fail if the lock is stale
node dist/generic-cli.js --package DIR options.json OUT_DIR [--trace]
```

**Syntax.** Imports precede declarations. `import ALIAS::path::to::module::{name, other as local};` binds selected functions under local names; `import ALIAS::path::module as m;` binds a module alias used as `m::name(...)`. `ALIAS` is a dependency alias from the importing package's manifest, or the keyword `package` for a module in the same package. Helper visibility is `function` (private to its module), `package function` (any module of the same package) or `export function` (other packages, but only from modules listed in `exports`). Helpers already require explicit parameter and result types. Contracts/tokens may only be declared in the root package entry module; library modules are declaration-only and cannot use `leaf_hash`/`contract_root`. Local names, imports and module aliases share one namespace per module; duplicates and builtin names (`checksig`, `sha256`, ...) reject. Single-file builds accept the visibility modifiers without effect. Imported helpers inline exactly like same-file helpers (the test compares a package build with an equivalent flattened source).

**Manifest.** `lotus.toml` uses a strict TOML subset parsed by [toml-subset.ts](src/toml-subset.ts) (tables `[package]`, `[dependencies]`, `[sources]`, `[replace]`; bare keys or quoted basic-string keys; plain strings and one-line string arrays; no escapes, numbers, dotted keys or inline tables; duplicates and unknown keys reject). Every accepted file is valid TOML. `[package]` has `name`, exact `version` (`MAJOR.MINOR.PATCH`), `kind` (`contract` or `library`), `source` (source root subdirectory), `modules` (all module files, `a/b` means `SOURCE/a/b.lotus`), optional `exports`, and `entry` for contract packages. A local package name is a short identifier. A git package name is its module path. `[dependencies]` maps a local alias to an exact `name@MAJOR.MINOR.PATCH` or to a module selector (`module@vX.Y.Z` or `module@` + 40 hex digits). `[sources]` in the root manifest maps a short name to a project-relative path. `[replace]` in the root manifest maps a module path to another relative path or git locator. Dependency `[sources]` and `[replace]` tables are ignored.

**Lock.** A path-only graph writes canonical JSON `lotus-v2/package-lock/1`: the root name/version/dependencies and, per dependency, its path locator, resolved package root (project-relative realpath), dependencies, per-file digests (manifest and declared modules) and tree digest. A graph that names a module path, a replace, or a quoted import writes `lotus-v2/package-lock/2` instead. Schema 2 adds the selected commit and git tree when the package came from git, the requesters, and whether a root replace is in effect. A build regenerates the lock text from disk and requires byte equality, so a changed source byte, manifest or dependency set is rejected (`lock-mismatch` names the file) until the lock is rewritten. Compile does not rewrite a schema-1 lock into schema 2.

**Module paths.** There is no registry and no name claim. A package is named by where it lives. For `github.com`, `gitlab.com`, `bitbucket.org` and `codeberg.org`, `host/owner/repo` is the git repository `https://host/owner/repo.git`. Any remaining path is a subdirectory of that repository. A final `/vN` with N ≥ 2 is a major-version suffix, as in Go: `github.com/acme/lotus-std/v2` is still `https://github.com/acme/lotus-std.git`. If `v2/lotus.toml` exists, that directory is the package root; otherwise the repository root is the package root when its manifest major is 2. Tags `v0` and `v1` have no suffix. A `v2+` tag on an unsuffixed path is rejected. `/v2` is a different module from v1, so minimal version selection does not merge them. Any other host is not guessed. The root manifest must name it in `[sources]` as an `https://` or absolute `file://` URL, with an optional `#dir` subdirectory. Vanity-domain HTML discovery and a proxy mirror are not implemented.

The same package can be named by an alias or by a quoted path. Both are requirements, and the compiler parses the selected module once:

```text
std = "github.com/acme/lotus-std@v1.2.0"          # root lotus.toml
import std::amounts::{checkedAdd as safeAdd};
import "github.com/acme/lotus-std@v1.2.0"::amounts::{checkedAdd as alsoAdd};
```

Selectors on compile and fetch are exact tags or full commit ids. Two tags of one module path use minimal version selection (the higher tag required by the root or by a selected version). Requirements of a version that lost that comparison are ignored. Two different commit pins are an error. A tag and a commit are accepted only when the tag resolves to that commit. Branch names and `^` / `~` ranges are rejected until `lotus-v2-package-update`, which rewrites the root manifest to an exact tag or commit and then fetches.

```sh
node dist/package-fetch-cli.js DIR              # clone into DIR/.lotus/deps and write lotus.lock
node dist/package-fetch-cli.js DIR --vendor     # clone into DIR/vendor instead
node dist/package-update-cli.js DIR std@^1.2.0  # pin the highest matching tag, then fetch
node dist/package-update-cli.js DIR std@main    # pin the branch's commit, then fetch
```

Fetch is the only networked package command. It runs git with hooks, templates, smudge filters and prompts disabled, deletes `.git` before the tree is scanned, and does not run repository code. Compile, `lotus-v2-package-lock` and a fetch that is not repeated read only the lock, `.lotus/deps` or `vendor`, and declared files. They verify every locked digest and do not spawn git. Exactly one of the cache and `vendor` may hold a selector. A root `[replace]` wins over the derived URL and is recorded in the lock; replacements are never read from dependencies.

**Digests.** All digests use the existing domain-separated `tagged(name, payload) = BLAKE3("Lotus/v2/" || name || 0x00 || payload)` with CompactSize-prefixed fields: `package/file` over the file bytes; `package/tree` over name, version and sorted `(path, file digest)` pairs; `package/declaration` over an exported helper's name, parameter names/types and result type; `package/interface` over package name, module path and exported declaration digests (bodies change `sourceDigest`, not `interfaceDigest`); `package/lock` over the lock bytes; `build-graph` over the UTF-8 JSON of the build graph without its `digest`.

**Resolution rules.** Module identity is `(name@version, normalized module path)`, written `core@1.0.0/amounts`. Absolute paths, `..`, backslashes and non-normalized segments reject; package roots must realpath inside the root project, source roots inside their package, and any symlink inside a source root must resolve to a file inside the package. Source roots are walked with exact on-disk names: undeclared files, declared modules without an exact-case file, and case/Unicode (NFKC + case-fold) collisions reject. Each module identity is parsed once and has one `module:<id>` scheduler job that links it after its imports, so diamond imports are deduplicated (`parses` and the trace prove it). Defaults: 64 packages, 256 modules, import depth 32, 4096 import bindings, 4 MiB total source, 4096 walk entries; `limits` lowers them.

**Diagnostics.** `PackageError` has a `code` (`path-escape`, `symlink-escape`, `path-collision`, `undeclared-file`, `missing-module`, `missing-symbol`, `unknown-alias`, `not-exported`, `visibility`, `duplicate-name`, `import-cycle`, `lock-missing`, `lock-mismatch`, `lock-stale`, `limit`, ...), a project-relative `file` and, for source errors, a UTF-8 byte `span`, formatted `file:start..end: message [code]`. Import cycles list every hop with file and span.

**Artifacts.** Package artifacts stay `lotus-v2/contract-artifact/2` with an optional `build` object (`lotus-v2/build-graph/1`): compiler name/version/profile, target, root package and entry module, lock digest, every package's tree digest and dependency aliases, and every reachable module's file, source digest, interface digest, exported signatures and imports. Source-map spans in package artifacts carry a `module` identity. Paths are project-relative, so identical inputs give byte-identical artifacts in any checkout. The contract root still commits only to bytecode: a comment-only dependency change alters the build graph but not the root; a semantic change alters both.

**Not yet implemented.** A proxy mirror, vanity-domain discovery, trust policy and published-package compatibility; importing contracts/policies or commitment builtins across modules and dependency-aware client generation (CABI-08); Python/native VM fixture execution of package-built contracts (CABI-08). Type errors detected while expanding an imported helper name the canonical helper (`lib_a@1.0.0/limits::withinBudget`) but do not yet carry a file span. Branch names and semver ranges resolve only through `lotus-v2-package-update`.
