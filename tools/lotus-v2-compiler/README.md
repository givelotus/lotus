# Lotus V2 TypeScript Payment compiler candidate

This package compiles only the example `Payment<owner: PublicKey>` contract with one `spend(signature: Signature)` method and `require(checksig(signature, owner));`. Identifiers, whitespace and comments may vary. Other statements, methods, types, opcodes and `OP_SUCCESS_N` are rejected. `owner` is a supplied 32-byte x-only public key, so compilation is deterministic and has no wallet, network, signing or RPC side effect.

The CLI emits a versioned JSON artifact with the P03 `PUSH_32 owner CHECKSIG` script, P02 one-leaf branch root and path, source byte spans, static stack report, and thin TypeScript and Python binding sources. The generated Python binding declares the runtime protocol; a production Python runtime is not yet implemented. Both bindings keep signing separate from call preparation. The maintained TypeScript runtime in this package implements only one native spending input, FULL-mode BIP340 signatures, one branch/path with zero siblings, and native spendable outputs. It requires explicit `chainId`, outpoint, sequence, resolved coin, outputs and profile. Amounts are `bigint`; bytes are `Uint8Array` internally. The fixture-only profile name prevents treating this as production network validation.

```sh
cd tools/lotus-v2-compiler
npm ci
npm test
node dist/cli.js examples/payment.lotus f9308a019258c31049344f85f89d5229b531c845836f99b08601f113bce036f9 /tmp/lotus-payment-abi
node examples/run-payment.mjs
```

`run-payment.mjs` signs with the public BIP340 test key 3 and zero auxiliary randomness. It prints actual transaction bytes and machine-readable stage results. Its signed wire, TxID, TxHash and signing digest match the independent Python reference candidate at `c0126889`; the same values appear in native C++ candidate `40a5479a` tests. These candidates are pending integration review. No VM invocation, contextual coin/lock check, block fee-floor check, connect or disconnect is claimed. The `stages` fields report these as `unavailable`.

## Offline test fixtures

`buildPaymentFixture(input)` in `@lotus/v2-payment-compiler/fixtures` accepts explicit source, 32-byte x-only owner, deterministic public test secret, ChainID, outpoint, sequence, lock, resolved coin, output list, profile and signing mode `0` (FULL). Its amounts and lock use `bigint`; the JSON CLI accepts canonical decimal strings. The test secret is an input to the offline builder and is **never included in exported fixtures**. The fixture has schema `lotus-v2/payment-fixture/1`, a signature-valid baseline with complete transaction bytes, and three named mutations: changed output value, changed ChainID and changed owner. Each mutation retains the original signature and records `expectedStage: signature` and the rejection reason. These are stage expectations, not full consensus-valid/invalid claims.

```sh
npm run build
node examples/generate-fixtures.mjs
node dist/fixture-cli.js input.json output.json
```

The CLI input uses schema `lotus-v2/payment-fixture-input/1`. It has the same fields as `PaymentFixtureInput`, except `coin.value` and output values are `valueAtoms` decimal strings and `lock` is a decimal string. Each output has `flags: 0`, `branches: [lowercase-h32]`, and `paths: [[0]]` for this slice. `profile` must be `payment-fixture-p01-v1`, `signingMode` must be `0`, and the first output must be positive so a changed-value mutation is possible. The builder rejects a test secret whose public key differs from `owner`. Its JSON output can be consumed by daemon fixture generators or native tests without importing the TypeScript compiler into consensus code.

The checked-in key-3 one-output fixture reproduces the independent hand vector. The key-4 two-output fixture varies the script/policy, input outpoint, amounts and output count. Generated TypeScript and Python wrappers are executed in tests and produce the same signed witness bytes. The Python test supplies a small wire adapter through the generated runtime protocol; a maintained production Python runtime is still outstanding.

To check those newly generated bytes against the separate native signing candidate:

```sh
cmake -S test/native-check -B /tmp/lotus-compiler-native -GNinja \
  -DLOTUS_V2_CPP=/path/to/native-candidate/src/lotus_v2 \
  -DLOTUS_SECP_LIBRARY=/path/to/libsecp256k1.a
cmake --build /tmp/lotus-compiler-native
node test/run-native-fixtures.mjs /tmp/lotus-compiler-native/compiler_fixture_native_check
```

This checker runs native framing, identities, signing message and BIP340 verification for both baseline transactions and all six changed-context/signature mutations. It does not run VM execution. Recovery, mint and stateful fixture builders follow only after their corresponding protocol slices and validation APIs are available.

The artifact schema is `lotus-v2/payment-artifact/1`; its target is `P01-P02-P03-candidate-2026-10-14`. JSON hashes and bytecode are lowercase hex; user-facing native amounts must be decimal atom strings and parsed to checked `bigint`. The runtime accepts no implicit network and rejects an artifact whose policy root does not match its script. Generated clients must pin this schema and supply a separately reviewed signer; they must not assume that a valid signature alone makes a transaction valid.

Current source mapping records UTF-16 offsets (JavaScript string offsets) and byte intervals in the emitted script. A future compiler profile should define UTF-8 source byte offsets for cross-language editor interoperability. This is a schema issue before broader language support.

## Bounded template and method frontend (artifact schema 2)

`compileContract(source, { contract, bindings })` in `@lotus/v2-payment-compiler/generic` compiles one selected contract from a source that may contain multiple contracts and free pure helpers. Every constructor value for every referenced contract must be supplied explicitly. It emits `lotus-v2/contract-artifact/2` with ordered method arguments, each method's script, leaf, bottom-up membership proof, source map and static size/stack report. The policy is one P02 branch root with path `[[0]]`. The deterministic wallet tree sorts distinct method leaves as unsigned little-endian hashes, splits at the greatest power of two below the leaf count, and uses P02's sorted-child node hash. Method names select an ABI entry; consensus sees the revealed script and proof, with no numeric method index.

```text
function digest(x: Bytes32): Bytes32 { return sha256(x); }
contract Vault<owner: PublicKey, target: Bytes32> {
    function spend(sig: Signature) { require(checksig(sig, owner)); }
    function reveal(data: Bytes32) { require(digest(data) == target); }
}
```

Supported constructor and method types are `PublicKey` (validated BIP340 x-only point), `Signature`, `Bytes32`, `Bytes(N)` (up to N bytes, N in 1..8192), signed 128-bit `Int`, `Bool`, and distinct `MethodLeafHash` / `ContractRootHash` values. Constructor byte values are lowercase hex, Int values canonical decimal strings or `bigint`, and Bool values booleans. Methods take ordered wire arguments. Expressions include `checksig`, `sha256`, `hash256`, `blake3`, equality, limited checked integer arithmetic/comparison, Boolean operators and unary `!`/`-`. Statements are `require(expr);` and bounded `if (expr) { ... } else { ... }`. A method finishes with exactly one true value after its requirements pass. Free helpers have a single typed return expression; they inline at calls with scoped parameters and source origin spans. There are no mutable locals, loops, external effects, general macros or arbitrary opcodes.

`leaf_hash(Other.method)` yields a `MethodLeafHash` of a fully bound compiled method. `contract_root(Other)` yields a `ContractRootHash` of a fully bound contract. Their types are distinct from plain `Bytes32`. A self or mutual dependency through these builtins is rejected, as are recursive helpers. Source spans in schema 2 are **UTF-8 byte offsets**; schema 1 Payment artifacts retain their historical UTF-16 code-unit offsets. Schema 2 limits source to 65536 UTF-8 bytes, methods to 16, scripts to 8192 bytes, opcodes to 4096, helper expansions to 256, and expression/control nesting to 64/16. Normal compilation emits only assigned P03 opcodes and rejects unsupported syntax, including an `OP_SUCCESS_N` spelling.

The v2 CLI reads source plus an options JSON object, then writes `artifact.json` and a generated TypeScript call wrapper:

```sh
node dist/generic-cli.js vault.lotus options.json /tmp/vault-artifact
```

For the example, `options.json` is `{"contract":"Vault","bindings":{"Vault":{"owner":"<32-byte lowercase hex>","target":"<32-byte lowercase hex>"}}}`. The schema is [artifact-v2.schema.json](artifact-v2.schema.json). Schema 1 artifacts are not reinterpreted as schema 2; its signed fixture remains an independent historical vector. The generated TypeScript wrapper calls the maintained `@lotus/v2-payment-compiler/call-runtime` interface once that separate runtime is integrated. Compilation has no RPC, wallet, filesystem import, or signing side effect; the CLI only reads its declared source/options and writes requested artifact files.
